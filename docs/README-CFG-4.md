# CFG-4 + FIX-30: свой набор диагностик доезжает до анализатора

Задача звучала как настроечная: «можно ли при разворачивании bsl-checker
подкинуть файл конфигурации». Ответ — можно, механизм штатный. Но при
разборе выяснилось, что механизм в проекте **уже был наполовину сделан**,
и эта половина маскировала отсутствие второй.

---

## Что было найдено (FIX-30)

Переменная `BSL_LS_CONFIG` читалась в `server.py`. Ключ `--configuration`
собирался в двух местах. `bsl_stats` даже проверял, есть ли файл. Всё это
выглядело работающим механизмом.

Не работало вот что:

```python
def _run_analysis(src_path, config_path="", ...)   # параметр есть
...
_run_analysis(tmpdir, file_path=...)               # строка 373 — без него
_run_analysis(str(p.parent), file_path=...)        # строка 439 — без него
_run_analysis(str(p))                              # строка 491 — без него
```

Ни один из трёх инструментов конфигурацию не передавал. Она доезжала
только до долгоживущего BSL LS — потому что там передаётся через
конструктор клиента, а не аргументом вызова.

Следствия на боевом стенде:

| Инструмент | Быстрый путь (LSP) | Запасной путь (`--analyze`) |
|---|---|---|
| `bsl_check_code` | ваш набор | **по умолчанию** |
| `bsl_check_file` | ваш набор | **по умолчанию** |
| `bsl_check_directory` | не используется | **по умолчанию, всегда** |

То есть `bsl_check_directory` — единственный инструмент, который смотрит
настоящую выгрузку, — работал набором по умолчанию независимо ни от чего.
А `bsl_check_file` при упавшем LSP молча менял состав правил посреди
сессии, и признака в ответе не было.

Это тот же жанр, что `FIX-6` (query-builder читал несуществующие свойства
графа) и `FIX-16` (запрос искал ребро `СОДЕРЖИТ`, которого нет):
инструмент не работает, но выглядит работающим, потому что отвечает
правдоподобно.

## Почему дефект прожил столько заходов

Потому что каждая его половина по отдельности выглядела правильной.
Переменная читалась — значит, поддержка есть. Ключ собирался — значит,
работает. `bsl_stats` показывал файл на месте — значит, применён.

Проверить это тестом «по коду» было нельзя: тест вида «`_run_analysis`
принимает `config_path`» был бы зелёным и до правки. Проверять надо
**команду, которая уходит в JVM**, — ровно тот приём, что в
`tests_graph_contract.py` (`TEST-1`): сверять не намерение, а то, что
уходит наружу.

## Что сделано

### 1. Команда для JVM собирается в одном месте

Корень дефекта не в забытом аргументе, а в том, что почти одинаковый argv
собирался в **трёх** местах: `server._analyze_dir`,
`bsl_lsp._default_launcher` и `bsl_lsp._compare`. Ключ `--configuration`
был в двух из трёх, доезжал из одного.

Сборка переехала в `bsl_config.analyze_argv` / `bsl_config.lsp_argv`, обе
стороны только зовут. Третью точку (в сверке `--compare`) нашёл тест — она
не была в плане правки.

### 2. Новый модуль `mcp-bsl-checker/bsl_config.py`

Читает файл один раз при старте и отвечает на вопрос «каким набором правил
получен отчёт»:

- разбор JSON с `utf-8-sig` — BOM из блокнота Windows ломал бы разбор, и
  рабочий файл выглядел бы битым;
- отпечаток `sha256:xxxxxxxxxxxx` — чтобы было видно, читает ли контейнер
  новый файл;
- `mode`, число объявленных и включённых правил, `language`,
  `configurationRoot`;
- решение **не передавать битый конфиг** анализатору.

Последнее — единственное неочевидное решение в правке. С битым JSON BSL LS
не поднимается ни быстрым путём, ни запасным: деградация («проверили не
тем набором») превратилась бы в полный отказ («не проверили вовсе»).

### 3. Секция `config` в каждом ответе проверки

```json
{
  "status": "ok",
  "message": "Ошибок не найдено",
  "config": {
    "applied": true,
    "path": "/app/bsl-config/bsl-language-server.json",
    "fingerprint": "sha256:1f4c9ab27de1",
    "mode": "ONLY",
    "diagnostics_enabled": 84
  }
}
```

При `mode: ONLY` «замечаний не найдено» значит «не найдено **из этого
списка**». Без отпечатка такой отчёт нельзя ни воспроизвести, ни сравнить
с прошлым.

Не применён — ответ помечается `degraded: true` с причиной (`OBS-1`), а в
секции стоит `"ruleset": "по умолчанию (BSL Language Server)"`.

### 4. Строгий режим `BSL_LS_CONFIG_STRICT`

Выключен по умолчанию. Включённый — отвечает отказом (`answerable: false`)
вместо проверки не тем набором. Продолжение `A-5`: там мы отказались
считать «набор не запускался» успехом, здесь — «проверил не теми
правилами».

### 5. Проверка `configurationRoot`

Ищется относительно **анализируемого каталога**, а не относительно файла
настроек. В вашем файле стоит `"configurationRoot": "УБД"`, значит корень
должен лежать в `<WORKSPACE_DIR>/УБД`.

Если его там нет, BSL LS молчит: просто не подтягивает метаданные, и
диагностики, которым они нужны, не срабатывают. Отчёт выглядит чище, чем
код — худший из возможных исходов для проверяющего инструмента. Поэтому
`bsl_check_directory` сверяет это сам и кладёт `config.warning` в ответ.

### 6. Инфраструктура

- `./bsl-config/` — каталог с вашим файлом и README.
  **Монтируется каталог, а не файл**: docker при bind-mount
  несуществующего файла создаёт на его месте каталог, и опечатка в пути
  дала бы не «файла нет», а невнятную ошибку чтения.
- `docker-compose.yml` — монтирование `:ro` + две переменные.
- `.env.example`, `Dockerfile.bsl` (`COPY bsl_config.py`).

## Тесты

`tests_bsl_config.py`, 22 теста. Полный прогон: **1154 теста, 43 набора,
14 с**, все зелёные.

Первая версия тестов импортировала `server.py` и была бы честнее — но
`server.py` не импортируется без пакета `mcp`, то есть набор молча не
запускался бы в прогоне на голом Python. Ровно тот случай, ради которого в
`A-5` появился `--strict`. Поэтому проверяемая логика (сборка argv,
правило строгого режима) вынесена в `bsl_config`, где её видно прогону.

Отдельно стоит `test_both_callers_use_the_shared_builder`: он запрещает
собирать команду для JVM на месте. Пока сборка живёт в нескольких
функциях, следующий добавленный ключ заведёт расхождение заново — и
`FIX-30` повторится под другим номером. Этот тест и нашёл третью точку
сборки в `--compare`.

## Приёмка на стенде

Пересборка нужна: в образ добавился файл.

```powershell
docker compose build mcp-bsl-checker
docker compose up -d --force-recreate --no-deps mcp-bsl-checker
```

⚠️ `docker compose restart` **не** подхватывает новый образ — на это уже
наступали при приёмке `SCALE-1`. `--no-deps` — чтобы не потянуть индексер
с его четырнадцатью минутами сканирования.

### 1. Конфиг применён

`bsl_stats` → секция `config`:

```
applied: true
fingerprint: sha256:…
mode: ONLY
diagnostics_declared: 85, diagnostics_enabled: 84
```

`applied: false` — смотрите `error` там же.

### 2. Главное: набор доезжает до `--analyze`

Ради этого весь заход. Быстрый путь надо выключить и убедиться, что состав
замечаний не изменился:

```powershell
docker compose up -d --force-recreate --no-deps -e BSL_LSP_MODE=off mcp-bsl-checker
```

Затем в Cursor — `bsl_check_code` на фрагменте с модальным окном
(`Предупреждение("текст")`). До правки на этом пути диагностика
`UsingModalWindows` бралась из набора по умолчанию; теперь — из вашего.
Различить можно по любому правилу, которое вы **выключили**: в вашем файле
это `UnusedLocalMethod: false`. Неиспользуемый локальный метод не должен
дать замечания ни быстрым путём, ни медленным. До правки медленный путь
его бы показал.

Не забудьте вернуть `BSL_LSP_MODE` обратно.

### 3. `configurationRoot`

```powershell
docker exec mcp-bsl-checker ls /data/1c-src
```

Есть каталог `УБД` — хорошо. Нет — либо поправьте путь в файле настроек,
либо уберите параметр вовсе; `bsl_check_directory` в ответе скажет то же
самое полем `config.warning`.

### 4. Сверка двух путей одним набором

```powershell
docker exec mcp-bsl-checker python3 /app/bsl_lsp.py --compare
```

Теперь она печатает применённый набор первой строкой и идёт им же. Ожидание
— `СОВПАДАЕТ`. Расхождение здесь означало бы, что пути всё-таки читают
разные правила.

### 5. Деградация видна

```powershell
docker compose up -d --force-recreate --no-deps -e BSL_LS_CONFIG=/app/bsl-config/нет-такого.json mcp-bsl-checker
```

Любая проверка обязана ответить `degraded: true` и назвать причину, а не
промолчать. Вернуть переменную обратно.

## Чего правка не делает

- **Не валидирует состав правил.** Опечатка в имени диагностики
  (`UsingModalWindws`) остаётся незамеченной: BSL LS её игнорирует, мы
  считаем её объявленной. Проверять состав по схеме анализатора — отдельная
  работа, и её цена (тянуть в образ JSON Schema и держать её в
  соответствии с `BSL_LS_VERSION`) выше пользы.
- **Не перечитывает файл на лету.** Состав правил не должен меняться
  посреди сессии оттого, что кто-то сохранил файл; перечитывается
  перезапуском контейнера, как всё остальное в наборе.
- **Не ведёт список правил при обновлении BSL LS.** При `mode: ONLY` новые
  диагностики следующих версий будут выключены молча. Это плата за
  управляемый список, и её надо помнить при смене `BSL_LS_VERSION` в
  `Dockerfile.bsl`.

## Замечание не по теме правки

В присланном архиве `tests_docs_canon.py` красный: в корне нет ни одного
`PLAN-*.md` (он лежит только в `docs/archive/PLAN-8.md`), а тест требует
ровно один — действующий. Похоже, план просто не попал в архив. Если в
корне он есть — набор зелёный, и это замечание не про вас.
