# Развёртывание 1C MCP Suite

> Статья для Confluence. Короткая инструкция «с нуля до рабочего агента»
> для того, кто разворачивает набор у себя на машине. Устройство набора —
> `ARCHITECTURE.md`, полное описание инструментов и режимов отказа —
> `README.md`; здесь только то, что нужно сделать руками.

## Что это

Набор MCP-серверов, дающих AI-агенту знание о **конкретной конфигурации
1С**: граф метаданных и вызовов, синтаксическая справка платформы,
конструктор запросов, статический анализ BSL, стандарты разработки.

Без него агент отвечает про 1С «вообще» и выдумывает имена объектов —
проектной конфигурации в его обучающих данных нет. С ним он сначала
спрашивает граф, а потом отвечает.

Серверы независимы и подключаются к любому клиенту, который умеет MCP по
Streamable HTTP: Cursor, OpenCode, собственное расширение для EDT.

| Сервер | Порт | Что даёт |
|---|---|---|
| `metadata-graph` | 8001 | структура конфигурации и граф вызовов (Neo4j) |
| `bsl-checker` | 8002 | статический анализ через BSL Language Server |
| `platform-help` | 8003 | синтакс-помощник платформы, поиск по `.hbk` |
| `query-builder` | 8009 | построение, валидация и разбор запросов |
| `v8std-mcp` | 8765 | стандарты разработки (чужой сервер, CC0) |

Транспорт один: **Streamable HTTP, эндпоинт `/mcp`, stateless**. Все порты
публикуются только на `127.0.0.1`.

## Что понадобится

- **Docker Desktop, лимит памяти не меньше 8 ГБ.** При 4 ГБ индексатор
  справки падает по OOM — он берёт ~2 ГБ только под модель;
- Python 3.10+ на хосте — нужен только проверочным скриптам;
- **XML-выгрузка конфигурации** в `workspace/`;
- **файлы справки платформы** `.hbk` в `platform-help-data/` — берутся из
  `bin\conf` установленной платформы;
- сеть — один раз, на сборку образов и загрузку корпуса стандартов.

Дисковое место: ~12 ГБ под образы, плюс граф Neo4j (на конфигурации в
16 тысяч объектов — около 3 ГБ).

## Установка

### 1. Секреты

```powershell
Copy-Item .env.example .env
```

Заполнить два обязательных поля:

```dotenv
MCP_SHARED_SECRET=<64 hex-символа>
NEO4J_PASSWORD=<случайная строка без спецсимволов>
```

Сгенерировать:

```powershell
python -c "import secrets; print(secrets.token_hex(32))"
```

Пустое значение любого из них — **серверы не стартуют**, выход с кодом 78.
Это намеренно: раньше пустой секрет просто отключал авторизацию, и стек
поднимался открытым с предупреждением в логе, которое никто не читает.

⚠️ Если Neo4j уже поднималась, пароль хранится **внутри тома**, и
`NEO4J_AUTH` его не переопределит — переменная работает только при первой
инициализации. Менять так:

```powershell
docker compose exec neo4j cypher-shell -u neo4j -p <старый> `
  "ALTER CURRENT USER SET PASSWORD FROM '<старый>' TO '<новый>'"
```

### 2. Проверка окружения

```powershell
python scripts\check_prereqs.py
```

Проверяет Docker, `.env`, пароли, наличие выгрузки и справки. Скрипт
ничего не чинит — только показывает, чего не хватает.

### 3. Корпус стандартов

```powershell
python scripts\fetch_v8std.py
```

Кладёт в `v8std-data/` индекс стандартов и модули сервера v8std, пишет
`FETCH.json` с коммитом и sha256 каждого файла. Сеть нужна только здесь —
дальше контейнер работает офлайн.

Шаг можно пропустить: при пустом каталоге сервер возьмёт индекс с
`v8std.ru` сам при старте, но тогда сеть нужна при каждом холодном старте.

### 4. Сборка и запуск

```powershell
docker compose build
docker compose up -d
```

**Первая сборка — 10–15 минут**, образ с моделями эмбеддингов тяжёлый.
**Первая индексация справки — час-полтора на CPU**, индексация
конфигурации — около двух часов на 16 тысяч объектов. Это разовая работа:
последующие запуски стартуют мгновенно, потому что отпечаток исходников
совпадает и переиндексация не запускается.

В логе каждого сервера должно быть три строки:

```
[tool-filter] metadata-graph: профиль=core, инструментов 29 -> 18
[mcp-auth] metadata-graph: auth ENABLED (secret length=64)
[mcp-http] metadata-graph: Streamable HTTP на http://0.0.0.0:8001/mcp (stateless, auth on)
```

### 5. Приёмка

```powershell
bash scripts\smoke_zahod1.sh
```

Проверяет главное: секретов нет в репозитории, без заголовка
`Authorization` серверы отвечают 401, с заголовком — 200, порты не слушают
наружу, состав инструментов в бюджете.

### 6. Подключение Cursor

Положить `.cursor/mcp.json` в корень **рабочего проекта 1С** — того, где
лежит выгрузка, а не обязательно этого репозитория:

```json
{
  "mcpServers": {
    "metadata": {
      "url": "http://127.0.0.1:8001/mcp",
      "headers": { "Authorization": "Bearer <секрет из .env>" }
    },
    "v8std": {
      "url": "http://127.0.0.1:8765/mcp"
    }
  }
}
```

Секрет вписывается строкой: подстановка `${MCP_SHARED_SECRET}` работает не
во всех версиях Cursor. Файл в `.gitignore`, коммитить его не нужно.

У `v8std` заголовка нет намеренно — сервер чужой и нашу схему авторизации
не знает.

Проверить независимо от Cursor:

```powershell
npx @modelcontextprotocol/inspector
```

Transport — `Streamable HTTP`, адрес `http://127.0.0.1:8001/mcp`, заголовок
`Authorization: Bearer <секрет>`.

## Ежедневная работа

### Обновление графа после правок конфигурации

Выгрузили изменения — граф надо обновить. Полная переиндексация для этого
не нужна: она стоит 1,5–2 часа, а частичное обновление — минуты.

Есть два пути, и выбор между ними стоит сделать осознанно.

#### Путь 1: вручную, пакетом (по умолчанию)

```powershell
# посмотреть, что изменилось (ничего не меняет)
docker compose run --rm --entrypoint python metadata-indexer /app/apply_changes.py --dry-run

# применить
docker compose run --rm --entrypoint python metadata-indexer /app/apply_changes.py
```

Скрипт обновляет затронутые объекты **вместе с их модулями**, пересчитывает
отпечатки исходников и снимок счётчиков рёбер, а в конце проверяет
целостность графа. Это важно: после него следующий `docker compose up` не
уйдёт в полную переиндексацию, потому что отпечатки сходятся.

Частичное обновление невозможно, если изменился `Configuration.xml`
(он задаёт состав конфигурации целиком), если правок больше 300 или если
сохранённого состояния ещё нет. Скрипт в таких случаях отказывается сам и
называет причину.

#### Путь 2: автоматически, контейнером `workspace-watcher`

Watcher следит за каталогом выгрузки и сам зовёт точечную переиндексацию
через 3 секунды после сохранения файла. Включается в `.env`:

```dotenv
WATCHER_ENABLED=true
WATCHER_POLLING_INTERVAL=10
```

**По умолчанию на наших стендах он выключен**, и вот почему. На Windows
события файловой системы в контейнер через bind-mount не доходят, поэтому
watcher работает **опросом**: периодически пересканирует всё дерево
выгрузки. На конфигурации в 16 тысяч объектов один такой обход стоит
примерно столько же, сколько явный запуск обновления, — только платится он
круглосуточно. Интервал в 10 секунд вместо стандартных 2 снижает эту цену
в пять раз и на удобство не влияет: выгрузка меняется не чаще чем раз в
несколько минут.

Второе отличие тоньше и важнее: **watcher не трогает отпечатки
исходников**. Граф после него свежий, а отпечатки старые — и ближайший
перезапуск `metadata-indexer` увидит расхождение и уйдёт в полный прогон
на два часа. Поэтому даже с включённым watcher время от времени полезно
прогонять `apply_changes.py` — он приводит отпечатки в соответствие.

#### Что общего у обоих путей

Слой кода собирается **глобальным** резолвом: тип параметра в модуле A
зависит от вызова в модуле B. Точечное обновление такой сходимости не
даёт, поэтому покрытие резолва после серии частичных обновлений медленно
падает. Раз в несколько недель имеет смысл прогнать полную
переиндексацию — она пересобирает связи целиком.

### Проверка, что граф в порядке

Спросите агента: **«покажи статистику графа»**. Смотреть на три вещи:

| Поле | Норма |
|---|---|
| `code.ownership.state` | `ok` |
| `code.ownership.without_owner` | небольшое число (единицы-десятки) |
| `index` — возраст отпечатков | сопоставим с датой последней выгрузки |

Если `ownership.state` = `broken`, связь «модуль → его методы» в графе
разрушена: вопросы про состав методов объекта отвечать нечем. В ответе
будет `answerable: false` и подсказка. Починка:

```powershell
docker compose run --rm --no-deps -e METADATA_FORCE_BSL=true metadata-indexer
```

### Перезапуск после обновления кода серверов

```powershell
docker compose build <сервис>
docker compose up -d --force-recreate --no-deps <сервис>
```

⚠️ `docker compose restart` **не подхватывает новый образ** — только
`up -d --force-recreate`. Флаг `--no-deps` не даёт зацепить индексатор и
потратить лишние минуты на сканирование выгрузки.

## Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| Серверы не стартуют, код выхода 78 | пустой `MCP_SHARED_SECRET` или `NEO4J_PASSWORD` в `.env` |
| Cursor не видит инструменты | секрет в `.cursor/mcp.json` не совпадает с `.env`; проверьте Inspector'ом |
| Агент отвечает про 1С «вообще», не заглядывая в граф | инструменты не подключились либо агент не получил указания ими пользоваться — см. `PROMPTS.md` |
| Индексатор справки падает | лимит памяти Docker меньше 8 ГБ |
| Ответы приходят не на русском | зависит от выбранной модели; правило языка — `.cursor/rules/language.mdc` |
| Сборка падает на скачивании пакетов | системный прокси; переменные для контейнеров закомментированы в `docker-compose.yml` |

Логи любого сервиса:

```powershell
docker compose logs --tail=50 <сервис>
```

Кириллица в PowerShell приезжает битой — лечится в текущем окне:

```powershell
[Console]::OutputEncoding = New-Object System.Text.UTF8Encoding $false
```

## Что важно понимать про ответы

Каждый ответ наших серверов содержит два служебных поля:

- **`answerable`** — можно ли опереться на ответ. `false` означает «данных
  нет», а не «в конфигурации этого нет»;
- **`meaning`** — что этот ответ НЕ значит. Поле написано для модели и
  удерживает её от неверного вывода.

Это не украшение. Самый частый и самый незаметный отказ такого набора —
когда агент отвечает уверенно и мимо: имя объекта звучит правдоподобно, а
объекта нет. Поля `answerable` и `meaning` существуют, чтобы отличить «не
знаю» от «нет».
