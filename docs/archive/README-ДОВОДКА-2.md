## FIX-14 — тридцать секунд тишины на первый вопрос

`1c-mcp-suite/mcp-platform-help/server.py`
(и та же правка в `optional-ubrat-its/`, чтобы наборы не расходились)

В прогоне датасета это выглядело безобидно — одна аномалия на десять
примеров:

```
  [  1/10] ph-001   ✓ hard 2/2  (31950 ms, mode=hybrid)
  [  2/10] ph-002   ✓ hard 2/2  (  162 ms, mode=hybrid)
```

`_get_model()` тянет e5 в память при первом обращении. В датасете это
разовая цифра, а в чате — тридцать секунд молчания на первый вопрос про
платформу после каждого рестарта контейнера. Достаточно, чтобы агент счёл
инструмент неотвечающим и пошёл отвечать по памяти — ровно тот исход,
ради предотвращения которого весь набор и строился.

Теперь модель греется в фоновом потоке при старте, вместе с одним холостым
`encode`: ленивая инициализация внутри torch тоже стоит секунд, и грузить
только веса недостаточно.

Поток демонический и не блокирующий: сервер принимает соединения сразу,
иначе healthcheck не дождётся старта. Если запрос всё же придёт раньше
прогрева — подождёт ровно там же, где ждал раньше, хуже не станет.
Прогрев — оптимизация, а не условие работы: при любой ошибке пишем в лог и
возвращаемся к ленивой загрузке.

Отключается `HELP_WARMUP=0` — в отладке лишние 2 ГБ ни к чему.

Проверено на четырёх сценариях: нормальный прогрев, модель не загрузилась,
`encode` падает, прогрев выключен. Ни в одном процесс не валится.

## Покрытие FIX-13 измерением

`evals/datasets/platform_help.jsonl` — три новых примера, `ph-011`…`ph-013`.

`FIX-13` добавил в индекс 87 чанков со страницами языка запросов и
синтаксиса, и ни один пример их не трогал. По правилу `PLAN-4 §EVAL-1`
функциональность без измерения не считается сделанной — тем более эта:
именно её отсутствие и позволило дефекту прожить недели, потому что
«HTML: 25, чанков: 0» никто не читал.

- `ph-011` — поиск «разыменование полей в запросе через точку». Заголовок
  «Разыменование полей» взят из настоящей страницы `field_dereferencing.html`,
  вытащенной из `shquery_ru.hbk`, поэтому проверка жёсткая. Это главный
  сторож: до `FIX-13` этой страницы в индексе не было вовсе.
- `ph-012` — «псевдоним источника данных». Заголовок известен только по
  ссылке внутри соседней страницы, точное написание не проверялось —
  поэтому в `soft`. Ошибка в угаданном названии означала бы провал теста, а
  не регресс кода.
- `ph-013` — тот же заголовок через `platform_help_lookup`. Проверяет, что
  у статей заполняется `name_ru`, а не только текст описания: если фолбэк
  начнёт класть заголовок в описание, `ph-011` может пройти на семантике, а
  этот — нет.

## Что смотреть после применения

**В логе контейнера** — строка прогрева:

```powershell
docker logs mcp-platform-help --tail 20
```

Ожидается `✓ Модель прогрета, поиск готов` через 20–40 секунд после старта.

**В прогоне датасета** — 13 примеров вместо 10, и первый уже без
тридцатисекундного всплеска:

```powershell
python scripts\eval.py --dataset evals\datasets\platform_help.jsonl
```

Если `ph-011` или `ph-013` упадут, а `ph-001`…`ph-010` пройдут — значит
статьи в индекс не попали. Проверьте, что индексация шла с исправленным
`hbk_parser.py`: в её логе у `shquery_ru.hbk` должно быть ненулевое число
чанков.

`ph-012` в hard проверяет только непустоту, так что его soft-часть может не
пройти — это ожидаемо и означает лишь, что я угадал заголовок неверно.
Посмотрите в отчёте, что реально нашлось, и поправьте `values`.
