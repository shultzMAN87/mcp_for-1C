# B-7. `bsl_stats` — «как ты себя чувствуешь» для bsl-checker

Дата: 16 августа 2026. Задача из `AUDIT-2`, оценка была 2 часа.

---

## Что было

Инструмент состояния есть у трёх серверов набора из пяти: `metadata_stats`,
`platform_help_stats`, `v8std_stats`. У `bsl-checker` не было ничего.

`OBS-1` научил его отказы различать — `linter_missing`, `analysis_timeout`,
`report_missing`, `report_unreadable` приезжают по-разному и честно говорят
«ответа нет». Но узнаёт об этом модель только после того, как дождётся
конца анализа. В худшем случае это 120 секунд ожидания, чтобы услышать
«java не найдена».

Спросить заранее было нечем.

## Что стало

Четвёртый инструмент сервера: `bsl_stats`, без параметров.

```json
{
  "linter_available": true,
  "answerable": true,
  "degraded": false,
  "meaning": "Анализатор готов отвечать. Это состояние инструмента, а не суждение о коде…",
  "java": {"available": true, "version": "17.0.10", "runtime": "…Temurin-17.0.10+7…", "probe_ms": 99},
  "jar":  {"present": true, "version": "0.28.5", "size_mb": 43.2, "modified_iso": "…"},
  "config": {"path": "", "present": null, "note": "BSL_LS_CONFIG не задан…"},
  "analysis": {
    "runs_total": 12, "runs_ok": 11, "runs_failed": 1,
    "failures_by_error": {"analysis_timeout": 1},
    "last_ok_iso": "2026-08-16 09:14:02", "last_ok_age_sec": 41.3,
    "last_ok_duration_sec": 12.8,
    "timeout_sec": 120, "java_opts": "-Xmx1g",
    "note": "Счётчики живут в памяти процесса…"
  },
  "checked_at_iso": "2026-08-16 09:14:43",
  "probe_note": "Проверка выполнена сейчас, кеша нет…"
}
```

### Три решения, которые стоит знать

**Он отвечает и тогда, когда анализатор мёртв.** `answerable: true` даже
при отсутствующей java: «java не найдена» — это достоверный ответ на
заданный вопрос, а не поломка инструмента. Неготовность видна по
`linter_available: false` и `degraded: true`.

Так же устроен `metadata_stats` после `FIX-3`: он обязан отвечать на пустом
графе, потому что его дело — отличить «объекта нет» от «граф не построен».
Инструмент состояния, отказывающийся отвечать, когда плохо, бесполезен
ровно в тот момент, ради которого написан.

**Кеша нет, и это решение.** Урок приёмки 15 августа: `metadata_stats` был
обёрнут в `@cached(ttl=600)` и во время аварии отдавал из кеша картину
здоровья работающего графа. К диагностическому инструменту приходят с
вопросом «жив ли ты **прямо сейчас**», и кешированный ответ на такой вопрос
не устарел, а перевёрнут. Ответ это про себя заявляет — поле `probe_note`.

Платить за это почти нечем: `java -version` не грузит jar анализатора
(замер в песочнице — 99 мс), версия jar читается из манифеста обычным
zip-ом, без запуска JVM вообще.

**Нули читаются как «не запускали».** На свежеподнятом контейнере
`runs_total: 0`, и без пояснения это выглядит аварией. Поле `analysis.note`
говорит прямым текстом, что счётчики живут в памяти процесса.

## Что поймалось по дороге

**Отсутствующий jar диагностировался неверно.** До правки он приезжал как
`report_missing`: java стартовала, писала «Unable to access jarfile» в
stderr и уходила с ненулевым кодом, отчёта не было. Формально честно — и
stderr, и код возврата лежали в ответе. По смыслу неверно: «анализатор не
создал отчёт» и «анализатора нет» лечатся разными командами, а различать их
приходилось чтением чужого stderr. Теперь один `stat` перед запуском, и
диагноз `linter_missing` стоит там, где линтера действительно нет.

**Пустой файл — это не «файл есть».** `probe_jar` считает jar меньше
килобайта заглушкой. Это `FIX-11` в миниатюре: сорок заглушек по 0,0 МБ
когда-то прошли `check_prereqs` с галочкой.

**Учёт исходов вынесен в обёртку.** `_run_analysis_inner` делает работу,
`_run_analysis` записывает результат. Расставить `record_*` по пяти точкам
возврата означало бы, что следующая ветка отказа появится без записи и
счётчик тихо разойдётся с действительностью — тот самый жанр «списка,
который надо помнить», четырежды разошедшийся в этом проекте.

**Едва не наступил на `B-4`.** Первая редакция датасета проверяла
`analysis.timeout_sec` предикатом `path_non_empty`. Это число, а предикат
меряет `len` — то есть пример был бы вечно красным без всякого дефекта.
Ровно находка `B-4` из `AUDIT-2`, на которой уже спотыкались `qb-003` и
`mg-404`. Предупреждение оставлено комментарием прямо в датасете, рядом с
местом, где следующий повторит ошибку.

## Применение

```powershell
docker compose up -d --build --force-recreate mcp-bsl-checker
```

`--force-recreate` обязателен: `docker compose restart` не подхватывает
новый образ — на этом уже терялась приёмка `SCALE-1`/`FIX-16`.

## Проверка

Тесты на хосте:

```powershell
python scripts/run_all_tests.py
```

Ожидается **826 тестов в 24 наборах** (было 793 в 23).

Датасет на живом стенде:

```powershell
python scripts/eval.py --dataset evals/datasets/bsl_checker.jsonl
```

Ожидается 9 примеров, hard 9/9.

Ручная проверка отказа — та, которую тесты не сделают. Подмените jar на
несуществующий путь и убедитесь, что `bsl_stats` отвечает мгновенно и
честно, а `bsl_check_code` даёт `linter_missing`, а не `report_missing`:

```powershell
docker compose run --rm --no-deps -e BSL_LS_JAR=/нет/такого.jar mcp-bsl-checker python3 -c @'
import os, json, sys
sys.path.insert(0, "/app")
from bsl_health import health_report
print(json.dumps(health_report(os.environ["BSL_LS_JAR"]), ensure_ascii=False, indent=2))
'@
```

Флаг `--no-deps` не косметический: без него `docker compose run` поднимает
остановленные зависимости обратно, и проверка отказа идёт на здоровом
стенде. Это вторая половина `A-8`, и один раз она уже дала ложные зелёные.

## Что осталось у `bsl-checker`

`PERF-7` — 13 секунд на вызов из-за старта JVM на каждую проверку. `B-7`
эту цену не трогает: он про «спросить заранее», а не про «быстрее
проверить». Держать BSL LS в LSP-режиме — отдельная работа на день.
