# FIX-9 — bsl-checker: анализ не запускался, и это было не видно

Патч поверх основного набора. Распаковать содержимое поверх корня проекта,
затем:

```powershell
docker compose up -d --build mcp-bsl-checker
python scripts\eval.py --dataset evals\datasets\bsl_checker.jsonl
```

## Что было сломано

Три ошибки подряд, каждой из которых хватало по отдельности. Подтверждено
вашим прогоном и сверено с исходниками BSL LS (`cli/AnalyzeCommand.java`,
`reporters/JsonReporter.java`).

**1. Несуществующий ключ.** Обёртка звала анализатор с `--src`. Такого ключа
нет — он `-s, --srcDir`. Неизвестный аргумент не приводил к ошибке:
`srcDir` оставался пустым, то есть текущим каталогом процесса (`/app`), где
`.bsl` нет. В вашем выводе это видно буквально: `Analyzing files... 0/0`.

**2. Чужое имя отчёта.** Отчёт искался как `bsl-ls_report.json` рядом с
исходниками или рядом с jar. `JsonReporter` пишет `bsl-json.json` в
`--outputDir`. В вашем логе: `JSON report saved to /app/./bsl-json.json` —
ни одно из двух мест не совпало. То есть даже с исправленным ключом
`srcDir` отчёт не нашёлся бы.

**3. Отказ выглядел как чистота.** Не найдя отчёт, `_run_analysis`
возвращала `{"diagnostics": []}`, а вызывающий код превращал это в
`{"status": "ok", "message": "Ошибок не найдено"}`. `stdout` и `stderr`
выбрасывались. «Анализатор не отработал» и «код чистый» были для агента
неотличимы.

Практический вывод: `bsl_check_*`, судя по всему, **не возвращал ни одной
диагностики с момента появления** — просто никто не спрашивал у него
заведомо плохой код.

## Что изменено

`1c-mcp-suite/mcp-bsl-checker/server.py`:

- ключи `--srcDir` и `--outputDir` вместо `--src`;
- отчёт читается как `bsl-json.json` из `--outputDir`;
- `--outputDir` — всегда временный каталог. Раньше отчёт лёг бы рядом с
  исходниками, а выгрузка монтируется `:ro` — то есть на
  `bsl_check_directory` запись провалилась бы и с правильными ключами;
- отсутствие отчёта возвращается полем `error` с подсказкой, `returncode`,
  `stdout` и `stderr`. `status: ok` теперь означает ровно одно: анализ
  прошёл, замечаний нет;
- `bsl_check_file` тоже проверяет `error` — раньше шёл дальше вслепую.

`evals/datasets/bsl_checker.jsonl` — 5 примеров. Инструмент не был покрыт
измерением ни одним, и именно поэтому дефект дожил до живой проверки.
Кроме «находит замечания» проверяется и обратное: `bsl-005` требует, чтобы
отказ приезжал полем `error`, а не тишиной.

`scripts/eval.py` — сервер `bsl` в списке, датасет подставляет его сам.

`README.md` — раздел troubleshooting переписан: команда воспроизведения,
что означает `0/0`, чем `--src` отличается от `--srcDir`.

## Чего патч не делает

Не трогает набор диагностик. Если после пересборки замечания появятся, но
не те, что ожидались, — это уже вопрос конфигурации BSL LS
(`BSL_LS_CONFIG`, сейчас пустая, то есть дефолт). Сначала посмотрите, что
он вообще находит.

## Что это меняет в оценке STD-5

Мост `bsl_check_*` → `v8std_explain_diagnostics` был проверен вами только
наполовину: цепочка через `v8std_explain_snippet` отработала, а через
линтер — нет, потому что линтер молчал. После патча проверяйте заново:
`std_lookup.codes` должен быть непустым, и в нём коды вида
`bslls:BeginTransactionBeforeTryCatch`.
