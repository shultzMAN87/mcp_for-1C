# Часть 1. Soft-промахи: их не разбирали, потому что их не видно

## Что было

Приёмка 16 августа: hard 100% во всех пяти датасетах, а soft — 8/9, 11/13,
7/9. Пять промахов, из которых объяснён один (`mg-002`: `min=20` при
`limit=10` — ошибка в ожидании). Остальные четыре прожили незамеченными
несколько недель.

Причина не в лени. Сводка `eval_all.py` печатала «7/9» и на этом
останавливалась, консоль раннера показывала только hard, а имена
промахнувшихся предикатов лежали в `.md`-отчёте, куда без повода не
заглядывают. **Число без имени — не измерение, а лампочка без надписи.**

## Что сделано

Разбирать промахи теперь не нужно просить у кого-то файлы: ответы уже
записаны в отчётах.

**`scripts/soft_misses.py`** читает сохранённые `evals/reports/*.json` и
печатает по каждому непройденному soft-предикату пример, инструмент,
аргументы и `detail` — почему не сошлось. Живой стенд не нужен, прогон не
нужен.

```powershell
python scripts/soft_misses.py                 # последний отчёт каждого датасета
python scripts/soft_misses.py platform_help   # только этот
```

Вывод на ваших вчерашних отчётах ответит на вопрос, который я не смог
закрыть в прошлый заход, — без единого прогона.

**Сводка `eval_all.py` называет промахи по именам** прямо под строкой
датасета, вместе с командой для подробностей.

**Консоль раннера** после строки примера печатает `~ soft 1/2 мимо:
name_in_top_k`, если что-то не сошлось.

Промах — не провал: это либо ошибка в ожидании, либо просадка качества.
Различить можно только прочитав «почему», поэтому `detail` печатается
целиком, а не сворачивается в галочку. Код возврата у `soft_misses.py`
всегда нулевой — это разбор, а не проверка.

## Что нашлось попутно

Список хостовых скриптов в `tests_host_scripts.py` был прибит руками —
четвёртый такой список в проекте после тех, что убрал `B-6`. Заменил на
вычисление по каталогу `scripts/`.

**Он немедленно нашёл дыру: четыре скрипта из девяти были без защиты
потоков** — `check_baseline.py`, `eval.py`, `fetch_v8std.py`,
`list_tools.py`. Это `FAIL-2` ровно в том виде, в каком он уже случался:
на cp1251-консоли `check_baseline.py` упал бы с `UnicodeEncodeError` на
строке «← за допуском» вместо того, чтобы сказать, сошлась база или нет.
Защита добавлена всем четырём, проверено запуском под `PYTHONIOENCODING=cp1251`.

Список, который ведут руками, отстаёт от действительности молча. Это уже
четвёртый случай в проекте.

# Часть 2. `A-7`: `file_path` не был ключом страницы

## Что было

`file_path` уникален внутри одного `.hbk` — и только внутри него. После
`HBK-1` контейнеров стало сорок, и индексатор насчитал **11 страниц из 27
тысяч под уже занятым путём**. Счётчик был добавлен в прошлом заходе,
починка помечена «потом».

Путь использовался ключом в трёх местах, и цена у них разная.

**Самое дорогое — карточка `platform_help_lookup`.** Она собирает
синтаксис, параметры и пример через фильтр Qdrant по `file_path`. На
занятом пути карточка собирала части **чужой** страницы — из другого
контейнера справки. Наружу это выходило не отказом, а правдоподобным
неверным ответом: параметры не того метода. Отличить такую карточку от
верной по ответу нельзя.

**Прореживание выдачи** (`collapse_pages`) считало две разные страницы
одной и выбрасывало вторую как дубль. Не ошибка, просто выдача беднее на
страницу — и заметить это со стороны невозможно.

**Ссылка на источник** в ответе указывала путь без контейнера, то есть
адрес, по которому лежат две разные страницы.

## Что сделано

Ключ страницы — пара `(hbk_file, file_path)`. Поле `hbk_file` лежит в
payload с самого начала (`hbk_chunker._common_fields`), брать его ниоткуда
не пришлось.

- `help_ranking.page_key` — составной ключ, со старым поведением как
  запасным путём для payload без `hbk_file`;
- фильтр связанных чанков — по обоим полям;
- карточка `lookup` и список альтернатив теперь **несут** `hbk_file`.

Последнее — не косметика. Без него `best.get("hbk_file")` возвращал бы
пустоту, фильтр вырождался обратно в поиск по одному пути, и правка стала
бы видимостью правки. Это ровно та ошибка, которую я чуть не сделал:
починил чтение, не проверив, доезжает ли туда второе поле.

## Счётчик в индексаторе теперь считает два разных числа

| Число | Что значит | Норма |
|---|---|---|
| `path_collisions` | сколько путей заняты дважды | **ненулевое** — сорок контейнеров, пути внутри каждого свои |
| `key_collisions` | сколько раз повторилась **пара** | **ноль обязателен** — повтор означает, что страница индексируется дважды |

Первое перестало быть тревогой и стало объяснением, почему ключ составной.
Второе — настоящая тревога с громким предупреждением.

## Проверка

Дефект возвращался в код: `page_key` снова по одному пути — тест
`test_same_path_in_different_books_is_two_pages` краснеет. Контрактные
тесты проверяют текстом по исходнику, что фильтр учитывает контейнер и что
карточка несёт поле (`server.py` не импортируется — он тянет FastMCP и
`qdrant_client`).

Пример `ph-021` в датасете проверяет наличие `hbk_file` в карточке, а не
совпадение содержимого: конкретная коллизия зависит от состава `.hbk`.

## Переиндексация справки НЕ нужна

`hbk_file` уже лежит в payload всех 41 062 чанков. Менялся только путь
чтения. Правка индексатора влияет лишь на то, что он напечатает при
следующей полной переиндексации.
