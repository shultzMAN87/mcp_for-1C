## Что показала приёмка

```
CommonPicture.ЗаказПокупателя    score 9.9404935836792
CommonPicture.ЗаказПоставщику    score 9.9404935836792
DataProcessor.ЗаказТоваров       score 9.9404935836792
```

Две картинки-иконки впереди всех документов, и score у всех совпадает до
последнего знака. Это не совпадение, а следствие двух фактов:

1. **Префиксный запрос Lucene константен по весу.** Все совпадения по
   `заказ*` получают одинаковый score.
2. **Имена в 1С — CamelCase.** «ЗаказПокупателя» это ОДИН токен, поэтому
   точное совпадение слова (`заказ^2`, которое я добавил ради веса) не
   срабатывает **никогда**.

Значит на типичном запросе ранжирования по score просто нет — порядок
целиком определяет тай-брейк. А тай-брейком стоял алфавит по английскому
имени вида: `CommonPicture` < `DataProcessor` < `Document`.

То есть `PERF-6` в том виде, в каком я его сдал, задачу не решал. Скорость
и запасной путь работали, ранжирование — нет.

## Что стало

Три уровня тай-брейка, в порядке убывания надёжности сигнала:

1. **Имя начинается с искомого слова.** Самый сильный признак:
   «ЗаказТоваров» релевантнее «ОбработкаИнтернетЗаказовКладовщиком», хотя
   Lucene дал им одинаковый вес.
2. **Вид объекта.** Справочники, документы, регистры — то, о чём
   спрашивают; картинки, роли, элементы стиля — почти никогда. Это не
   сокрытие: они остаются в выдаче, просто ниже.
3. **Алфавит** — чтобы порядок был воспроизводимым. Без уникального
   последнего ключа Neo4j не гарантирует стабильный порядок при равных
   ключах, и пагинация начнёт задваивать и терять строки на границах
   страниц.

Сортировка одинакова для полнотекстового и запасного путей: иначе выдача
менялась бы при переключении на CONTAINS, и объяснить это было бы нечем.
