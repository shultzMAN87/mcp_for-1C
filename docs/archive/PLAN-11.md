# PLAN-11: граф следит за выгрузкой через git

Дата: 3 ноября 2026. Предыдущий план — `PLAN-10.md`, состояние набора —
`СТАТУС.md`, что не сделано — `ОТКРЫТОЕ.md`.

## Правило захода

Ключевой элемент контроля изменений — **git**. Граф перестаёт угадывать,
что поменялось в выгрузке, по размерам и датам 56 тысяч файлов и начинает
спрашивать об этом git и агента.

Причина в цифрах. Узнать, что изменилось, сейчас можно только обходом:
`stat` каждого файла через границу Docker Desktop стоит около 5 мс, отсюда
3–12 минут на каждый `apply_changes.py` и на каждый старт индексера.
Watcher в контейнере делает тот же обход опросом, круглосуточно, и потому
выключен. События ФС с диска Windows в контейнер не доходят — третьего
пути, кроме «обойти всё» или «получить сигнал», нет. Сигнал есть у двух
источников из трёх, и оба дешёвые:

| Кто меняет выгрузку | Сигнал | Стоимость |
|---|---|---|
| `ubd-git-sync` (pull из GitLab) или коммит после своей выгрузки | сдвинулся `HEAD` → `git diff <проиндексированный>..HEAD` | секунды: читается только `.git` |
| агент (правки в `src/`, без коммита) | агент сам вызывает `metadata_refresh(paths)` | только перечисленные файлы |
| всё остальное (ручная правка, забытый вызов) | ночная сверка | минуты, но раз в сутки |

**Запреты захода.**

1. Всё, что строит и обновляет граф, остаётся в Docker. На Windows-хосте —
   только то, что там уже есть (git, `ubd-git-sync`) и необязательный
   скрипт возврата канона (`SRC-14`).
2. Выгрузка монтируется **только на чтение**. Ни одна git-команда в
   контейнере не пишет в `.git`.
3. Не ломать работу без git. Каталог без `.git` обязан работать ровно как
   сейчас — через отпечатки по `(путь, размер, mtime)`.
4. Не привязываться к IDE. Сигнал агента — MCP-вызов, а не хук Cursor.
   Хуки допустимы только как необязательное ускорение поверх.

Блоки 0 → A → B → C → D → E. Блок 0 полезен сам по себе и делается
первым при любом исходе остальных. Блок F — по отдельному решению.

## Целевая схема

### Раскладка на диске — одна для обоих случаев

```
<корень репозитория>/        ← WORKSPACE_DIR; .git здесь
├── .git/
├── AGENTS.md, .cursor/, openspec/   ← служебное, в граф не идёт
└── src/                     ← CONFIG_SUBDIR; корень конфигурации
    ├── Configuration.xml
    ├── ConfigDumpInfo.xml
    └── CommonModules/, Catalogs/, ...
```

| | Клон GitLab (`ubd_for_ai`) | Своя выгрузка |
|---|---|---|
| Откуда `.git` | `git clone` | `git init` в корне, `core.autocrlf false` |
| Новая версия | `ubd-git-sync`: только `pull --ff-only` | выгрузка `-update` в `src/` + `git add -A` + `git commit` |
| Правки агента | `metadata_refresh` + список `dirty` | то же |

### Состояние источника в графе

Один узел `:SourceState {key: 'main'}` вместо разрозненных отпечатков:

| Свойство | Смысл |
|---|---|
| `mode` | `git` или `legacy` (каталог без `.git`) |
| `config_subdir` | под каким подкаталогом индексировали (`src` или пусто) |
| `indexed_sha` | коммит, по которому граф соответствует выгрузке |
| `dirty` | JSON `{путь: хеш_того_что_в_графе \| "deleted"}` — файлы, где граф отражает диск, а не `indexed_sha` |
| `needs_reconcile` | граф мог разойтись с диском, нужна сверка (после полной индексации, после ошибки) |
| `needs_full` + `needs_full_reason` | частичным обновлением не обойтись; полную индексацию запускает человек или расписание, не цикл |
| `last_cycle_at`, `last_error` | для `metadata_stats` |
| `lock_owner`, `lock_until` | аренда записи: обновляет граф кто-то один |

Инвариант, ради которого всё затевается: **граф = `indexed_sha` + `dirty`**.
Любая операция, обновившая граф, обязана в той же транзакции записи
состояния оставить этот инвариант верным.

### Цикл (раз в `SOURCE_POLL_SEC`, по умолчанию 60 с)

```
взять аренду
1. dirty не пуст → для каждого пути:
     хеш на диске == хеш в HEAD (или оба отсутствуют)
         → переиндексировать с диска (= канон), убрать из dirty
     хеш на диске != хеш в dirty (агент правил ещё раз, не сказав)
         → переиндексировать, обновить хеш в dirty
2. HEAD != indexed_sha →
     git diff --no-renames --name-status indexed_sha HEAD -- <config_subdir>
     минус пути из dirty (их уже обработал шаг 1)
     → удалить D, обновить A/M; indexed_sha = HEAD
3. записать состояние, отпустить аренду
```

Возврат канона (`git stash -u` / `restore`) `HEAD` не двигает — его
ловит шаг 1. Pull ловит шаг 2. Оба шага читают `.git` и несколько
конкретных файлов, обхода выгрузки нет.

### Режимы работы: вручную или автоматически

Такт цикла — **одна и та же функция** при любом способе запуска. Разница
только в том, кто нажимает кнопку. Ручной запуск работает всегда,
включён watcher или нет; watcher лишь вызывает тот же такт по таймеру.

**Ручной запуск доиндексации** — три равноценных способа:

| Откуда | Команда | Когда удобно |
|---|---|---|
| консоль, из корня репозитория стека | `docker compose run --rm --entrypoint python metadata-indexer /app/apply_changes.py` | после pull, после своей выгрузки, после возврата канона |
| то же, короче | `.\scripts\graph-refresh.ps1` / `make graph-refresh` | то же; обёртка над строкой выше, с `--dry-run`, `--reconcile`, `--full` как ключами |
| чат с агентом | `metadata_refresh()` без аргументов | не выходя из Cursor; агент сразу видит результат |

Ключи у всех трёх одинаковые по смыслу:

| Ключ | Что делает |
|---|---|
| (без ключа) | такт: `dirty` + `HEAD` против `indexed_sha` → доиндексация изменившегося |
| `--dry-run` | показать, что будет обновлено, ничего не меняя |
| `--reconcile` | сверка (`SRC-11`): найти изменения, о которых никто не сообщил |
| `--full` | полная индексация (то же, что `METADATA_FORCE_REINDEX=true`), с подтверждением в консоли |

**Автоматический режим — watcher.** Выключен по умолчанию, включается
двумя строками в `.env`:

```dotenv
WATCHER_ENABLED=true
SOURCE_POLL_SEC=60        # раз в минуту; 300 — раз в 5 минут
```

и пересозданием одного контейнера:

```powershell
docker compose up -d --no-deps --force-recreate workspace-watcher
```

Раз в `SOURCE_POLL_SEC` watcher делает такт: если `HEAD` сдвинулся или
изменились файлы из `dirty` — запускает доиндексацию; если нет — ничего
не делает и ничего не пишет в лог. Такт в режиме `git` стоит
миллисекунды, поэтому, в отличие от нынешнего опроса файлов, держать
watcher включённым круглосуточно дёшево.

Дополнительно, по желанию:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SOURCE_RECONCILE_AT` | пусто (выкл.) | время ночной сверки, например `03:00` |
| `SOURCE_AUTO_FULL` | `false` | разрешить watcher'у самому запускать полную индексацию при `needs_full`; по умолчанию только напоминает |
| `SOURCE_FULL_REINDEX_CRON` | пусто (выкл.) | плановая полная индексация (`SRC-13`) |

Включён watcher или нет, видно в `metadata_stats` → `source.watcher`:
режим, интервал, время последнего такта. Выключенный watcher плюс
отставание `HEAD` от `indexed_sha` дают там подсказку: «граф отстаёт на
N коммитов — запустите доиндексацию или включите watcher».

## Блок 0. Сразу и независимо

### `SRC-1` — корневые XML не должны блокировать частичное обновление

**Что сломано.** `partial_fingerprint.owner_of` относит любой XML в корне
выгрузки к `ROOT_KEY`, и `build_plan` при его изменении отказывает:
«изменились корневые файлы конфигурации». В корне лежит
`ConfigDumpInfo.xml`, который меняется **при каждой** выгрузке из
хранилища — для `ubd_for_ai` это до 13 раз в день. Сейчас каждый pull
гарантированно уводит в двухчасовую полную индексацию.

**Почему можно.** Граф содержимое корневых файлов не читает: индексер
только проверяет, что `Configuration.xml` существует; объекты находятся
обходом каталогов (`KIND_BY_DIR`), имя конфигурации берётся из
`METADATA_CONFIG_NAME`. Проверено поиском по коду: `Configuration.xml` и
`ConfigDumpInfo` упоминаются только в `partial_fingerprint.py`,
`indexer.py` (проверка существования) и `mcp-bsl-checker/bsl_config.py`
(другой сервер, к графу не относится).

**Что сделать.**
- `owner_of`: корневые XML → `None` (не участвуют в плане). `ROOT_KEY`
  оставить константой для чтения старых сохранённых состояний, где он
  есть, — иначе первый прогон после обновления покажет «удалён `_root`».
- `build_plan`: ветку отказа по `ROOT_KEY` убрать; `ROOT_KEY` в
  сохранённом состоянии молча отбрасывать.
- Комментарий в `partial_fingerprint.py` («DefinedTypes на верхнем
  уровне») сверить с фактом: `DefinedTypes/X.xml` — это объект
  (`len(parts) == 2`), а не корень.
- README, `docs/РАЗВЁРТЫВАНИЕ.md`: строку таблицы отказов убрать.

**Страховка.** Тест-сторож в `tests_partial_fingerprint.py`: прогнать
`metadata_xml.build_graph` на фикстуре дважды — с исходным
`Configuration.xml` и с изменённым (другой список `ChildObjects`, другие
свойства) — и сравнить графы. Совпали — граф от корневых файлов не
зависит. Если кто-то когда-нибудь начнёт их читать, сторож покраснеет, и
правило придётся вернуть осознанно.

**Мера приёмки.** На стенде: коммит, где изменились только
`ConfigDumpInfo.xml` и `Configuration.xml`, → `apply_changes.py --dry-run`
пишет «Делать нечего», а не код 3.

## Блок A. Раскладка и монтирование

### `SRC-2` — `CONFIG_SUBDIR`: корень репозитория и корень конфигурации разделены

**Сейчас.** `WORKSPACE_DIR` — это корень конфигурации; он монтируется в
пять сервисов (`opencode` → `/workspace`, `metadata-indexer` и
`mcp-metadata-graph` → `/data/1c-xml`, `workspace-watcher` →
`/workspace`, `mcp-bsl-checker` → `/data/1c-src`). Для `ubd_for_ai`
конфигурация лежит в `src/`, а `.git` уровнем выше — контейнер его не
видит.

**Что сделать.**
- Новая переменная `CONFIG_SUBDIR` (по умолчанию пусто = как сейчас).
- `WORKSPACE_DIR` = корень репозитория.
- Сервисы, которым нужен git (`metadata-indexer`, `mcp-metadata-graph`,
  `workspace-watcher`), монтируют **корень** в `/data/repo:ro` и получают
  `METADATA_SRC_DIR=/data/repo/${CONFIG_SUBDIR}`.
- Остальные (`mcp-bsl-checker`, `opencode`) монтируют
  `${WORKSPACE_DIR}/${CONFIG_SUBDIR}` в свою прежнюю точку — им git не
  нужен, и их код не меняется.
- Проверить, что пустой `CONFIG_SUBDIR` даёт путь `…/` с хвостовым
  слешем и это одинаково принимают Docker Desktop на Windows и Docker на
  Linux. Если нет — две строки монтирования через профиль, а не
  подстановка.
- `indexer.py` уже предупреждает, если в корне нет `Configuration.xml`;
  добавить подсказку: «если конфигурация в подкаталоге — задайте
  `CONFIG_SUBDIR`».

**Мера приёмки.** Две конфигурации стенда: старая (`WORKSPACE_DIR` = корень
конфигурации, `CONFIG_SUBDIR` пусто) поднимается без единого отличия в
логах индексера; новая (`ubd_for_ai`, `CONFIG_SUBDIR=src`) индексирует
`src/` и видит `.git`.

**Объём:** S.

### `SRC-4` — пути от агента в любом виде

**Что сломано.** `incremental._norm_rel` понимает относительный путь от
корня конфигурации и абсолютный POSIX-путь. Агент на Windows пришлёт
`D:\projects\Cursor\ubd_config\src\Catalogs\X\Ext\ObjectModule.bsl`:
после замены `\` это `D:/projects/...`, `PurePosixPath` считает его
**относительным** и возвращает как есть — путь неверный, ошибки нет.
Путь от корня репозитория (`src/Catalogs/...`, так его отдаёт и
`git diff`) тоже вернётся как есть, с лишним `src/`.

**Что сделать.**
- Распознавать путь с буквой диска и UNC (`\\wsl$\...`) как абсолютный
  и уходить в существующий фолбэк по хвосту (`_TAIL_TOP_DIRS`).
- Относительный путь, начинающийся с `CONFIG_SUBDIR/`, — срезать префикс.
- Путь вне корня конфигурации (`openspec/...`, AGENTS.md) → явный
  статус `outside_config`, не `file_not_found`.
- Таблица тестов на все формы: Windows абсолютный, UNC, POSIX
  абсолютный, от корня репозитория, от корня конфигурации, с `..`,
  смешанные слеши, кириллица в имени.

## Блок B. Движок источника

### `SRC-5` — `git_source.py`: всё, что спрашиваем у git

Новый модуль рядом с `partial_fingerprint.py`. Чистые функции поверх
обёртки из `SRC-3`, без Neo4j — чтобы тестироваться на временных
репозиториях.

| Функция | Что делает |
|---|---|
| `detect(repo_root, config_subdir)` | `mode='git'` если `rev-parse --show-toplevel` совпал с корнем, иначе `legacy` с причиной |
| `head()` | хеш `HEAD`; на «пустом» репозитории без коммитов — `None` и понятная причина |
| `commit_exists(sha)` | `cat-file -e sha^{commit}`; ложь → состояние недостоверно, нужна сверка |
| `changed_between(a, b)` | `diff --no-renames --name-status -z a b -- <subdir>` → `[(статус, путь_от_корня_конфигурации)]`; переименования приходят парой D+A, отдельной логики не нужно |
| `blob_at_head(path)` | `rev-parse HEAD:<subdir>/<path>` → хеш или `None` (файла в `HEAD` нет) |
| `blob_on_disk(path)` | `hash-object --no-filters <file>`; если не совпал с `HEAD` — повторить с нормализацией CRLF→LF (см. риск ниже) |

**Риск: переводы строк.** Если пользователь когда-то коммитил с
`core.autocrlf=true` (глобальная настройка Windows, контейнер её не
видит), в `HEAD` лежат LF, а на диске CRLF. Тогда «файл совпадает с
каноном» не опознается никогда, и путь навсегда застрянет в `dirty`.
Поэтому сравнение двойное: сырое и нормализованное. Совпадение по
второму варианту логировать один раз на запуск — это признак, что
репозиторий нормализован, и об этом стоит знать.

**Тесты** (`tests_git_source.py`): временный репозиторий, создаваемый в
тесте; сценарии — добавление, удаление, переименование, кириллица и
пробелы в путях, файл вне `src/`, CRLF/LF, пустой репозиторий, коммит,
которого нет. **Git на машине прогона нужен.** Если его нет, набор
скипается целиком и по правилу `CI-5` помечается `ПУСТО` — это верно:
непроверенный движок не должен выглядеть проверенным.

**Объём:** M.

### `SRC-6` — `:SourceState` в Neo4j и аренда записи

**Что сделать.**
- `source_state.py`: чтение/запись узла из раздела «Целевая схема».
  `dirty` хранится одним JSON-свойством: путей в нём единицы-десятки, а
  читается он целиком.
- Аренда: `MERGE` + условное обновление `lock_until < now()` одним
  запросом; срок по умолчанию 10 минут, продлевается по ходу работы.
  Если аренду не взять — цикл пропускает такт, `metadata_refresh`
  отвечает `busy` с тем, кто держит и до какого времени, `apply_changes`
  ждёт до таймаута и выходит с кодом 2. Полная индексация берёт аренду
  на всё время прогона.
- Миграция: если узла нет, а есть старые куски `fp_owner_*` и
  `:Fingerprint` — состояние создаётся с `needs_reconcile=true`.
  Старые узлы не удаляются до `SRC-15`.

**Почему аренда обязательна.** Писателей становится три (цикл,
`metadata_refresh`, `apply_changes`) плюс индексер. Без неё два
одновременных upsert одного объекта дают ровно тот класс дефектов, что
`FIX-27`: срез снесён одним, привязка кода потеряна другим.

**Объём:** M.

### `SRC-7` — применение изменений: одна функция для всех

Сейчас логика «удаления, потом обновления вместе с зависимыми
единицами» живёт внутри `apply_changes.main()`. Вынести её в
`apply_set(neo, src_root, removed, upserted)`:
- принимает пути, сама переводит их во владельцев (`owner_of`) и
  добавляет зависимые (`dependent_owners`);
- порядок прежний: удаления, затем обновления;
- проверка владения (`FIX-27`) и снимок рёбер (`PERF-12`) — в конце, как
  сейчас;
- возвращает итоги по файлам; при любой ошибке — исключение, и
  вызывающий **не** сдвигает `indexed_sha` и **не** чистит `dirty`.

Ею пользуются цикл, `metadata_refresh`, `apply_changes` и индексер при
старте. Отдельные копии этой логики — источник расхождений, которые
проект уже разбирал не раз.

**Порог.** Если изменений больше `METADATA_MAX_PARTIAL` (300), функция не
работает, а возвращает `needs_full` с причиной. Цикл сам двухчасовую
индексацию не запускает — только ставит флаг (см. `SRC-12`).

**Объём:** M.

## Блок C. Точки входа

### `SRC-8` — MCP-инструмент `metadata_refresh`

```
metadata_refresh(paths: list[str] | None = None) -> JSON
```

- **С путями** — «я поменял эти файлы». Нормализация по `SRC-4`; пути
  вне конфигурации возвращаются со статусом `outside_config`. Файлы
  применяются через `apply_set`, пути попадают в `dirty` с хешем того,
  что проиндексировано.
- **Без путей** — «проверь сейчас»: внеочередной такт цикла. Нужен,
  когда агент только что вернул канон или сделал pull и не хочет ждать
  минуту.
- **Ответ:** по файлам (`reindexed` / `removed` / `outside_config` /
  `error` с причиной) и сводка источника: `head`, `indexed_sha`, размер
  `dirty`, `needs_full`. Агент сразу видит, что граф свежий, или видит,
  почему нет.
- Существующие `metadata_upsert_file` / `metadata_remove_file`
  переделать в тонкие обёртки над той же логикой: сейчас они обновляют
  граф, но не состояние, и это ровно путь к неожиданной полной
  индексации на следующем старте. Старые два остаются под
  `ENABLE_WATCH_TOOLS` для совместимости.
- `mcp_tool_filter.py` работает списками **исключений**, а не набором
  разрешённых: новый инструмент виден агенту без правок фильтра. В
  `WATCH_TOOLS` добавить служебный `metadata_source_tick` (такт цикла,
  его зовёт watcher — см. `SRC-9`); тесты фильтра обновить.

**Мера приёмки.** Агент правит модуль и добавляет новый общий модуль,
вызывает `metadata_refresh` со списком — оба видны в `metadata_search` и
`code_callers` в том же ответе, `dirty` = 2.

**Объём:** M.

### `SRC-9` — `workspace-watcher`: цикл по git вместо опроса файлов

- **Главный выключатель — `WATCHER_ENABLED`, по умолчанию `false`.**
  Включение — осознанное решение пользователя (см. «Режимы работы»).
  Выключенный watcher не мешает ничему: ручной запуск работает так же.
- `SOURCE_POLL_SEC` — интервал такта, по умолчанию 60. Допустимо от 30
  до 3600; значение вне диапазона — ошибка конфигурации при старте, а не
  молчаливая подстановка. Переменная обязана быть в `environment`
  сервиса в `docker-compose.yml` — урок `WATCHER_POLLING_INTERVAL`,
  который из `.env` до контейнера не доходил.
- `WATCHER_MODE` = `git` | `poll`. По умолчанию `git`, если `detect()`
  нашёл репозиторий, иначе `poll` (прежнее поведение для каталогов без
  git, со всей его ценой — в лог об этом одна строка при старте).
- В режиме `git` нет `watchdog` вообще: такт раз в `SOURCE_POLL_SEC`
  вызывает у сервера графа служебный инструмент цикла
  `metadata_source_tick`. Сам цикл живёт в `mcp-metadata-graph`, рядом с
  арендой и `apply_set`; watcher — только будильник. Так логика одна, а
  не две, и ручной запуск (`apply_changes.py`, `metadata_refresh()`)
  выполняет ровно тот же такт.
- Такт, пришедший, пока предыдущий ещё идёт (долгая доиндексация после
  большого pull), не встаёт в очередь, а пропускается: аренда занята,
  в лог одна строка.
- Лог: одна строка на такт, где что-то произошло
  (`HEAD a1b2→c3d4: +3 ~12 -1 за 41 с`), и ничего — где не произошло.
  Раз в час — строка «жив, HEAD такой-то, dirty N».

**Мера приёмки.** Таблица времени: `ubd-git-sync` подтянул часовой
коммит → через сколько секунд изменённый объект виден в
`metadata_search`. Цель — не больше двух минут. Загрузка CPU watcher'а в
простое — в пределах шума (сравнить с замером 12 августа: 6,2 %).

**Объём:** M.

### `SRC-10` — индексер при старте: догнать, а не пересобрать

Сейчас старт индексера = полный обход (3–12 минут) и при расхождении —
полная индексация (1,5–2 часа). В режиме `git`:

| Состояние | Действие |
|---|---|
| `HEAD == indexed_sha`, `config_subdir` тот же, владение в порядке | выход за секунды, без обхода |
| `HEAD` ушёл вперёд, изменений ≤ порога | `apply_set` по `git diff` — те же минуты, что у цикла |
| изменений больше порога, `indexed_sha` пропал, сменился `CONFIG_SUBDIR`, состояния нет, форс | полная индексация, как сейчас |
| владение не в порядке (`FIX-27`) | как сейчас: фаза 2 принудительно |

После полной индексации: `indexed_sha` = `HEAD`, **снятый до начала
прогона** (если `HEAD` сдвинулся за два часа, следующий такт догонит
разницу); `dirty` пуст, `needs_reconcile=true` — граф проиндексировал
диск вместе с возможными незакоммиченными правками, и узнать их можно
только сверкой (`SRC-11`). Это заменяет ручной `what_changed.py --save`,
о котором пришлось писать в README: состояние после полной индексации
пишется само.

Режим `legacy` — без изменений, вплоть до текста логов.

**Мера приёмки.** `docker compose up` на неизменившейся выгрузке:
индексер выходит меньше чем за 30 секунд (сейчас 3–12 минут),
в логе строка с `HEAD` и «граф актуален».

**Объём:** M.

### `SRC-11` — сверка: поймать то, о чём никто не сообщил

Агент может забыть `metadata_refresh`, человек может поправить файл
руками. Сверка — единственное место, где обход выгрузки допустим.

- `git status --porcelain=v1 -z --untracked-files=all -- <subdir>` с
  `GIT_OPTIONAL_LOCKS=0`, `-c core.checkStat=minimal -c
  core.trustctime=false`: индекс писал git на Windows, inode и владельца
  контейнер видит другими, и без этих настроек git перехеширует все
  1,2 ГБ.
- Результат против `dirty`: файл изменён, а в `dirty` его нет или хеш
  другой → `apply_set` и в `dirty`; в `dirty` есть, а `status` его не
  показывает → проверить по шагу 1 цикла.
- Запуск: ночью (`SOURCE_RECONCILE_AT`, по умолчанию `03:00` по
  `TZ` контейнера), при `needs_reconcile`, и вручную —
  `apply_changes.py --reconcile`.
- **Сначала мерить.** Сколько `git status` в контейнере идёт на боевой
  выгрузке — неизвестно. Сравнить с параллельным обходом на потоках
  (`os.stat` отпускает GIL, задержка 5 мс — это ожидание, а не работа).
  Взять быстрый. Если оба дольше 15 минут — сверку оставить только
  ночной и по запросу, при `needs_reconcile` не запускать автоматически.

**Мера приёмки.** Руками поправить модуль, `metadata_refresh` не звать,
`apply_changes.py --reconcile` → модуль обновлён, в `dirty`. В таблицу
`СТАТУС.md` — время сверки на боевой выгрузке.

**Объём:** M.

### `SRC-12` — `apply_changes.py` в режиме git и видимость состояния

- `apply_changes.py` в режиме `git`: по умолчанию делает такт цикла
  немедленно (без ожидания watcher'а), `--reconcile` — сверку,
  `--dry-run` — показывает, что сделал бы, не беря аренду, `--full` —
  полную индексацию с подтверждением. Режим `legacy` — прежний обход.
- Обёртки для ручного запуска одной командой: `scripts/graph-refresh.ps1`
  и цель `graph-refresh` в `Makefile` с теми же ключами. Сторож
  `scripts/tests_commands_cross_platform.py` уже следит, чтобы у каждой
  цели `make` был вариант без `make`, — новую цель добавить и туда.
- `metadata_stats` получает блок `source`: `mode`, `head`,
  `indexed_sha`, отставание в коммитах, размер `dirty` (и первые 20
  путей), `needs_full` с причиной, `needs_reconcile`, время последнего
  такта и последней сверки, `last_error`, долг `stale_after_incremental`.
  Это ответ на вопрос «граф свежий?» без чтения логов — и для человека,
  и для агента.
- `needs_full` при этом не исчезает молча: каждый такт пишет в лог одну
  строку-напоминание, пока флаг стоит.

**Объём:** S.

## Блок D. Плановая полная индексация

### `SRC-13` — долг и расписание

Частичные обновления каждый час быстрее копят долг
`stale_after_incremental`: слой кода собирается глобальным резолвом, и
точечное обновление его не пересчитывает. Порог
`METADATA_STALE_DEBT_LIMIT` и предупреждение уже есть. Добавить:

- `SOURCE_FULL_REINDEX_CRON` — необязательное расписание полной
  индексации (например, суббота 02:00). По умолчанию **выключено**:
  двухчасовой прогон без ведома человека, на машине, которую могут
  выключить, — решение пользователя, а не умолчание.
- Полная индексация, запущенная по расписанию или по `needs_full`,
  держит аренду; цикл в это время пропускает такты и пишет об этом.
- `metadata_stats.source` показывает дату последней полной индексации и
  рекомендацию, если долг выше порога.

### `SRC-14` — правило для агента и скрипт возврата канона

**Правило.** Файл-шаблон `docs/agents/metadata-refresh.md` для
вставки в AGENTS.md / правила / скилл (BMAD, Spec Kit — неважно):

> После любой записи в каталог конфигурации (`src/`) вызови
> `metadata_refresh` со списком изменённых и созданных файлов. После
> возврата канона или обновления выгрузки — `metadata_refresh()` без
> аргументов. Перед ответом, который опирается на граф, проверь
> `metadata_stats` → `source.needs_full`.

Хук Cursor `afterFileEdit` — в том же файле как **необязательное**
ускорение, с пометкой, что облачные агенты хуки не выполняют.

**Скрипт возврата канона** (`scripts/restore-src-canon.ps1`, запускается
на Windows, не в Docker):
1. Показывает изменённые и новые файлы в `src/`.
2. Спрашивает подтверждение: «.cf уже в хранилище?».
3. `git stash push -u -m "<дата> <N файлов>" -- src` — правки не
   стираются, а откладываются; достать — `git stash list` / `pop`.
4. Если найден `ubd-git-sync` (`%LOCALAPPDATA%\CursorUbdGitSync\config.json`)
   — запускает `Update-UbdRepo.ps1 -Source manual`.
5. Печатает напоминание: граф подхватит сам за минуту, или
   `metadata_refresh()` из чата.

Вариант для своей выгрузки — `scripts/dump-and-commit.ps1`:
`DumpConfigToFiles <repo>\src -Format Hierarchical -update`, затем
`git add -A` и `git commit`. Путь к платформе и строку ИБ — параметрами,
пароль не принимать в командной строке.

**Объём:** S.

## Чего не делать

- Не запускать git-команды, которые пишут: `fetch`, `pull`, `add`,
  `commit`, `stash` — это забота хоста и `ubd-git-sync`. Контейнер
  читает.
- Не запускать полную индексацию из цикла автоматически.
- Не включать watcher по умолчанию и не делать опрос файлов режимом по
  умолчанию там, где есть git.
- Не заводить у ручного запуска и у watcher'а разную логику: оба —
  один и тот же такт.
- Не завязывать сигнал агента на хуки Cursor.
- Не удалять режим `legacy` и старые отпечатки, пока режим `git` не
  отработал неделю на стенде.

## Как реализовано (3 ноября 2026)

Код — блоки 0, A–E полностью; блок F не делался. Отступления от плана,
каждое осознанное:

- **Watcher делает такт сам, а не через MCP-инструмент сервера.** План
  предлагал `metadata_source_tick` на сервере и watcher-будильник. Сверка
  и полная индексация идут минуты и часы — это упирается в таймауты
  MCP-вызова и авторизацию. Логика всё равно одна: общий модуль
  `source_sync.py`, его зовут watcher, индексер, `apply_changes.py` и
  `metadata_refresh`; порядок между ними — аренда в Neo4j. Инструмент
  `metadata_source_tick` не понадобился.
- **Плановая полная индексация — `SOURCE_FULL_REINDEX_AT=sat 02:00`**, а
  не cron-строка: формат «день ЧЧ:ММ» читается без справочника.
- **Хеш файла на диске считается в Python** по формуле git, а не
  `git hash-object`: белый список git-подкоманд стал короче на одну.
- **Ручной запуск получил `--full` и `--force-unlock`** — без них
  graph-refresh.ps1 не закрывал бы два сценария стенда (7 и 11).
- **Хук Cursor не делался**: он не может вызвать MCP-инструмент напрямую,
  его не выполняют облачные агенты, и он привязал бы набор к IDE. Почему
  без него не страшно — `docs/agents/metadata-refresh.md`.

Модули: `git_source.py`, `source_state.py`, `source_sync.py`
(в `mcp-metadata-graph-neo4j/`). Тесты: `tests_git_source.py`,
`tests_source_state.py` (Cypher-часть — против живой базы при
`NEO4J_TEST_URL`), `tests_source_sync.py`, `tests_indexer_git.py`,
`tests_apply_changes_git.py`, `tests_refresh_tool.py`,
`tests_workspace_watcher.py`, `scripts/tests_host_ps1.py`.

Что требует стенда — `ОТКРЫТОЕ.md`, строка `SRC`.
