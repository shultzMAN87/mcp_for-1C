Последняя задача `PLAN-5`. В плане она описана четырьмя пунктами: README
про `.hbk` (был сделан раньше), проверка истории git на секреты, лицензия,

## Проверка истории: чисто

Ни секретов, ни ключей, ни проприетарных файлов. 14 коммитов, 341 путь,
572 объекта — из чувствительного в истории только `.env.example`, чем он и
должен быть.

Отдельно проверено, что в историю никогда не попадали `.hbk` (справка
вендора), выгрузка конфигурации и корпус `v8std`.

**Но однократная проверка — это ровно тот жанр, который проект чинит пятый
заход подряд.** История растёт: чистая сегодня, через десять коммитов она
другая, а вывод «проверено» остаётся тем же. Поэтому проверка оформлена
скриптом:

```powershell
python scripts/check_publish.py    # или make check-publish
```

Он смотрит содержимое всех объектов истории, а не только рабочий каталог:
файл, удалённый коммитом, из репозитория никуда не девается и утечёт
вместе с ним.

### Как проверка сама себя высекла

Первая редакция выдала **286 строк FAIL**, из которых 284 были про отчёты
прогонов. Два настоящих пункта — «нет LICENSE» и «нет ARCHITECTURE.md» —
утонули в мусоре.

Дефект не в объёме, а в том, что важность не различалась: утёкший пароль и
лишний `.json` кричали одинаково. На проверку, которая всегда красная,
перестают смотреть — и она перестаёт работать в тот день, когда покраснела
по делу. Ровно `ph-005` и «7/9» из прошлой части, только в другом файле.

Починено двумя правками: важность в третьей колонке правил (`FAIL` —
уедет наружу то, чему там не место; `WARN` — сор в репозитории) и
сворачивание находок в строку «N файлов такого-то вида». Сто сорок три
одинаковых сообщения — это одно сообщение и число.

Стало:

```
  OK    обязательные файлы на месте (5)
  OK    по содержимому истории чисто (572 объектов)
  WARN  под версионным контролем: отчёты прогонов — 142 шт. (…)
  WARN  в ИСТОРИИ: отчёты прогонов — 142 шт. (…)
```

## Находка: отчёты прогонов лежат в гите

`.gitignore` для `evals/reports/` (пункт из итогов части 3, оценка «5
минут») **сам по себе ничего не чинит**: 142 файла уже отслеживаются, а
`.gitignore` действует только на неотслеживаемые.

Нужна вторая команда, и её нет ни в одном плане:

```powershell
git rm -r --cached evals/reports
git commit -m "отчёты прогонов больше не в гите"
```

В истории они останутся навсегда — но это сор, а не утечка, чистить
историю ради них не стоит.

## Находка: мёртвая зависимость с AGPL

`pymupdf` стоял в `requirements-embeddings.txt` со времён, когда справку
разбирали из PDF. После `HBK-1` источник — `.hbk`, и `import fitz` в
проекте не встречается **ни разу**.

Мёртвая зависимость сама по себе не страшна. Но у этой лицензия
**AGPL-3.0** (Artifex, dual license) — единственная копилефт-лицензия во
всём наборе, и требует она немало: распространяете софт с ней, в том числе
как сетевой сервис или в контейнере, — открывайте исходники всего
приложения под AGPL либо покупайте коммерческую лицензию.

Для проекта, который вы собираетесь выложить под MIT, это ненужный
разговор про ничто. Строка убрана из `requirements-embeddings.txt` и из
лок-файла (в локе от неё никто не зависел — ни одного `via pymupdf`).

Заодно образ справки станет чуть легче.

### Рядом лежит та же находка размером в две тысячи раз больше

Чистая пересборка образа справки 17 августа скачала около **2,5 ГБ колёс
`nvidia-*`** (cuBLAS 423 МБ, cuDNN 366 МБ, cuFFT 214 МБ, NCCL 206 МБ,
cuSOLVER 201 МБ и далее по списку) плюс `triton` 198 МБ — их тянет за
собой `torch` в сборке по умолчанию.

На машине без проброшенного GPU всё это не используется никогда, ровно как
`pymupdf`. Разница только в масштабе: одна мёртвая строка стоила лицензии,
другая стоит двух с половиной гигабайтов образа и двадцати минут чистой
сборки.

Лечится указанием CPU-индекса torch при генерации лока:

```
pip-compile --extra-index-url https://download.pytorch.org/whl/cpu ...
```

Не делаю в этом заходе: правка трогает генерацию лок-файлов для образа, а
их только что чинил `LOCK-1`, и мешать эти две вещи в одном изменении не
стоит. Задача записана в итоги части 4.

> Лок правился руками, потому что `pip-compile` требует сети. Когда будет
> удобно — прогоните `make lock`, чтобы файл снова был порождением
> генератора, а не редактирования.

## Лицензия: MIT, и это решение за вами

Положен `LICENSE` с текстом MIT. Три вещи, которые стоит проверить, прежде
чем считать вопрос закрытым:

1. **Строка правообладателя.** Сейчас там `shultzMAN87` — ник из адреса
   репозитория. Если хотите настоящее имя или название компании, замените.
2. **Кому принадлежит код.** Если он писался в рабочее время или на
   оборудовании работодателя, права могут принадлежать не вам. Это стоит
   выяснить до публикации, а не после. Я не юрист и советовать тут не
   берусь.
3. **MIT против Apache-2.0.** MIT короче и привычнее; Apache-2.0
   дополнительно даёт явную патентную лицензию и требует отмечать
   изменения. Для инструмента разработчика обычно берут MIT — но если
   проект может попасть в корпоративный контур, Apache-2.0 иногда
   проходит согласование легче.

Что до чужого: в репозитории **не хранится ни одного чужого бинарника**.
BSL Language Server (LGPL-3.0) скачивается при сборке образа с релизов
`1c-syntax`, корпус v8std (CC0) — скриптом `fetch_v8std.py`, образы Neo4j
(GPL-3.0, отдельный процесс, общение по Bolt) и Qdrant (Apache-2.0) —
официальные. Таблица целиком — в `ARCHITECTURE.md`.

Справка платформы `.hbk` — проприетарные файлы 1С, их в репозитории нет и
быть не может: пользователь берёт их из своей установленной платформы.

Заодно нашлись два абзаца, уехавшие не в тот раздел при прошлых правках:

Первый переехал во вступление к разделу серверов — туда же, где теперь
описаны `answerable` и `degraded`. Второй — в раздел `platform-help`, и
дополнен `PERF-6.1`.

Такие склейки не ловит ни один тест, и это стоит помнить: документация —
единственная часть проекта, где нет проверки на соответствие.

## Что осталось от `DOC-2`

Ничего блокирующего. `make check-publish` даёт код возврата 0 при двух
предупреждениях про отчёты, и оба снимаются одной командой `git rm -r
--cached evals/reports`.

Перед первым выкладыванием стоит пройти глазами один раз:

1. `python scripts/check_publish.py` — должен быть зелёным;
2. строка правообладателя в `LICENSE`;
3. `README.md` — первые два экрана: понятно ли постороннему, что это;
4. `.env` на всякий случай — он в `.gitignore`, но проверить дешевле, чем
   потом чистить историю.
