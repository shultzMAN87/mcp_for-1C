# FIX-20. «OK, 0 тестов» — третье состояние набора

Дата: 16 августа 2026. Найдено вашей приёмкой `B-7`/`B-6`, в плане не было.

## Что было видно в логе

```
  OK   tests.py                        0 тестов    2.1 с
...
OK: проверено 25 наборов из 25, 833 тестов
```

Набор запустился, вернул код 0 и был засчитан пройденным — с нулём тестов.

## Что происходило на самом деле

`evals/runner/tests.py` написан не на unittest: пять функций с `assert` и
печатью прогресса «`[5/5] run_one + report: OK`». Строки «Ran N tests» в его
выводе нет, и регулярное выражение в `run_all_tests.py` честно читало ноль.

То есть пять настоящих проверок отработали, но не попали ни в число 833, ни
в чьё-либо внимание. На моей машине этого не видно вовсе: там нет пакета
`mcp`, набор уходит в «не запускался», и состояние выглядит другим.

Хуже другое. Набор, который сломался бы так, что выходит с кодом 0, ничего
не проверив, выглядел бы **точно так же**. Это ровно тот жанр, ради которого
затевался весь заход: отказ, притворившийся успехом.

`A-5` развёл два состояния — «прошло» и «не запускался». Третье осталось
незамеченным, потому что на моей машине оно не воспроизводится.

## Что сделано

**Счётчик знает второй формат.** Если «Ran N tests» нет, ищутся строки вида
`[3/5] что-то: OK` — берётся знаменатель последней. На реальном выводе
`evals/runner/tests.py` это даёт 5.

**Нераспознанный счётчик назван.** Набор, вернувший ноль при нулевом коде
возврата, попадает в отдельный список и отдельное число итоговой строки —
`БЕЗ СЧЁТЧИКА: N`. В построчном выводе вместо «0 тестов» стоит «? тестов»
и пометка.

**`--strict` считает это провалом.** В CI «прошло» и «ничего не
проверялось» — разные исходы, как и с не запустившимся набором.

**Три состояния закреплены тестами** (`scripts/tests_host_scripts.py`,
класс `TestSuiteCounting`): unittest считается, прогресс-формат считается,
молчаливый успех даёт честный ноль, а не придуманное число.

## Чего сознательно не сделано

`evals/runner/tests.py` не переписан на unittest. Соблазн был: тогда формат
один и парсер не нужен. Но набор уже правился в этом заходе (`FIX-15`),
работает и читается, а переписывание ради единообразия отчёта — это правка
кода ради удобства измерения. Дешевле научить измеритель.

Если браться, то отдельной задачей и с одним аргументом: unittest даёт
номер упавшей проверки, а `assert` в цепочке функций останавливает набор на
первой же.

## Изменённые файлы

| Файл | Что |
|---|---|
| `scripts/run_all_tests.py` | второй формат счётчика, состояние «без счётчика», `--strict` |
| `scripts/tests_host_scripts.py` | класс `TestSuiteCounting`, 3 теста |

## Проверка

```powershell
python scripts/run_all_tests.py
```

На вашей машине (с пакетом `mcp`) ожидается: `tests.py` — **5 тестов**,
итог **841 тест в 25 наборах**, без строки «БЕЗ СЧЁТЧИКА».

Если строка появится — какой-то набор молчит о том, сколько проверок
отработало, и его имя будет названо.
