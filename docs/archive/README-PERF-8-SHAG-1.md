# `PERF-8`, шаг 1 — узнать, что изменилось

Первая половина частичного отпечатка: **определение** изменений. Ничего не
меняет в графе, только читает.

```powershell
docker compose build metadata-indexer mcp-metadata-graph mcp-query-builder workspace-watcher
```

| Файл | Что |
|---|---|
| `…/mcp-metadata-graph-neo4j/partial_fingerprint.py` | новый |
| `…/mcp-metadata-graph-neo4j/what_changed.py` | новый, скрипт |
| `…/mcp-metadata-graph-neo4j/tests_partial_fingerprint.py` | новый, 26 тестов |
| `1c-mcp-suite/Dockerfile.python` | два `COPY` |

## Идея

Сейчас fingerprint — одна сумма на всю выгрузку: изменился байт →
переиндексируется слой целиком. Правка одного модуля стоит столько же,
сколько полная замена конфигурации.

Стало — сумма **на каждый объект метаданных и каждый модуль отдельно**.
Сравнение двух состояний даёт не «изменилось / не изменилось», а список:
что добавлено, изменено, удалено.

Раскладка файлов по владельцам — самое ответственное место, ошибка здесь
означает незамеченную правку. Правила не дублируются: используются те же
`classify_bsl_path` и таблица `KINDS`, что и в самом индексаторе. Своя
копия рано или поздно разошлась бы с настоящей — тот самый класс дефектов,
что Заход 4 ловил пять раз.

Отдельный случай — вложенные XML. `Forms/…/Form.xml` не самостоятельный
объект, но его читает резолвер (реквизиты форм, `FIX-4.1`), поэтому правка
формы перестраивает **родительский объект**. Отдельный ключ здесь означал
бы, что изменение реквизита формы никогда не доедет до графа.

## Чего это не ускоряет

Обход дерева остаётся: чтобы узнать, что изменилось, надо посмотреть на все
файлы. Те же 3–14 минут `stat` на виндовом bind-mount — не лучше и не хуже,
чем сейчас. Экономия начинается **после** обхода.

## Как пользоваться

**Первый раз — записать отпечатки для текущего графа.** Граф у вас собран и
соответствует выгрузке, так что это безопасно:

```powershell
docker compose run --rm --entrypoint python metadata-indexer /app/what_changed.py --save
```

`--save` пишет только свойство `fp` на существующие узлы — ни рёбра, ни
состав графа не трогаются.

**Дальше — в любой момент:**

```powershell
docker compose run --rm --entrypoint python metadata-indexer /app/what_changed.py
```

Ответ выглядит так:

```
ИТОГ: изменений 12: добавлено 1, изменено 10, удалено 1

Добавлено (1):
    Catalog.НовыйСправочник
Изменено (10):
    CommonModule.ЭдоОбщий
    Document.ЭдоЛогистика_ТранспортнаяНакладная
    ...
Удалено (1):
    DataProcessor.СтараяОбработка
```

Это и есть ответ на «мне опять ждать два часа» — числом, до того как
что-либо запускать.

## Что проверить сейчас

1. `--save`, потом сразу обычный запуск — должно сказать «изменений нет».
   Если скажет что-то другое, раскладка нестабильна, и это надо разбирать
   до второго шага.
2. Поправьте один общий модуль и запустите снова — ожидается ровно одна
   изменённая единица.
3. Посмотрите число «единиц» в первой строке: это сколько объектов и
   модулей всего. Ожидается около 24 800 (10 747 объектов + 14 047 модулей).

## Чего в этом шаге нет

**Применения плана.** Скрипт только показывает. Второй шаг — прогонять по
списку точечные обновления из `incremental.py` и обновлять сохранённые
отпечатки.

Второй шаг упирается в честное ограничение, которое стоит проговорить до
того, как я его сделаю. Слой 2 собирается **глобальным** фикс-пойнтом: тип
параметра в модуле A зависит от вызова в модуле B. Точечное обновление
такой сходимости не даёт — вызовы из чужих модулей в обновлённый
помечаются `stale_after_incremental`, и покрытие резолва медленно падает с
каждым частичным прогоном.

Поэтому частичный режим — это «быстро и достаточно хорошо для рабочего
цикла», а не замена полной сборке. Полную придётся прогонять периодически.
В модуль уже заложен счётчик долга (`stale_debt`), чтобы «периодически»
означало число, а не ощущение.
