## Сначала — важное про запуск

**`docker compose restart` не подхватывает новый образ.** Он перезапускает
существующий контейнер с тем, что в нём уже есть. Нужен
`up -d --force-recreate`.

Похоже, именно поэтому в вашей приёмке не сработали `SCALE-1` и `FIX-16`:
образ собран в 09:28, а `mcp-metadata-graph` пересоздавали только для
`metadata-indexer`. Агент не увидел параметра `subsystem` и полез искать по
префиксу имени вручную — то есть работал на коде трёхдневной давности.

## `FIX-17` — свойств `kind` и `full_name` у объектов нет

Ваш вывод:

> Поиск по «заказ» нашёл 196 объектов. Тип в ответе не приходит
> (`kind`/`full_name` = null)

Writer пишет узлам `kind_eng`, `kind_ru`, `full_name_eng`, `full_name_ru`
(см. `write_meta_nodes`). Свойств `kind` и `full_name` у них **нет**: они
принадлежат `:Callable`. А запросы обращались именно к ним — в пятнадцати
местах.

Последствия шире, чем пустые колонки в поиске:

* `metadata_list_kinds` возвращал `kind: null` — то есть был бесполезен;
* фильтр `kind="Справочник"` **не работал никогда**: сравнение шло с null,
  и срабатывала только английская ветка `kind_eng="Catalog"`;
* поиск по полному имени не работал: `toLower(n.full_name) CONTAINS …` тоже
  сравнивался с null, так что искалось только по `name` и `synonym`;
* `metadata_references_*` отдавали `target: null`.

Cypher на несуществующее свойство возвращает **null, а не ошибку** — как и
на несуществующий тип ребра возвращает пустоту. Поэтому дефект прожил
незамеченным.

Заодно `metadata_list_kinds` теперь исключает узлы модулей (`NOT n:Module`) —
иначе в списке видов конфигурации значились бы «ObjectModule» и
«ManagerModule».

## `TEST-1` — контрактный тест

Четыре дефекта за два дня, все одного класса:

| | что было не так | цена |
|---|---|---|
| `PERF-4` | `MATCH` без метки | слой 1 писался 28 минут |
| `FIX-14` | метка `:MetadataObject` там, где `:Form` | молча потеряно 69 % рёбер |
| `FIX-16` | ребро `СОДЕРЖИТ` вместо `CONTAINS` | три инструмента возвращали пустоту |
| `FIX-17` | свойства `kind`, `full_name` | вид и полное имя всегда null |

Общая черта: **Neo4j не считает это ошибкой**. Ни один не проявился
отказом, все четыре нашлись случайно — при ручной сверке счётчиков или в
приёмке.

Обычные тесты такое не ловят: чтобы увидеть разницу, нужна живая база с
боевыми данными. `tests_graph_contract.py` ловит иначе — сверяет **текст
запросов** с тем, что writer объявляет в схеме:

* каждое `n.<свойство>` в запросах существует;
* каждое `-[:РЕБРО]` есть среди тех, что пишет writer;
* ни одного типа ребра кириллицей (рёбра латиницей, метки — и так, и так;
  перепутать легко, и именно это произошло);
* ни одного `MATCH` по `id` без метки.

**Список разрешённых свойств не захардкожен** — он извлекается из
`write_meta_nodes`, а типы рёбер из `EDGE_QUERIES`. Значит, тест не
разойдётся с кодом при следующей правке writer'а: добавите свойство — оно
станет разрешённым само.

Проверил, что тест не декоративный: вернул `FIX-16` и `FIX-17` в код по
очереди — оба поймались.

Комментарии при сканировании пропускаются намеренно. В них цитируются
прежние, неверные запросы — ровно чтобы объяснить, что было не так;
проверять их значило бы запретить документировать исправленные дефекты.
