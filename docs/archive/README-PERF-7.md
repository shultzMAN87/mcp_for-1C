# PERF-7. BSL LS живёт процессом, а не стартует на каждый вызов

Дата: 16 августа 2026. Оценка была — день.

---

## Цена, которую платили

Замер с вашего стенда: медиана `bsl_check_code` — **9,4 с**, максимум 16,6.
При этом `bsl_stats`, который щупает ту же java, отвечает за **100 мс**.
Разница не в анализе, а в старте: каждый вызов поднимал JVM, грузил jar на
43 МБ, инициализировал парсер и после ответа всё это выбрасывал.

Для инструмента, к которому агент идёт после каждой правки, десять секунд —
это не «медленно», это «перестану им пользоваться».

## Что сделано

BSL LS без аргументов работает языковым сервером: живёт процессом, говорит
по LSP через stdin/stdout, диагностики присылает уведомлением
`textDocument/publishDiagnostics`. JVM стартует один раз.

Проверка одного файла и фрагмента идёт этим путём. **Анализ каталога —
нет**, и это граница, а не недоделка: он занимает минуты, старт JVM в нём
теряется, а открывать по LSP сотни файлов — другая задача со своими
рисками.

## Главный вопрос: безсостоятельность

`bsl-checker` был единственным сервером набора, не зависящим ни от чего
внешнего. Долгоживущий процесс это свойство ломает — появляется то, что
может умереть, зависнуть и утечь памятью.

Три вещи делают размен приемлемым.

**Транспорт остаётся stateless.** Между вызовами MCP не сохраняется ничего,
что относится к разговору. Живой процесс — кеш дорогого старта, а не
сессия: любой вызов самодостаточен, результат не зависит от предыдущих.

**Отказ кеша не отказ инструмента.** LSP не поднялся, умер или молчит —
уходим на `--analyze`. Ответ тот же, только медленный. Это единственный
способ ввести долгоживущий процесс, не сделав его новой точкой отказа.

**Состояние названо вслух.** `bsl_stats` показывает секцию `lsp`: жив ли
процесс, сколько запросов обслужил, сколько раз перезапускался, чем
закончилась последняя попытка. И `analysis.by_mode` — сколько вызовов
прошло каким путём. Скрытое состояние делает систему неотлаживаемой.

## Решение, на котором держится вся правка

Быстрый путь отдаёт результат **в точно той же форме**, что json-репортер
`--analyze`. Можно было отдать диагностики как есть и научить три
инструмента разбирать два формата — и получить третий способ прочитать одно
и то же. Вместо этого перевод сделан в одном месте, на границе
(`to_report`), а `bsl_check_code`, `bsl_check_file` и разбор отчёта не
тронуты вовсе.

Побочная выгода важнее косметики: **старые примеры датасета `bsl-001`…
`bsl-003` проверяют новый путь, ничего не зная о нём**. Если LSP отдаст
другие диагностики — они покраснеют.

## Что нашли тесты

**Тест перезапуска отказался проходить, и прав был он.** Пауза после
неудачи задумывалась против одного случая — «LSP вообще не поднимается»
(нет java, битый jar): там повторные попытки добавляют полный таймаут
старта к каждому вызову. Но под неё попало и падение посреди запроса, а это
другое событие: одна смерть долгоживущей java не повод выключать быстрый
путь на минуту для всех последующих проверок.

Разделено: **не поднялся** — виноват сервер, пауза; **умер в работе** —
возможно, виноват конкретный файл, следующий вызов имеет право на новый
процесс. Три падения подряд снова означают сервер — тогда пауза.

**Смерть посреди запроса — отказ, а не частичный ответ.** Я писал тест с
ожиданием «перезапустится и ответит». Реализация не согласилась, и она
права: диагностики могли прийти частично — сервер успел разобрать половину
файла и упал. Отдать пришедшее значило бы сказать «вот все замечания», не
зная этого.

**Плавающий провал набора — и настоящая ошибка за ним.** Собрав архив, я
прогнал тесты из распакованной копии, и первый прогон упал, а второй
прошёл. Плавающий тест хуже отсутствующего, поэтому пришлось искать: падало
примерно раз в десять прогонов, каждый раз в другом тесте, а в изоляции не
падало никогда.

Причина оказалась не в тестах. `stop()` закрывал дескрипторы сразу после
`kill()`, а поток чтения в этот момент сидел в `read()`. Номера
дескрипторов переиспользуются: следующий процесс получает тот же номер, и
зомби-поток вычитывает ЧУЖИЕ сообщения. Снаружи это выглядит как
«диагностики не пришли» — то есть как отказ анализатора.

В тестах это плавающий провал. В работе — редкий, но настоящий: перезапуск
после падения java даёт ровно ту же расстановку. Порядок исправлен
(завершить процесс → дождаться выхода читателя → закрыть дескрипторы), и
закреплён двумя тестами. Двадцать прогонов подряд — чисто.

**`B-6` назвал забытый `COPY` третий раз подряд.** Строку `COPY bsl_lsp.py`
я не вспоминал — её назвал тест доставки, с точным адресом, до сборки.

## Чего я НЕ смог проверить, и как это проверить вам

Протокольная часть покрыта 28 тестами с настоящим обменом по каналам:
поддельный языковой сервер поднимается потоком и говорит теми же рамками
`Content-Length`. Проверены разбор потока, кириллица в длине сообщения
(байты, не символы), корреляция ответов, ожидание диагностик, молчание,
битые рамки, смерть процесса, перезапуск, параллельные вызовы, пауза.

**Чего в песочнице нет — самой BSL LS.** java и jar живут только у вас.
Поэтому утверждение «LSP выдаёт те же диагностики, что `--analyze`» я
проверить не могу — и не буду делать вид, что проверил.

Для этого в модуле есть сверка. Одна команда:

```powershell
docker exec mcp-bsl-checker python3 /app/bsl_lsp.py --compare
```

Она прогоняет один файл обоими путями и печатает:

```
--analyze :   9.81 с, диагностик 3
LSP холодн:  10.42 с, диагностик 3   (включая старт JVM)
LSP тёплый:   0.34 с, диагностик 3

СОВПАДАЕТ: 3 диагностик, оба пути дали одно и то же.
Выигрыш на тёплом вызове: в 29 раз (9.8 с → 0.34 с).
```

При расхождении — печатает, какие диагностики есть только у одного пути.
**Если расходится — не переключайте**, пришлите вывод, разберём.

Аргумент не нужен: без него файл берётся из выгрузки сам — не пустой и не
самый большой, средний по размеру. Это исправление моей же ошибки: в первой
редакции инструкции стояло `/workspace/...`, тогда как в `bsl-checker`
выгрузка смонтирована в `/data/1c-src`, и первая попытка приёмки уткнулась
в «нет файла». Вывод не «впредь быть внимательнее», а «пусть инструмент
найдёт сам»; если путь всё же указан и не существует, сверка печатает,
какие каталоги смонтированы на самом деле.

Конкретный файл, если он нужен:

```powershell
docker exec mcp-bsl-checker python3 /app/bsl_lsp.py --compare /data/1c-src/<путь>.bsl
```

## Откат

```
BSL_LSP_MODE=off
```

Одна переменная в `.env`, перезапуск контейнера — и работает ровно то, что
работало вчера. Быстрый путь при этом даже не пытается стартовать.

## Порядок

```powershell
# 1. Распаковать поверх корня

# 2. Пересобрать bsl-checker
docker compose up -d --build --force-recreate mcp-bsl-checker

python scripts/eval.py --dataset evals/datasets/bsl_checker.jsonl
```

## Чего ждать в датасете

`bsl-001`…`bsl-003` обязаны остаться зелёными — это и есть проверка, что
диагностики не изменились. Их время должно упасть с ~10 с до долей секунды,
кроме первого примера: он платит за старт JVM.

`bsl-010` — новый: hard проверяет, что состояние LSP видно, soft — что
быстрый путь реально работает. **Красный soft здесь означает «выигрыш не
получен», а не «сервер сломан»** — и отличить одно от другого можно только
так.
