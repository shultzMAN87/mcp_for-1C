## 1. Цель и границы

### 1.1 Что решаем

Техническая документация (контракты HTTP-сервисов, алгоритмы процессов, интеграции, замысел по объектам метаданных) ведётся в Confluence вручную, неравномерно, местами отсутствует. Механизма принуждения к обновлению нет. Агенты в Cursor не имеют к ней доступа в пригодном виде.

Нужен контур, в котором документация пишется и обновляется агентом в том же ходе, что и код; устаревание обнаруживается машинно; агент получает документ инструментом с честной пометкой о свежести; Confluence остаётся местом, куда человек ходит читать глазами.

### 1.2 Что НЕ входит

| Не входит | Почему |
|---|---|
| Бизнес-документация аналитиков | Другой жизненный цикл и авторы. Пересечение решается ссылками |
| Генерация описаний всех 231 114 процедур | Отравляет индекс, см. R1 |
| Двусторонняя синхронизация с Confluence | Ломается всегда. Блок H — разовая миграция, не синк |
| Автоматическая документация состава реквизитов | Отдаёт metadata-graph. Дублирование = расхождение |
| Планы выполнения запросов MS SQL | См. 3.6 |

### 1.3 Три уровня хранения

| Уровень | Содержимое | Кто ведёт | Где живёт |
|---|---|---|---|
| Производное | Реквизиты, типы, вызовы, связи, подсистемы | Никто, считается | metadata-graph |
| Замысел, мелкая зернистость | Ограничения, побочные эффекты, подводные камни | Агент + ревизия | `docs/`, отдаётся через MCP |
| Замысел, крупная зернистость | Процессы, интеграции, контракты сервисов | Разработчик + агент | `docs/`, публикуется в Confluence |

Ожидаемый объём в Confluence — десятки, максимум пара сотен страниц. Больше тысячи — значит туда уехало производное, надо останавливаться.

### Р-2. Где живут документы в Confluence

Первая редакция содержала три взаимоисключающих решения. Нужно одно.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Всё в новом `TECHDOC`, legacy мигрирует туда, на старых страницах редирект | Одно место, чистые права, легко откатить эксперимент целиком | Ломает закладки и внешние ссылки, редирект надо ставить руками на каждой странице |
| B. Новые документы в `TECHDOC`, legacy правится по месту в старом пространстве | Ссылки не ломаются, миграция дешевле | Два места жительства навсегда, человеку неочевидно, где искать |
| C. Всё по месту в старом пространстве | Ничего не ломается | Генерируемое смешано с ручным, риск R4 максимален, откатить нельзя |

**Рекомендация: B.** Обоснование: сохранность внешних ссылок важнее эстетики единого места, а «два места» лечится ссылкой из старой страницы на новую, если тема переехала. Вариант A оставить как возможный шаг через год, когда станет ясно, сколько legacy действительно живо.

**Следствия, которые надо зафиксировать:** DOC-36 публикует в `page_id` старого пространства (это и есть B). DOC-28 не «гасит» страницы, а помечает неактуальными и ставит ссылку.

### Р-4. Судьба существующих страниц

### Р-5. Где агент пишет файлы (блокер)

Ключевая развилка. Без неё блок E — декларация: MCP отдаёт текст, но не заменяет репозиторий, а скилл «поправь markdown» работает только с тем, что видно в рабочем пространстве.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. `docs/` в рабочем пространстве Cursor** (подкаталог `30_mcp_cursor` или второй корень) | Скиллы работают штатными средствами. Git уже есть. Дифф в ревизии — обычный git diff. Пишущих MCP-инструментов не появляется | `docs/` мозолит глаза при работе над кодом сервера; нужен запрет агенту трогать `reviewed`-документы вне скилла ревизии |
| B. Отдельный репозиторий без мультикорня | Изолировано | Скиллы мертвы: агент файлов не видит. Отклоняется |
| C. Запись через MCP (`docs_propose` пишет) | Репозиторий где угодно | Появляется пишущий инструмент, чего в наборе сознательно не делали. Два чекаута надо мирить. Скиллы нельзя формулировать как правку файлов |

**Решение: A.** Дополнительно нужен предохранитель, которого не было ни в одном отзыве: раз `docs/` лежит рядом с кодом, агент во время обычной задачи может незаметно поправить `reviewed`-документ. Правило в `.cursor/rules`: вне скилла ревизии агент пишет только в `docs/_proposed/`; изменение файла с `source: reviewed` вне ветки ревизии — ошибка валидатора.

### Р-6. Какие инструменты видит кодер

Заход 9 выиграл на запрете новых инструментов. У агента их порядка 48. Шесть новых — перебор.

| Потребитель | Инструменты |
|---|---|
| Агент-кодер | `docs_get`, `docs_search` — и всё |
| Скилл ревизии | CLI: `python scripts\docs_stale.py`, `python scripts\docs_propose.py` |
| Скилл конца задачи | CLI: `python scripts\docs_gap.py` |

`docs_gap` намеренно не инструмент. Агент выполняет команды, а заявка ставится в конце задачи скиллом, а не спонтанно посреди чтения кода — это же лечит конфликт DOC-23 с R7.

### Р-7. Отпечаток для объектов метаданных

DOC-17 описывал нормализованное тело процедуры. В `targets` лежат ещё справочники, регистры, документы — у них тела нет.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Нормализованный XML объекта | Единый механизм для всех типов | XML шумный: порядок элементов, UUID, служебные атрибуты. Нужна аккуратная нормализация |
| B. Отпечаток по значимому срезу из графа (состав реквизитов, типы, табличные части) | Мало шума, меняется только по делу | Требует доступа к графу при расчёте — но это офлайн-скрипт, не CI |
| C. Не ставить `fp` объектам, ловить устаревание только через `affects` и сверку с `OPERATES_ON` | Ничего не писать | Пропускает изменения, не прошедшие через BMAD |

**Рекомендация: B**, с оговоркой — считать в том же обходе, что и `partial_fingerprint.py`, чтобы не плодить второй проход по 56 410 файлам.

## 3. Формат документа

### 3.1 Фронтматтер

```yaml
---
id: proc-obmen-mp
type: process                        # process | http-service | object
title: Обмен заказами с маркетплейсом
targets:                             # КАНОН — full_name_eng из графа
  - CommonModule.ОбменМП
  - InformationRegister.СостоянияЗаказов
  - Catalog.Контрагенты
subsystem: Продажи
source: reviewed                     # generated | reviewed
specs: [BMAD-142, BMAD-201]
fp:
  CommonModule.ОбменМП: a3f9c1...
  InformationRegister.СостоянияЗаказов: 71bc04...
confluence:
  page_id: "3948112"
  space: PROD
  body_hash: 8e2f...
publish: true
updated: 2026-08-30
reviewed_by: ivanov
---
```

**Имена в `targets` — только `full_name_eng`.** Первая редакция предлагала форму `Справочник.Контрагенты`, которой в графе нет вообще: там `full_name_eng` (`Catalog.Контрагенты`) и `full_name_ru` во множественном числе вида (`Справочники.Контрагенты`, грабли FIX-18). Валидатор отверг бы собственные эталоны.

Человеку писать по-английски неудобно, поэтому у валидатора режим `--fix`: принимает любую из трёх форм на входе, приводит к канону при сохранении, используя нормализатор, который уже написан для FIX-18. Свою нормализацию не изобретать.

`targets` — несущее поле. Пустой `targets` = документ нельзя поставить в очередь = он сгниёт молча. Валидатор считает это ошибкой, а не предупреждением.

### 3.2 Шаблон `process`

```markdown
## Зачем
2–4 строки. Что сломается, если этого не будет.

## Алгоритм
1. Забираем из <источник>: эндпоинт, периодичность, кто инициирует
2. Преобразуем: что во что, где лежит маппинг
3. Пишем в <объект>
4. Поведение при повторном запуске

## Работает с
InformationRegister.НастройкиОбмена, Catalog.Контрагенты,
InformationRegister.СостоянияЗаказов

## Ограничения
Нельзя вызывать внутри транзакции. Не идемпотентно. Только на сервере.

## Когда ломается
Симптом → где смотреть → обычная причина.

## Решения
2026-04-12 (BMAD-142): регистр сведений вместо реквизита — нужна история значений.
```

Секция раньше называлась «Читает / пишет». Переименована в «Работает с» по замечанию отзыва 2: ребро `OPERATES_ON` есть (67 620 после схлопывания MERGE), но направление доступа по нему надёжно не восстанавливается. Сверять множество объектов можно, глагол — нет. Иначе DOC-19 красил бы документы вечно.

**Калибровочный шаг перед DOC-19:** проверить на боевой, различимо ли направление хотя бы для части рёбер. Если да — вернуть разделение чтения и записи, но как необязательное. Если нет — оставить как есть и не пытаться.

Раздел «Когда ломается» на практике читается чаще остальных. Агенту его не выдумывать: заполняется из инцидентов и спек.

### 3.3 Шаблон `http-service`

Метод, путь, авторизация, параметры пути и строки запроса, тело запроса, тело ответа, коды ошибок и что каждый означает, пример вызова, идемпотентность, ограничения по объёму и частоте, версионирование. Тела — примеры JSON, не описание полей прозой.

### 3.4 Шаблон `object`

Короткий: зачем существует, ограничения, неочевидные связи. Состав реквизитов не перечислять никогда. Обычно 10–20 строк, `publish: false` по умолчанию — живёт в MCP, в Confluence не едет.

### 3.5 Правило генерации

Если утверждение выводится из имени объекта или процедуры — не писать. Пустой раздел с честным «замысел неизвестен» лучше пересказа сигнатуры.

### 3.6 Почему в шаблоне нет планов выполнения MS SQL

Предложение из отзыва 1: подтягивать в «Ограничения» метрики и планы выполнения из реальных запросов СУБД. Отклонено, обоснование:

**План выполнения — снимок, а не свойство кода.** Он меняется от объёма данных, статистики, версии сервера, нагрузки за последние сутки — без единой правки кода. Значит документ с вклеенным планом устаревает по причине, которую не ловит ни отпечаток тела процедуры, ни сверка с графом. Получается раздел, который выглядит фактом, не проверяется ничем и врёт тем убедительнее, чем аккуратнее оформлен. Это ровно тот класс ошибки, из-за которого состав реквизитов не кладётся в Confluence.

**Цена тоже немаленькая:** доступ к боевой базе, трассировка, обратное сопоставление сгенерированного платформой SQL с исходным текстом запроса через таблицу соответствия имён, временные таблицы и автопсевдонимы. Отдельный проект, не строка в шаблоне.

**Что взять в узком виде.** В «Ограничениях» ценен вывод, а не план: «выборка по регистру X не использует индекс по периоду, деградирует свыше N строк» живёт годами и переживает обновление статистики. Пишет это человек, который разбирался. Ссылку на замеры приложить можно.

Производительность — это наблюдаемость, а не документация.

## 4. Компоненты

`mcp-docs` — **пятый свой сервер внутри `30_mcp_cursor`**, а не отдельный стек. Первая редакция читала требование независимости слишком буквально: независимость нужна по источнику данных и по возможности подключить сервер к любому агенту, как у platform-help относительно графа. Отдельная кодовая база завела бы второй `refusal`, вторую авторизацию, второй словарь отказа — за месяц они разойдутся.

```
30_mcp_cursor/
  docs/                          ← рабочее пространство Cursor (Р-5 вариант A)
    manifest.json                ← признак «репозиторий прочитан», см. DOC-10
    names.json                   ← словарь имён из графа, для автономного валидатора
    process/*.md
    http-service/*.md
    object/*.md
    _proposed/*.md               ← черновики, единственное место записи агента
    _imported/<page_id>.txt      ← исходники страниц до первой публикации
    _queue/gaps.jsonl            ← заявки
  mcp-docs/
    server.py                    ← docs_get, docs_search
    store.py  search.py  staleness.py
    refusal.py                   ← общий модуль OBS-1, не копия
    tests_*.py
  scripts/
    docs_validate.py   docs_names_dump.py
    docs_fingerprint.py  docs_graph_check.py
    docs_stale.py  docs_propose.py  docs_gap.py
    docs_publish.py  docs_import.py  docs_index.py
  evals/datasets/docs.jsonl
```

Переиспользуется как есть: Qdrant (новая коллекция `docs`), `mcp_auth`, пагинация из B-4, журнал вызовов EVAL-7, `refusal`, схема лок-файлов, `run_all_tests.py`.

### Git-контур

Без него «человек принимает» — лозунг.

```
1. Скилл готовит правку          → ветка docs/rev-<дата>, коммит в docs/_proposed/
2. Человек смотрит дифф          → git diff, рядом дифф кода за период
3. Принял                         → merge в main, source: generated → reviewed
4. Публикация                     → python scripts\docs_publish.py
```

Пункт 4 — вручную или по расписанию, в зависимости от Р-1а ниже.

**Р-1а (уточнение к Р-1): есть ли git-сервер с веб-интерфейсом и раннером.** Отзыв 1 предлагал ревизию через Pull Request с автопубликацией по merge. Идея лучше моей — дифф текста рядом с диффом кода в вебе нагляднее, чем что угодно в IDE. Но она требует корпоративного GitLab/GitHub и раннера с сетевым доступом до Confluence, а стек живёт на Windows-машине за системным прокси. Есть и то и другое — берём PR-вариант. Нет — локальный git и `docs_publish.py` руками, инфраструктуру ради процесса ревизии не строим.

## 6. Миграция существующих статей (блок H)

**Это миграция, а не синхронизация.** Формулировка первой редакции («актуализация») читалась как двусторонний обмен и спорила с R4. Правильно так: страницу читают один раз, переносят в репозиторий, дальше единственный источник правды — git, а Confluence получает публикации в одну сторону. Возврата к чтению из Confluence по этой странице больше нет.

### 6.1 Чем этот сценарий опаснее

При создании нового документа худшее — документа не появилось. При миграции худшее — потеря невосстановимого. В старых статьях лежит замысел, которого нет ни в коде, ни в графе. Агент не сможет его подтвердить и, если дать волю, вычистит как неподтверждённое.

**Правило блока: агент не удаляет ничего.** Может переместить, понизить в статусе, пометить «требует проверки». Удаляет только человек.

### 6.2 Конвейер

```
1. Инвентаризация   список страниц + метаданные, без содержимого
2. Приоритизация    что разбирать первым
3. Импорт           storage format → текст + структура, через AST
4. Привязка         извлечь targets по словарю имён
5. Разбор           статья → список утверждений
6. Проверка         каждое против графа и кода
7. Карточка         отчёт для человека
8. Черновик         обновлённая статья, ничего не удалено
9. Ревизия          человек по git diff
10. Публикация      в тот же page_id
```

Шаги 1–8 не пишут в Confluence. Первый прогон по пространству — чистое чтение.

### 6.3 Классификация утверждений

| Категория | Признак | Что делать |
|---|---|---|
| Подтверждено | Объект есть, связь есть, сигнатура совпадает | Оставить |
| Противоречит | Объект есть, но связь другая; тип не тот; имя иное | В «Требует проверки» с указанием расхождения |
| Не существует | Объекта или процедуры нет в графе | В «Требует проверки», «не найдено в конфигурации» |
| Не проверяемо | Замысел, бизнес-правило, история | **Сохранить дословно.** Самое ценное |

Если непроверяемых утверждений в статье нет вообще — статья состоит из производного. Её не мигрируют, а помечают неактуальной со ссылкой на инструмент графа.

### 6.4 Противоречия не правятся автоматически

Расхождение имеет три возможные причины: статья устарела; статья описывает целевое состояние; в коде дефект. Агент их не различает, и «приведение в соответствие с кодом» в третьем случае документирует баг как норму. Противоречия идут в карточку нейтральной формулировкой: «в статье А, в конфигурации Б», без вывода о том, кто прав.

Побочный эффект: первые прогоны выдадут десятки расхождений по коду. Кто-то должен их разбирать — заложить это организационно.

### 6.5 Карточка страницы

```
Страница: Обмен с маркетплейсом (page_id 3948112)
Обновлена: 2024-11-03, автор petrov
targets: CommonModule.ОбменМП, InformationRegister.СостоянияЗаказов
не найдено в графе: InformationRegister.ОчередьОбмена

Утверждений: 23   подтверждено 11 / противоречит 4 / нет объекта 2 / не проверяемо 6

Противоречия:
  - «пишем в РегистрСведений.ОчередьОбмена» — объекта нет в конфигурации
  - «вызывается из регламентного задания» — в графе нет вызывающих

Неподдерживаемые конструкции: draw.io (1), макрос jira (3)
Вердикт: отложить до ручного переноса схемы
```

Вердикты: **мигрировать**, **пометить неактуальной**, **разделить** (одна страница = несколько документов), **отложить** (конструкции, которые конвертер не берёт).

### 6.6 Приоритизация

1. Страницы, чьи `targets` часто трогают.
2. Страницы, к которым обращаются (просмотры, если Р-1 показал их доступность).
3. Страницы по заявкам из `docs_gap`.
4. Остальное — по остаточному принципу или никогда.

Страница, которую никто не открывал за год и чьи объекты не менялись, ревизии не стоит. Честнее пометить «не проверялась с такой-то даты».

## 7. Риски

### R1. Отравление индекса сгенерированной документацией

**Суть.** Агент генерирует правдоподобные тексты, они попадают в Qdrant, агент цитирует их как факты, пишет по ним код, по коду генерирует следующую порцию. Петля замыкается незаметно: всё читается складно.

**Вероятность** высокая, **ущерб** тяжёлый — обнаруживается поздно, лечится выбрасыванием корпуса.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Не генерировать, только человек | Нет риска | Не масштабируется |
| B. Генерировать всё, помечать `source` | Быстрое покрытие | Метку игнорируют, если её не видно |
| C. Генерировать по приоритету, `generated` вне основного поиска | Индекс чист по построению | Медленнее, нужен работающий контур ревизии |

**Решение: C** плюс матрица раздела 9, которая закрывает дыру, найденную отзывом 2: про `docs_search` было сказано, что он отдаёт только `reviewed`, а про `docs_get` — ничего. Если бы `docs_get` молча отдавал `generated`, вся защита обходилась бы одним вызовом.

### R2. Шум в отпечатках → всё вечно stale

**Суть.** Отпечаток файла модуля меняется от любой правки, включая пробел. При 14 042 модулях после каждого коммита в очереди сотни документов, метку перестают читать за две недели.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Отпечаток файла | `partial_fingerprint.py` уже есть | Шум убивает механизм |
| B. Нормализованное тело процедуры | Срабатывает только на смысловых правках | Нужен разбор BSL — он есть в `bsl_parser` |
| C. Проверка моделью | Точнее всего | Дорого, недетерминировано |

**Решение: B** для процедур, Р-7 для объектов. Нормализация: убрать комментарии, схлопнуть пробелы, привести регистр (BSL регистронезависим — FIX-4.1).

**Контроль:** после DOC-17 замерить долю корпуса, помечаемую stale за неделю обычной работы. Больше 15% — нормализация недостаточна.

### R3. Публикация плодит версии и уведомления

**Суть.** Прогон без изменений создаёт новую версию каждой страницы, Confluence рассылает уведомления. При ежедневном прогоне — сотни писем в неделю.

**Решение.** `body_hash` — хэш готового тела **после конвертации**, не от markdown: иначе правка конвертера вызовет массовую перепубликацию корпуса. Публикация только при расхождении. Сообщение версии с номером задачи.

### R4. Люди правят опубликованные страницы

**Суть.** Кто-то видит опечатку, правит в вебе, следующая публикация затирает. Человек делает вывод, что система враждебна.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Затирать молча | Просто | Люди уходят |
| B. Запретить редактирование правами | Однозначно | Ощущается как запрет, нужно администрирование |
| C. Детект по `body_hash`, при расхождении не публиковать и поднять флаг | Правки не теряются | Нужна разборка конфликта |

**Решение: C.** Отзыв 2 верно указал, что в первой редакции конфликт зависал без хозяина. Поэтому: конфликты складываются в `docs/_queue/conflicts.jsonl`, разбираются в том же еженедельном окне ревизии, срок — две недели, после чего либо принимаются, либо публикуются поверх с уведомлением автора правки. Зависших конфликтов без срока быть не должно.

### R5. Спеки расходятся с реализацией

Спека — источник вопросов, не фактов. В DOC-22 обязательный шаг: сравнить спеку с диффом, выписать расхождения в «Решения». Накопленный список расхождений — фактическая история проекта, которой нет ни в спеках, ни в коде.

### R6. Поле `affects` не заполняется

Заполняет агент по диффу, человек проверяет. Валидатор сверяет со словарём. В Definition of Done — не «обновить документацию» (не проверить), а «заполнить `affects` и выписать расхождения» (проверяется машинно).

### R7. Очередь ревизии растёт быстрее, чем разгребается

**Суть.** 10 747 объектов. Даже 5% изменений в неделю превысят человеческую пропускную способность.

**Решение.** Корпус ограничен спросом: документируется то, что попало в `docs_gap` или менялось за квартал. 200–300 документов на ДНС — реалистично, 10 000 — нет. Плюс сужение DOC-23: заявка только когда агент упёрся, иначе на первой неделе очередь взрывается.

**Индикатор провала:** очередь растёт четыре недели подряд → сокращать корпус, а не наращивать ревизию.

### R8. Ревизия вырождается в проставление галочек

**Суть.** Человек, принимающий 20 документов в неделю, через месяц жмёт «принять» не читая. `source: reviewed` при фактическом `generated` — хуже честного `generated`.

**Решение:**
- очередь ограничена жёстко, остальное ждёт;
- агент показывает **что изменилось и почему** — дифф текста рядом с диффом кода, а не готовый текст;
- раз в месяц 3 случайных `reviewed` сверяются с кодом всерьёз. Нашлись ошибки — ревизия не работает, и это надо признать.

Раздел 11 добавлен именно из-за этого риска: в режиме кампании 40 минут в неделю — фикция, и R8 срабатывает гарантированно.

### R9. Кодировки

Уже наступали: битая кириллица в `docker logs` и аргументах `cypher-shell`, BOM ломает stdin, `cp1251` у дочернего процесса роняет вызов (FAIL-2). Здесь плюс HTTP с кириллическими телами.

**Решение.** `PYTHONIOENCODING=utf-8:replace`, UTF-8 без BOM, явный `charset` в заголовках, тест публикации страницы с кириллицей в заголовке и теле — в обязательный набор.

### R10. Уникальность заголовков

Заголовки страниц уникальны в пределах пространства. Валидатор проверяет уникальность `title` среди `publish: true` — ошибка на валидации, а не на публикации.

### R11. Смешение с бизнес-документацией

Не сливать. Ссылки в обе стороны, разные пространства. Граница: «что должно происходить» — аналитики, «как сделано» — разработчики. Пограничные случаи разбирать по факту.

### R12. Legacy без спек

Контур закрывает то, что пойдёт после внедрения. Для накопленного — только `docs_gap` и комментарии к версиям хранилища. Ожидание: три четверти конфигурации останется без документации, и это нормально, потому что три четверти никто не трогает.

### R13. Зависимость от доступности графа

`docs_get` и `docs_search` работают без графа полностью (читают репозиторий и Qdrant), недоступны только сверки. Отвечать `degraded: true`, не падать, и быстро — грабли FAIL-1 (7916 → 102 мс) не повторять, таймаут ставить сразу.

Валидатор от графа отвязан отдельно (DOC-38): он ходит в `names.json`, а не в Neo4j. Иначе тесты падали бы при остановленной базе.

### R14. Токены и права

Отдельная техучётка с правами только на целевые пространства. Токен в `.env`, ротация, в логах заголовки не печатать.

### R15. Агент вычищает непроверяемое

**Центральный риск блока H.** Агент оставляет подтверждённое и убирает неподтверждённое — то есть ровно то, ради чего документация существует. Статья становится аккуратнее и беднее. Заметить почти невозможно.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Инструкция в промпте | Дёшево | Не работает: «ценное» не тот критерий, который модель применяет надёжно |
| B. Агент только помечает, правит человек | Безопасно | Не хватит людей |
| C. Машинная проверка: все фрагменты «не проверяемо» присутствуют дословно, иначе черновик отклонён | Не зависит от послушности модели | Требует разбора на утверждения (DOC-33) |

**Решение: C.** Плюс исходный текст сохраняется в `docs/_imported/<page_id>.txt` до первой публикации.

### R16. Потери при обратной конвертации

**Суть.** Storage format богаче markdown: макросы, слияние ячеек, вложения, draw.io. Наивный конвертер выбросит молча.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Поддержать всё | Ничего не теряется | Конца работе нет |
| B. Терять молча | Быстро | Недопустимо |
| C. Отказ: страница «требует ручного переноса», не трогается | Ничего не ломается | Часть страниц вне контура |
| D. Переносить неподдерживаемое вставками storage format внутрь markdown | Сохраняет содержимое | Файлы-гибриды, конвертер туда-обратно усложняется |

**Решение: C** в первой версии, **D** по мере необходимости. Отчёт DOC-31 обязан перечислять встреченные конструкции и число отложенных страниц.

Обе стороны конвертации — только AST. Регулярки по storage format запрещены: это XML, который к тому же не всегда берётся строгим парсером из-за HTML-сущностей — нужен снисходительный.

### R17. Противоречие истолковано неверно

См. 6.4. Автоматическое приведение к коду документирует дефект как норму.

### R18. Массовый прогон затирает пространство

Четыре независимых предохранителя: `--dry-run` по умолчанию; лимит 20 страниц на запуск; белый список `page_id` из фронтматтера; сохранённые исходники. Первый боевой прогон — одна страница, вручную выбранная, результат смотреть глазами.

### R19. Rate limiting при чтении

**Суть.** Найдено отзывом 1. `--dry-run` защищает от записи, но инвентаризация обходит всё пространство, и быстрый сбор даже метаданных может заблокировать сервисную учётку.

**Решение (DOC-39).** Сначала уважать `Retry-After`, если приходит; при его отсутствии — экспоненциальная задержка с потолком. Лимит параллельности. Плюс главное: читать пакетными запросами со списком страниц, а не постранично — это на порядок меньше вызовов и снимает половину проблемы. Заголовки лимитов из ответов логировать с первого прогона, чтобы знать реальные пороги.

## 9. Матрица сигналов

Раздел добавлен по замечанию отзыва 2. Идёт в `mcp-tools.mdc` сразу (DOC-24), а не «потом».

| Ситуация | `answerable` | `degraded` | Поля | Как трактует агент |
|---|---|---|---|---|
| Документ найден, `reviewed`, свежий | true | false | `source: reviewed`, `stale: false` | Факт. Можно опираться |
| Документ найден, `reviewed`, `stale` | true | true | `stale: true`, `stale_reason` | Опираться с оглядкой, проверить расхождение по коду |
| Документ найден, `generated` | true | true | `source: generated` | **Гипотеза, не факт.** Проверить по коду перед использованием |
| Документа по `target` нет | true | false | `found: false` | Документации нет. Это ответ. Ставить заявку, если упёрся |
| `docs_search` без флага | — | — | Только `reviewed` | — |
| `docs_search` с флагом `include_generated` | true | true | Смешанная выдача с пометками | Каждый результат проверять по `source` |
| Репозиторий не читается | false | — | `meaning`: это НЕ значит, что документа нет | Не делать вывода об отсутствии |
| Граф недоступен | true | true | Документ отдаётся, сверки не выполнены | Свежесть неизвестна |

Ключевое: `docs_get` отдаёт `generated` — иначе агент не увидит черновик, который сам же положил, — но всегда с `degraded: true` и явным `source`. Обход R1 закрывается пометкой, а не сокрытием.

## 10. Метрики

Процент покрытия не мерить: накручивается заглушками за вечер.

| Метрика | Как считается | Целевое поведение |
|---|---|---|
| Размер очереди stale | `docs_stale.py` | Не растёт четыре недели подряд |
| Доля заявок от обращений | Журнал вызовов EVAL-7 | Падает 2–3 месяца, потом плато |
| Документов с расхождением по графу | `docs_graph_check.py` | Меньше 5% корпуса |
| Датасет `docs.jsonl` | `scripts\eval.py` | 100% hard |
| Сценарий «позовёт ли Cursor `docs_get`» | Ручной чек-лист EVAL-4 | Зачтён на ≥4 из 5 сценариев |
| Зависших конфликтов R4 | `conflicts.jsonl` | Ноль старше двух недель |
| Выборочная проверка `reviewed` | Раз в месяц, 3 документа вручную | 0 ошибок, иначе R8 сработал |

Две последние — единственные, которые нельзя автоматизировать, и без них остальные будут зелёными при неработающей системе.

## 11. Режимы работы и ёмкость людей

Первая редакция закладывала один режим и 30–40 минут в неделю. Отзыв 2 верно указал, что режимов три и смешивать их нельзя: на кампании 40 минут — фикция, а фикция запускает R8.

| Режим | Когда | Содержание | Ёмкость | Кто |
|---|---|---|---|---|
| **Пилот** | Первые 3–4 недели | 5 эталонов, первые публикации, проверка карточек на 20 страницах | 2–3 часа в неделю | Тот, кто ведёт заход |
| **Кампания по legacy** | Разово, 4–8 недель | Разбор карточек, конфликты, ручной перенос отложенных страниц | 3–5 часов в неделю, конечна по времени | Отдельно назначенный, можно не тот же человек |
| **Крейсерский** | Постоянно, после кампании | Очередь stale ≤20, конфликты R4, раз в месяц выборочная проверка | 30–40 минут в неделю + час в месяц | Владелец документации |

Если человек для режима кампании не находится — блок H не запускать вообще. Начатая и брошенная миграция оставляет пространство в худшем состоянии, чем нетронутое: часть страниц переписана, часть нет, и непонятно, каким верить.

## 12. Что считать успехом

Через три месяца:

- 30–50 документов `process` и `http-service` опубликованы и актуальны;
- очередь ревизии не растёт;
- агент при работе с задокументированным куском отвечает по документации, а не выдумывает, и это подтверждено ручным сценарием, а не только датасетом;
- разработчики не пишут документацию руками — принимают подготовленное;
- выборочная проверка не находит ошибок в `reviewed`;
- зависших конфликтов нет.

**Успехом не считается:** количество страниц, процент покрытия объектов, факт запуска контура.
