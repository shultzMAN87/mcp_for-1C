## Диагноз

В плане предполагалось, что у части файлов другой формат контейнера:
«начать с сигнатуры файла: вытащить сырые байты и сравнить с рабочим
`shquery_ru.hbk`». Сравнил. Формат у всех 39 файлов **один и тот же**, а
дефекта — два, и оба из класса «отказ выглядит как успех».

### Дефект 1: контейнер не разбирался вообще

Прежний `hbk_reader` исходил из того, что `.hbk` — это «префикс
V8-контейнера (~1700 байт), а дальше поток ZIP Local File Header'ов».
Отсюда способ чтения: найти первый `PK\x03\x04` и идти по LFH подряд.

На деле `.hbk` — полноценный V8-контейнер, а ZIP лежит **внутри** него,
как содержимое одного элемента:

```
шапка 16 байт
таблица элементов  → Book, FileStorage, IndexMainData,
                      IndexPackBlock, MainData, PackBlock, PackLookup
FileStorage        → обычный ZIP с центральным каталогом — здесь страницы
```

Контейнер хранит данные блоками, и перед каждым блоком стоит 31-байтовый
ASCII-заголовок:

```
\r\n0000abcd 00000200 00001234 \r\n
    ^ размер     ^ размер   ^ адрес следующего блока
      документа    блока      (7fffffff = последний)
```

То есть байты ZIP-потока в файле **не непрерывны**. Последовательный проход
упирался в первую врезку и молча останавливался — `return` без строки в лог.
Видно прямо в байтах `ecsui_ru.hbk` на смещении 3233: хвост PNG, потом `PK`,
потом заголовок блока, потом `\x03\x04` — граница блока разрезала сигнатуру
записи пополам.

Сколько на этом терялось:

| файл | LFH в файле | читалось |
|---|---|---|
| `ecsui_ru.hbk` | 70 | 3 |
| `mngbase_ru.hbk` | 186 | 57 |
| `config_ru.hbk` | 39 | 24 |
| `shlang_ru.hbk` | 74 | 49 |

### Дефект 2: HTML отбирался по расширению имени

`iter_html_from_hbk` пропускала запись, если имя не кончается на `.html` или
`.htm`. Внутри `.hbk` расширения нет почти ни у кого: страницы называются
`LEFTJOIN`, `ENDOFPERIOD`, `form_AllSubsystemsDlg`, часть носит своё —
`dcsparameters.lf`.

Из 1410 реальных страниц по расширению проходили 47. Остальные 1363
отбрасывались **уже после успешного чтения** — то есть даже там, где первый
дефект не мешал (`shquery_ru.hbk`: прочитано 118 записей, в индекс ушло 25).

Проверка сигнатуры, с которой план предлагал начать, ничего бы не дала:
`shquery_ru.hbk` и `shlang_ru.hbk` устроены одинаково, разница была только
в том, где именно граница блока попадала в поток.

## Что изменено

### `1c-mcp-suite/mcp-platform-help-embeddings/hbk_reader.py` — переписан

Читает контейнер как контейнер:

1. Проверяет, что по смещению 16 стоит заголовок блока. Это надёжнее
   сигнатуры: первое поле шапки — адрес свободной страницы, и `0x7FFFFFFF`
   там лежит не всегда (в 25 файлах из 39 — другое значение; проверка по
   сигнатуре отбраковала бы две трети справки).
2. Читает документ по смещению 16 — таблицу элементов (тройки uint32).
3. Из заголовка элемента берёт имя (UTF-16LE с 20-го байта), из данных —
   содержимое; нужен `FileStorage`.
4. Внутри `FileStorage` — обычный ZIP с центральным каталогом, отдаётся
   штатному `zipfile`.

Ручной разбор LFH никуда не делся — он стал **запасным путём**: для файлов,
которые контейнером не оказались, и для потоков без центрального каталога.
Поэтому ни на одном файле не станет хуже, чем было. Но и тихо не станет:
причина отката пишется в stderr.

Новое в API:

* `looks_like_html(content)` — определение HTML по содержимому. Список
  начал намеренно короткий (`<html`, `<!doctype html`, `<head`, `<body`) —
  всё, что не подошло, видно в инвентаризации как «прочее», а не пропадает.
* `hbk_inventory(path)` — что внутри одного файла: записи, страницы,
  разбивка отброшенного, список элементов, ошибка.
* CLI: `python3 hbk_reader.py <файл.hbk | каталог>`.

Ещё поправлено попутно: имена записей ZIP декодируются utf-8 → cp437, как
раньше (штатный `zipfile` без флага UTF-8 сделал бы из русских имён кашу).

### `hbk_indexer.py`

* **`PIPELINE_VERSION = 2` входит в fingerprint.** Дыра, которую вскрыл сам
  HBK-1: fingerprint считался только по файлам справки. Чинишь читатель,
  выкатываешь образ — файлы те же, fingerprint тот же, `if_files_changed`
  отвечает «данные не менялись» и оставляет индекс, собранный сломанным
  кодом. Отказ выглядит как успех уже на уровне доставки исправления.
  Меняете чтение или чанкинг — увеличивайте число.
* **`skip_if_nonempty` больше не молчит.** Пропуск законен, но пропуск
  устаревшего индекса стоит сказать вслух: сравнивается сохранённый
  fingerprint с текущим, и при расхождении в лог идёт «поиск отвечает по
  устаревшим данным».
* **«0 страниц» стало предупреждением.** Раньше строка `HTML: 0, чанков: 0`
  выглядела одинаково и для контейнера с картинками, и для непрочитанного.
  Теперь — `⚠ ни одной страницы` с подсказкой, чем посмотреть внутрь, и
  сводка в конце: «Без единой страницы: N из M».

### `hbk_parser.py`

Одна строка: `utf-8-sig` вместо `utf-8`. Страницы `.hbk` почти все с BOM, и
он уезжал в текст — `'\ufeff Функция КОНЕЦПЕРИОДА...'` попадало в заголовок
чанка и в то, что эмбеддится.

### `tests_hbk_reader.py` — новый набор, 30 тестов

Подхватывается `scripts/run_all_tests.py` сам, по маске.

Главный — `TestBlockBoundaries`: контейнер собирается синтетически, с
заведомо мелким блоком (64–128 байт), чтобы граница гарантированно попадала
внутрь ZIP. На «как получится» этот дефект не воспроизводится.

Отдельно `test_old_style_sequential_scan_would_lose_pages` — страховка от
возврата старого способа: если кто-то снова начнёт искать `PK\x03\x04` по
всему файлу, тест покажет, что записей находится меньше, чем есть.

Плюс приёмочная часть `TestRealContainers` на живых файлах: каждый
контейнер обязан отдать хотя бы одну страницу. Она сама пропускается, если
`platform-help-data/` пуст (файлы 1С в git не лежат), и сама включается,
когда файлы на месте.

## Приёмка

Порядок важен: сначала посмотреть, что получится, и только потом
переиндексировать.

### 1. Инвентаризация на боевом каталоге

```powershell
docker compose build help-indexer
docker compose run --rm --no-deps help-indexer python /app/hbk_reader.py /data/1c-platform
```

Смотреть на две вещи:

* строку `Итого` — сколько страниц теперь всего;
* строку `⚠ Без единой страницы` — её быть не должно.

Отдельно на `shcntx_ru.hbk`: в текущем индексе 25 556 страниц, все они
пришли оттуда. Прироста может почти не быть (у его страниц расширения на
месте) — это нормально. А вот **убыли быть не должно**. Если число меньше
25 556 — не переиндексируйте, покажите вывод, разберёмся.

Прирост по остальным файлам примерно +1350 страниц (это ~2900 чанков, +7% к
41 062) — на время индексации влияет слабо.

### 2. Переиндексация

```powershell
$env:HELP_REINDEX_MODE = "force"
docker compose up -d --force-recreate help-indexer
docker logs -f help-indexer
```

`restart` не годится — не подхватит новый образ (грабли из Захода 4).

В логе теперь по каждому файлу видно число страниц и предупреждение, если
их ноль. Ожидаемое время — как раньше, плюс ~7%.

### 3. Проверка результата

```powershell
python scripts/eval.py --dataset evals/datasets/platform_help.jsonl
```

Было 10/10 hard, 7/8 soft, MRR 0,875. Числа не должны просесть: индекс
только пополнился. Если MRR упал — значит, новые страницы шумят, и это
повод отфильтровать разделы, а не откатывать чтение.

Ручная проверка в Cursor — вопрос по языку запросов, который раньше не
находился, например про `КОНЕЦПЕРИОДА` или `ЛЕВОЕ СОЕДИНЕНИЕ`: эти
страницы лежат в `shquery_ru.hbk` без расширения и до сих пор в индекс не
попадали ни разу.

## Что осталось в блоке B

* `LOCK-1` — `make lock` для `requirements-v8std.lock.txt`. Нужна машина с
  сетью и docker, отсюда не сделать.
* `ITS-1` — применить `optional-ubrat-its/`. Правки готовы и лежат в
  проекте; сверил их с текущими файлами — расхождений нет, применяются
  копированием поверх плюс одна строка из `docker-compose.yml`
  (`ITS_COLLECTION=its_articles`). Отдельное решение: это единственная
  необратимая правка в наборе.

## Что это говорит про план

Блок A (`AUDIT-1`) стоит начинать с той же проверки, которая нашла оба
дефекта здесь: не «читает ли код правильно», а **сходятся ли числа на
входе и на выходе**. Ни один из двух дефектов не был виден в коде — оба
нашлись сравнением «сколько записей в файле» с «сколько записей прочитано».
В `AUDIT-1` уже есть пункт «возвращается ли пустой список там, где
произошла ошибка»; к нему просится второй — «есть ли у шага счётчик входа и
выхода, и сверяются ли они».

# Продолжение: что вскрылось при приёмке

## Приёмка прошла, цифры сошлись

Боевая инвентаризация: 40 файлов, 53 720 записей, **26 903 страницы**.
`shcntx_ru.hbk` отдал 25 509 — ровно столько же, сколько отдавал старому
читателю (все три способа подсчёта записей на нём сходятся: 52 060).
Прежний итог 25 556 = 25 509 + 47, где 47 — то, что старый отбор по
расширению набирал с остальных 39 файлов. Убыли нет, прирост +1347 страниц.

Индексация: **43 896 чанков из 26 892 страниц, parse_errors=0**, 1 ч 48 мин.

## Регресс в eval и чем он оказался

`ph-002` («длина строки») перестал находить `СтрДлина` в топ-5:
13/13 → 12/13 hard, MRR 0.900 → 0.833.

Разбор показал: данные ни при чём. `СтрДлина` в индексе (lookup находит),
она на **6-м месте**. Выше встали три новые страницы, и все три по делу —
`Функция Строка` и `Функция ДлинаСтроки` из `shquery_ru.hbk` (аналоги для
языка запросов, которых в индексе не было никогда) и статья `Работа со
строками`. Плюс два места из пяти занимал один объект:
`КвалификаторыСтроки.Длина` и `КвалификаторыСтроки.По умолчанию`. До HBK-1
он же занимал позиции 1 и 3, но тогда конкурентов не было и это не мешало.

То есть новые страницы не создали дефект — они сделали дефицитным топ-5 и
проявили давнюю проблему: выдача не следит за разнообразием.

### Правка: `mcp-platform-help/help_ranking.py` (новый модуль)

1. **Один чанк на страницу.** У страницы бывает `card`, `description`,
   `syntax`; два чанка одной страницы в выдаче — это один ответ дважды.
2. **Чередование по объектам.** Сначала лучший результат каждого объекта,
   потом вторые, потом третьи. Ничего не выбрасывается, меняется только
   порядок.

Соблазн был сделать проще — «не более одного результата на объект». Это
чинит `ph-002` одной строкой, но `parent` у всех глобальных функций —
«Глобальный контекст», и такое правило схлопнуло бы `СтрДлина`,
`СтрЗаменить`, `СтрНайти` в один результат на любом запросе про строки.

`_help_search` теперь берёт из Qdrant втрое больше кандидатов, чем просят,
иначе после прореживания выдача была бы короче запрошенной.

Переиндексация **не нужна** — правка только на стороне сервера.

## Ещё одна находка, важнее первой

Во время разбора коллекция оказалась пустой (`points_count: 0`) при том,
что индексация завершилась успешно. Причина: в сессии PowerShell остался
`$env:HELP_REINDEX_MODE = "force"`, а `mcp-platform-help` был объявлен
зависимым от `help-indexer` (`condition: service_started`). Поэтому **каждый
запуск `scripts/eval.py` поднимал индексатор, тот видел `force`, удалял
коллекцию и начинал сборку заново** — на 1 ч 48 мин.

Измерение уничтожало измеряемое, и снаружи это выглядело как «поиск
сломался»: точные имена отвечал встроенный фолбэк (`mode=builtin_fallback`),
`lookup` молчал. На этой ложной картине я успел построить и отбросить три
неверные гипотезы.

Зависимость убрана из `docker-compose.yml`. Серверу поиска индексатор не
нужен — ему нужен Qdrant.

**Правило на будущее:** `force` — это команда на удаление данных, ей не
место в переменных оболочки. Запускать разово:

```powershell
docker compose run --rm -e REINDEX_MODE=force help-indexer
```

```powershell
docker compose build mcp-platform-help
docker compose up -d --force-recreate mcp-platform-help
python scripts\eval.py --dataset evals/datasets/platform_help.jsonl
```

Ожидается 13/13 hard и MRR не ниже 0.900. **Мерить по всем 13 примерам, а
не по `ph-002`:** правка, после которой проходит ровно тот тест, что падал,

откатить (удалить `help_ranking.py`, вернуть `_help_search` к прежнему виду)

справки в индексе не было.

Тесты модуля: `1c-mcp-suite/mcp-platform-help/tests_help_ranking.py`,

отчёта. Полный набор проекта: 17 наборов, 691 тест, 0 провалов.

## Про MRR: почему 0.845 — это не регресс

Ранги просели ровно у двух примеров из тринадцати, и в обоих ожидаемый
ответ остался в топ-5.

`ph-002` («длина строки»), было 2 -> стало 5. Выше встали `Функция Строка` и
`Функция ДлинаСтроки` из `shquery_ru.hbk` — функции языка запросов, которых
в индексе не было никогда.

`ph-003` («заменить подстроку»), было 2 -> стало 4. Первое место занял
`Функция СтрЗаменить` из `shquery_ru.hbk` (0.75) — тоже новая страница.
Одну позицию отнял рост индекса, вторую — штраф за повтор объекта:
`СтрЗаменить` (0.5) как второй результат «Глобального контекста» учтён как
0.25 и пропустил вперёд статью со скором 0.361.

Коэффициент штрафа **намеренно не подбирался**. Любое значение между 0.72 и
1 вернуло бы `СтрЗаменить` на третье место, но подбор множителя по двум
известным примерам — это подгонка под набор тестов, а не улучшение поиска.
Выбор был из двух: оставить (13/13, Recall@5 100%, MRR 0.845) или откатить
ранжирование целиком (12/13, MRR 0.833) — второе хуже по всем числам.

MRR здесь меряет место одного заранее названного ответа и проседает даже
там, где выдача объективно стала лучше.

## Что осталось открытым

**Диалект языка не различается.** Разработчик, спрашивающий «заменить
подстроку», чаще имеет в виду встроенный язык, а не язык запросов. Сейчас
отличить их нечем: ни фильтра, ни признака в payload. Кандидат в отдельную
задачу — полезнее любой подкрутки ранжирования.

**`evals/runner/tests.py` падает** (`assert len(real) == 10`). К этому
заходу отношения не имеет: каталог `evals/runner/` не менялся. Вне
контейнера набор пропускается из-за отсутствия `mcp`, поэтому в прогонах
«0 провалов» его не было ни разу. Стоит посмотреть `git log` по каталогу.

## Что сделано сверх задачи

- **`PIPELINE_VERSION` в fingerprint** — иначе починка читателя не
  приводит к переиндексации и не доезжает до данных.
- **Убрана зависимость `mcp-platform-help` -> `help-indexer`** — из-за неё
  каждый запуск eval с `HELP_REINDEX_MODE=force` в переменных оболочки
  стирал коллекцию: измерение уничтожало измеряемое.
- **`scripts/probe_hbk.py`** — сверка числа записей в контейнере тремя
  независимыми способами и поиск конкретной страницы.
- **Прореживание дублей чанков одной страницы** в выдаче: само по себе
  подняло soft с 7/10 до 8/10.
