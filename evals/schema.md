# Формат eval-датасета

Один пример датасета — одна JSON-строка в `.jsonl`-файле. Пустые строки и строки, начинающиеся с `//`, пропускаются (нестандарт, но удобно оставлять комментарии в файле).

## Запись примера

```json
{
  "id": "ph-001",
  "tool": "platform_help_search",
  "args": {"query": "как разделить строку", "limit": 10},
  "expect": {
    "hard": [
      {"type": "name_in_top_k", "k": 5, "values": ["СтрРазделить", "StrSplit"]}
    ],
    "soft": [
      {"type": "any_hit_kind", "k": 5, "kinds": ["method"]}
    ]
  },
  "notes": "базовая функция работы со строками"
}
```

### Поля

| Поле      | Тип    | Обязательность | Описание                                                             |
|-----------|--------|----------------|----------------------------------------------------------------------|
| `id`      | строка | обязательно    | Уникальный идентификатор примера (например `ph-001`).                |
| `tool`    | строка | обязательно    | Имя MCP-tool'а. Например `platform_help_search`, `platform_help_lookup`, `v8std_get_page`. |
| `args`    | объект | обязательно    | Аргументы tool'а как есть — передаются в `session.call_tool(name, arguments=...)`. |
| `expect`  | объект | обязательно    | Группы предикатов: `hard` (должны пройти все) и `soft` (для мониторинга). |
| `notes`   | строка | опционально    | Пояснение — попадёт в markdown-отчёт.                                |

## Ground truth — смешанный

Идея — писать **жёсткие** проверки там, где эталон очевиден («должен быть такой метод в топе»), и **мягкие** там, где требования размытые («хорошо бы, чтобы топ был осмысленный»). Hard влияет на pass-rate, soft — только наблюдается в отчёте.

## Поддерживаемые типы предикатов

Предикат — объект с обязательным полем `type`. Остальные поля зависят от типа.

### `name_in_top_k` (hard или soft)

Ищет в первых `k` хитах ответа tool'а элемент, у которого `name_ru`, `name_en`, `full_name`, `id` или `title` совпадает с одним из `values`. Совпадение — точное, без учёта регистра.

`id` и `title` добавлены ради сервера `v8std`: там опознавательный признак хита — идентификатор страницы (`std783`, `bslls:UsingModalWindows`). Для `platform_help` этих ключей в хите нет, поэтому поведение старых датасетов не меняется.

```json
{"type": "name_in_top_k", "k": 5, "values": ["СтрРазделить", "StrSplit"]}
```

Поля:
- `k` — глубина поиска (1..50).
- `values` — список допустимых имён. Матч по любому считается попаданием.

### `any_hit_kind` (soft-рекомендуется)

Хотя бы один из первых `k` хитов имеет `kind` из списка `kinds`.

```json
{"type": "any_hit_kind", "k": 5, "kinds": ["method", "property"]}
```

### `non_empty` (hard-рекомендуется)

Tool вернул непустой `results`.

```json
{"type": "non_empty"}
```

Минимальная защита от «поиск не завёлся вообще». Стоит добавлять в каждый пример как страховочный hard.

### `results_count_at_least` (soft или hard)

В ответе не менее `min` результатов.

```json
{"type": "results_count_at_least", "min": 3}
```

### `full_name_contains` (soft)

В первых `k` хитах есть такой, у которого `full_name` содержит подстроку (без учёта регистра).

```json
{"type": "full_name_contains", "k": 5, "substr": "СправочникОбъект"}
```

### `field_equals` (hard или soft)

Значение по точечному пути в ответе равно ожидаемому. Путь идёт по ключам словарей и индексам списков: `found`, `page.id`, `results.0.type`.

```json
{"type": "field_equals", "path": "page.id", "value": "std783"}
```

Строки сравниваются без учёта регистра и пробелов по краям, остальные типы — как есть. Если ключа в ответе нет, предикат **не проходит** (в `detail` будет `found: false`) — это отличает «поле отсутствует» от «поле равно null».

Нужен там, где у ответа нет ключа `results`: так устроен `v8std_get_page` (`found` + `page`) и ловушки вида «стандарта не существует».

### `path_non_empty` (hard или soft)

По точечному пути лежит непустой список, строка или словарь.

```json
{"type": "path_non_empty", "path": "diagnostics"}
```

Аналог `non_empty` для ответов с другой формой: `diagnostics` и `standards` у `v8std_explain_diagnostics`, `related` у `v8std_get_related`.

### Неизвестный тип

Если `type` не опознан, предикат считается **failed** и помечается в отчёте как `unknown_predicate_type`. Это чтобы опечатка в датасете не проходила молча.

## Как считается MRR и Recall@K

Только по hard-предикатам типа `name_in_top_k` — это единственный предикат, где есть понятие «ранг первого совпадения». Для примеров без такого предиката MRR не считается (в отчёте — `—`), и в агрегированной метрике они не участвуют.

- **Recall@K** — доля примеров (с hard `name_in_top_k`), где совпадение нашлось в первых K хитах.
- **MRR** — среднее `1/rank`; если не нашлось в пределах `k` предиката — вклад 0.

## Мини-пример файла

```jsonl
// строковые функции
{"id":"ph-001","tool":"platform_help_search","args":{"query":"разделить строку","limit":10},"expect":{"hard":[{"type":"non_empty"},{"type":"name_in_top_k","k":5,"values":["СтрРазделить","StrSplit"]}],"soft":[{"type":"any_hit_kind","k":5,"kinds":["method"]}]}}
{"id":"ph-002","tool":"platform_help_lookup","args":{"name":"НайтиПоНаименованию"},"expect":{"hard":[{"type":"non_empty"},{"type":"name_in_top_k","k":3,"values":["НайтиПоНаименованию","FindByDescription"]}],"soft":[]}}
```
