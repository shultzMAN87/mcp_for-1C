## FIX-3 — «Neo4j недоступна» ≠ «граф пуст»

Раньше `_neo4j_available()` возвращал `False` в обоих случаях, и оба давали
один ответ `{"error": "Neo4j недоступен"}`. Агент, получив его на
`metadata_search`, сообщал пользователю, что такого объекта в конфигурации
нет — хотя про конфигурацию не было известно ничего.

Теперь три состояния и два разных ответа:

```json
{
  "error": "graph_empty",
  "graph_state": "empty",
  "answerable": false,
  "message": "Neo4j отвечает, но граф пуст: ни одного узла :MetadataObject…",
  "meaning": "Это НЕ значит, что искомого объекта нет в конфигурации…",
  "hint": "docker compose run --rm -e METADATA_FORCE_REINDEX=true metadata-indexer"
}
```

```json
{
  "error": "neo4j_unavailable",
  "graph_state": "unavailable",
  "answerable": false,
  "meaning": "Это НЕ значит, что искомого объекта нет в конфигурации…",
  "detail": "OSError: [Errno 111] Connection refused",
  "hint": "docker compose ps neo4j && docker compose logs --tail=50 neo4j"
}
```

Поля `answerable: false` и `meaning` — прямая инструкция агенту не
домысливать. Ради этого задача и делалась.

**Три инструмента ведут себя по-особому:**

- `metadata_stats` теперь отвечает и на пустом графе — нулями и
  `graph_empty: true`. Иначе агенту нечем отличить одно от другого:
  диагностический инструмент не может сам падать с той же ошибкой.
- `metadata_reload` блокируется только при недоступности: очистка пустого
  графа осмысленна.
- `metadata_upsert_file` / `metadata_remove_file` пропускают пустой граф —
  `incremental.py` сам вернёт `metadata_layer_empty` с внятной причиной.

**Новый модуль `graph_state.py`.** Логика вынесена из `server.py`, потому
что тот при импорте поднимает FastMCP и требует `NEO4J_PASSWORD` — покрыть
его юнит-тестами нельзя ни в CI, ни на хосте, где `mcp` не установлен.
Заодно снята дубликация `NON_CONFIG_CALL_REASONS`: раньше константа лежала
в двух серверных файлах с пометкой «править оба места», теперь источник
один. Парная копия в indexer-side `bsl_resolver.py` осталась — общего
import-пути между двумя сторонами нет, и за их совпадением следит тест.

## FIX-4.2 — добор по разбору 22 пробелов

- `ВладелецФормы` добавлен в свойства контекста формы — снимает 3 записи.
- `BUILTIN_FUNCS` пополнен восемью глобальными методами платформы
  (`СтрокаСоединенияИнформационнойБазы`,
  `ПолучитьСтруктуруХраненияБазыДанных`, три
  `Начать*РасширенияРаботыСФайлами` и родственные) — снимает 5 записей.
- Туда же три метода, вызываемых неявно на `ЭтотОбъект`: `Метаданные`,
  `ИзменитьРеквизиты`, `Индекс` — по той же схеме, что уже лежащие там
  `Записать`, `Закрыть`, `ЭтоНовый`. Снимает ещё 3 записи.

Ограничение приёма известно и записано в комментарии: если в конфигурации
появится **своя** процедура с одним из этих имён, её вызов уйдёт в skip
вместо `:CALLS`. Для этих конкретных имён риск ничтожен.

Ожидаемый результат: пробелов 22 → 11.

**Не закрыто (по договорённости, хвост в PLAN-2):** реквизиты объектов
обработок (`СохраняемыеСостояния` — 2 записи) и резолв `Объект` /
`ЭтотОбъект` / `Ссылка` через родительский объект метаданных. Это одна и та
же работа с индексом слоя 1, и делать её логично рядом с `FEAT-1`.

## Порядок применения

### 1. Тесты на хосте

Два набора, в разных каталогах.

```powershell
cd D:\Docker\30_mcp_cursor\1c-mcp-suite\mcp-metadata-graph-neo4j
python -m unittest tests_bsl_parser tests_bsl_resolver tests_graph_writer `
                   tests_incremental tests_metadata_xml
```

Ожидается `Ran 271 tests … OK (skipped=8)`.

```powershell
cd D:\Docker\30_mcp_cursor\1c-mcp-suite\mcp-metadata-graph
python -m unittest tests_graph_state
```

Ожидается `Ran 22 tests … OK`. Это новый набор — `mcp` для него не нужен,
проверяется `graph_state.py`.

### 2. Замер на выгрузке

```powershell
cd D:\Docker\30_mcp_cursor\1c-mcp-suite\mcp-metadata-graph-neo4j
python calibrate_inference.py D:\Docker\30_mcp_cursor\workspace --check
```

Пробелов должно стать около 11. В `топ module_ref среди настоящих пробелов`
не должно остаться `ВладелецФормы`.

### 3. Пересборка и переиндексация

```powershell
cd D:\Docker\30_mcp_cursor
docker compose build mcp-metadata-graph metadata-indexer
docker compose up -d --force-recreate mcp-metadata-graph
docker compose run --rm -e METADATA_FORCE_REINDEX=true metadata-indexer
```

`Dockerfile.python` изменился, поэтому `build` обязателен, а не только
`up --force-recreate`.

### 4. Проверка FIX-3 на живом стеке

Это единственная задача из всех, которую можно проверить прямым
экспериментом. Порядок такой.

**Шаг А — нормальное состояние.** В Cursor:

```
Вызови metadata_search на сервере metadata и найди справочник АукАукционы.
```

Должен найтись.

**Шаг Б — гасим Neo4j:**

```powershell
docker compose stop neo4j
```

Тот же промпт в Cursor. Ожидаем ответ с `"error": "neo4j_unavailable"`.
Важно не только это поле, но и поведение агента: он должен сказать, что
база недоступна, **а не** что справочника нет в конфигурации.

**Шаг В — поднимаем обратно:**

```powershell
docker compose start neo4j
```

Подождать секунд двадцать, повторить промпт — снова находит.

Состояние `graph_empty` специально воспроизводить не нужно: очистка графа
через `metadata_reload` требует `ALLOW_DESTRUCTIVE_TOOLS`, а ронять рабочий
граф ради проверки текста ошибки не стоит. Логика этого состояния покрыта
тестами из шага 1.

### 5. Проверка счётчиков

```
Вызови metadata_stats и покажи блок code.
Затем code_unresolved_callsites с limit=50 — все записи таблицей.
```

Контроль: `callsites_resolved` = 2426 не меняется, пробелов около 11.
`callsites` может немного уменьшиться — восемь новых `BUILTIN_FUNCS` теперь
уходят в skip и узлов `:CallSite` не создают.
