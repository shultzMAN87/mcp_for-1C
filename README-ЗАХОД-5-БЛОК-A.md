## Часть 1. Что за дисциплина и почему она одна на все находки

За предыдущую сессию один узор всплыл четыре раза:

| Что случилось | Как выглядело |
|---|---|
| читатель `.hbk` отдавал 25 страниц из 128 | `HTML: 25` — нормальная строка лога |
| fingerprint не знал версии кода | «данные не менялись», починка не доезжала |
| `depends_on` на one-shot стирал коллекцию | измерение уничтожало измеряемое |
| `gen_lockfiles.sh` и `.ps1` разошлись | скрипт отрабатывал успешно |

Ни один не выглядел поломкой. Каждый нашёлся сверкой чисел. Это не четыре
дефекта, а один: **шаг печатает выход и не печатает вход.**

Образец правильного поведения в проекте уже был — `_warn_shortfall` в
`graph_writer.py`, «отправлено N, записано M, разница вслух». Он вызывался
в трёх местах и больше нигде, хотя ровно та же пара чисел есть у каждого
парсера, читателя и индексатора.

## Часть 2. `A-2` — общий модуль `1c-mcp-suite/shortfall.py`

Без зависимостей сверх стандартной библиотеки: модуль кладётся и в
`Dockerfile.python` (индексер метаданных), и в `Dockerfile.embeddings`
(индексатор справки), и проверяется тестами без единого пакета.

Три сущности:

**`warn_shortfall(what, sent, written, log=, hint=)`** — прежнее правило
`graph_writer`, вынесенное наружу. Сам `graph_writer._warn_shortfall`
остался тонкой обёрткой со своей подсказкой: три его вызова переписывать
незачем, а второй копии правила быть не должно.

**`Tally`** — счётчик одного шага: `see()` на каждом входном элементе,
`keep()` на дошедшем, `drop(причина, пример)` на отсеянном. Проверяет
арифметику:

```
вход == выход + сумма отсева
```

Невязка в этом равенстве — главное число модуля. Ноль означает, что автор
шага перечислил все выходы. Не ноль — что данные уходят по пути, которого
в коде счётчика нет. Именно такие пути и съедали данные во всех
разобранных случаях.

Отсев сам по себе не тревога: картинки в контейнере справки — законная и
массовая потеря. Тревога — это невязка, нулевой выход при непустом входе,
причина, помеченная `alarm=True` (битый XML законным не бывает), или
падение доли ниже `min_keep_ratio`.

**`TallyBook`** — набор счётчиков за прогон и сводка. Отдельный шаг может
отчитаться честно, а прогон в целом — потерять треть данных на трёх шагах
по одиннадцать процентов: ни один из трёх не выглядит поломкой, и заметить
это можно, только когда все пары чисел стоят рядом.

Формат вывода:

```
  разбор XML метаданных: вход 4 файл → выход 3, отсев 1
  причины отсева: битый XML 1 (напр. Catalogs/Битый.xml)
  ⚠ разбор XML метаданных: «битый XML»: 1 — причина законной не бывает
    проверьте выгрузку: конфигуратор битых XML не даёт
```

Главная строка идёт в INFO **всегда**, в том числе когда всё сошлось: вход
должен быть виден и при хорошем исходе, иначе сравнивать со следующим
прогоном будет не с чем.

## Часть 3. `A-1` — где сверка проставлена

| Место | Вход | Что было невидимо |
|---|---|---|
| `metadata_xml._parse_object` | — | четыре разных «не получился» были неразличимы |
| `metadata_xml.walk_workspace` | `*.xml` в каталогах KINDS | потеря 30% файлов неотличима от нормы |
| `metadata_xml.unknown_kind_dirs` | каталоги верхнего уровня | **новое**: вид объектов вне KINDS |
| `bsl_parser.walk_workspace_bsl` | `rglob("*.bsl")` | файл вне схемы путей уезжал в `log.debug` |
| `hbk_reader.iter_html_from_hbk` | записи контейнера | «25 страниц» выглядело результатом |
| `hbk_indexer.iter_chunks_from_dir` | четыре сужения подряд | каждое печатало только свой выход |
| `indexer.py` | все шаги | сводка потерь в конце прогона |

### Детектор смены раскладки

`unknown_kind_dirs()` — новая функция, отвечающая на вопрос, которого
раньше никто не задавал: какие каталоги верхнего уровня содержат XML и не
входят в `KINDS`. `walk_workspace` ходит только по известным каталогам,
поэтому появление нового вида объектов не даёт ни ошибки, ни
предупреждения — объекты просто не появляются в графе. Ровно так жил
`FIX-8`: восемь видов не индексировались, и узнали об этом случайно.

Диагностика идёт мимо арифметики счётчика: эти файлы не «отсеяны», их
вообще не рассматривали. Но в лог они попадают:

```
⚠ каталоги верхнего уровня вне KINDS: 1, в них 1 XML — эти объекты
  в граф НЕ попадут: НовыйНеизвестныйВид (1)
  если это новый вид объектов — добавьте его в KINDS; если сменился
  формат выгрузки — индексер к нему не готов
```

### Порог доли для BSL

У разбора BSL отсев по причине «вне схемы путей» законен поштучно и
катастрофичен массово. Один файл — норма, девять из десяти — переход
выгрузки на другой формат. Поэтому `min_keep_ratio=0.9`: на реальной
выгрузке схема путей покрывает все штатные размещения модулей.

### Совместимость

Все изменённые функции принимают `tally` необязательным параметром и без
него работают ровно как раньше — сигнатуры совместимы, вызовы из
`incremental.py`, `calibrate*.py` и `smoke_resolver.py` не трогались. Когда
счётчик не передан, `walk_workspace` и `walk_workspace_bsl` заводят его
внутри и печатают сами: вход должен быть виден при любом вызове.

## Часть 4. Остальные находки

### `A-3`. Фолбэк на 20 функций — авария, а не режим

`mcp-platform-help/server.py`. 14 августа коллекция была пуста два часа, и
этого не поймал никто: предикат `non_empty` проходил на встроенном списке,
поиск по точному имени проходил, галочки стояли. Диагноз занял четыре
итерации, причём неверные гипотезы строились именно на «поиск же
отвечает».

Что сделано:

- сообщение уезжает в `stderr`, а не только в поле ответа, которое читает
  модель, а не человек;
- в ответе появилось поле `degraded`, и оно присутствует **в обеих
  ветках** — на успехе тоже. Урок `FIX-19`: поле, по которому отличают
  норму от отказа, обязано быть везде, иначе проверка на него получает
  `null` там, где всё хорошо;
- `note` при фолбэке прямо говорит, что это не полная справка и ответы на
  её основе считать неполными.

### `A-4`. Деградация hybrid → dense перестала быть молчаливой

Переход «гибрид сломался, отвечаем одним вектором» жил в `logger.debug`,
невидимом при штатном уровне. Качество выдачи падало, а метрики нет: eval
меряет попадание в топ-k, и на простых запросах dense-only справляется.

Первое падение режима печатается в `stderr`, дальше только считается;
счётчики уезжают в `platform_help_stats` полем `degradations`. Залить лог
это не может, а человек, пришедший разбираться «почему выдача стала хуже
без единой ошибки», получает ответ сразу.

### `A-5`. Пропущенный набор — не успех

`scripts/run_all_tests.py`. Итоговая строка была `OK: 17 наборов, 696
тестов` и не различала «прошло» и «не запускалось». Следствие уже
случилось: `evals/runner/tests.py` падает на боевой машине, а во всех
прогонах пропускался из-за отсутствующего пакета `mcp` — и «0 провалов»
было верно ровно для того окружения, где тест не выполнялся.

Теперь:

```
OK: проверено 19 наборов из 20, НЕ ЗАПУСКАЛИСЬ: 1, 740 тестов за 6.8 с
```

и флаг `--strict` (цель `make test-strict`), который делает не запущенный
набор провалом. В CI «не проверялось» и «проверено» — разные исходы.

### `OBS-2`. Сервер сам отвечает, чем и когда собран индекс

Вопрос «почему поиск не находит X» занял четыре итерации именно потому,
что ответить на него мог только человек с доступом в контейнер. Данные всё
это время лежали в коллекции — индексатор пишет их в точку `id=0`.

`platform_help_stats` получил блок `index`:

```json
"index": {
  "fingerprint": "a1b2c3…",
  "indexed_at_iso": "2026-08-14 19:22:10",
  "age_hours": 20.3
}
```

плюс сводное поле `degraded` — считается на сервере, а не выводится
читателем из трёх других полей: выводить приходилось человеку, и он
выводил неверно.

`metadata_stats` получил тот же блок по узлам `:Fingerprint` (слои XML и
BSL отдельно): значение, режим, дата, возраст. На вопрос «граф вообще
пересобирался после правки выгрузки» до этой правки отвечал только запрос
к Neo4j руками.

### `EVAL-3`. `scripts/eval_all.py` — все датасеты одной командой

За сессию датасеты гонялись вручную семь раз. Скрипт находит их сам по
маске (захардкоженный список разошёлся бы ровно так же, как разошлись два
генератора лок-файлов), гоняет через `scripts/eval.py`, печатает таблицу и
сравнивает с предыдущим отчётом по тому же датасету:

```
датасет                 hard      soft    MRR      мс  отчёт
platform_help          15/15     8/10  0.845     274  platform_help_20260815_….json
                       ↓ против platform_help_20260814_….json: hard 13/13 → 12/15
```

Просадка hard — это регресс, и он должен быть виден, а не вычисляться
человеком из двух json. Код возврата ненулевой при регрессе
(`--no-regression-check` отключает) и при hard < 100%.

Попутно закрыт `DOC-3`: рядом с числами печатается имя файла отчёта.
Базовая строка в `PLAN-5` разошлась с фактическим отчётом и успела стать
основанием для неверного критерия приёмки именно потому, что рядом с ней
не стояло, откуда она взята.

Цели: `make eval-all`, `make eval-summary` (сводка без прогона).

### `DOC-1`. LLM-ключи → WARN вне профиля `opencode`

`check_prereqs` ставил `FAIL` на отсутствие LLM-ключей, которые нужны
только оркестратору OpenCode — сервису из профиля `opencode`, в связке с
Cursor не поднимающемуся вообще. Проверка кричала о том, что не влияет.

Это зеркало той же болезни: там отказ выглядел как успех, здесь успех
выглядит как отказ, и цена одинаковая — в отчёт перестают смотреть.
Красный, который горит всегда, ничего не сообщает.

Профиль считается запрошенным, если `opencode` перечислен в
`COMPOSE_PROFILES` (переменная окружения или `.env`). Если да — `FAIL` как
раньше. Если нет — `WARN` с пояснением, за что ключи отвечают. То же для
`LLM_MODEL_STRONG` / `LLM_MODEL_FAST`: без профиля это `OK` с примечанием.

## Часть 6. Как проверять

Правки в парсерах не меняют состав графа — меняют то, что печатается.
Поэтому переиндексация не нужна, а приёмка идёт по логам.

```powershell
# 1. Тесты. Ожидается: 19 наборов из 20, 740 тестов, 1 не запускался.
python scripts\run_all_tests.py

# 2. Сверка двух генераторов лок-файлов (входит в набор выше).
python scripts\tests_lockfile_pairs.py

# 3. Пересборка образов — новый модуль должен доехать в оба.
docker compose build mcp-metadata-graph mcp-platform-help

# 4. Подъём. --no-deps, иначе перезапуск потянет индексер.
docker compose up -d --force-recreate --no-deps mcp-metadata-graph mcp-platform-help
```

Кириллица в PowerShell: `$OutputEncoding` и `[Console]::OutputEncoding` —
иначе `docker logs` приедет битым.

### Что смотреть в логах индексера

При следующем полном прогоне (`METADATA_FORCE_REINDEX=true`) в логе должны
появиться строки вида:

```
  разбор XML метаданных: вход 39114 файл → выход 10747, отсев 28367
  причины отсева: нет элемента <Catalog> 28367
  разбор BSL: вход 17296 файл → выход 14047, отсев 3249
Сводка потерь (4 шагов):
  ✓ разбор XML метаданных: вход 39114 → выход 10747 (отсев 28367)
  ✓ разбор BSL: вход 17296 → выход 14047 (отсев 3249)
  ✓ модули → узлы :Module: вход 14047 → выход 14041 (отсев 6)
  ✓ процедуры → узлы :Callable: вход 231114 → выход 231114 (отсев 0)
```

Числа приведены по прошлым прогонам и заведомо не сойдутся точно — важно
не совпадение, а то, что **обе цифры теперь есть**. Ожидаемые отклонения:

- шаг «модули → узлы `:Module`» покажет недостачу 6 — это те же 6 модулей
  форм перечислений, из-за которых 28 процедур без владельца. Известный
  остаток, не регресс;
- если всплывёт предупреждение про каталоги вне `KINDS` — посмотрите,
  что там: либо новый вид объектов для `KINDS`, либо обвязка без XML
  (тогда её надо занести в исключения).

### Что смотреть в справке

```powershell
# Индекс собран, дата и отпечаток на месте.

python scripts\eval.py --dataset evals/datasets/platform_help.jsonl
```
