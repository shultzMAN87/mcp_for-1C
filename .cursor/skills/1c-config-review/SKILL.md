# Обзор и аудит конфигурации

Это отчёт, по которому принимают решения «удалить», «переписать»,
«оставить». Каждый вывод — с источником: инструмент и что он вернул.
Слово «мёртвый» без оговорок не писать (см. ниже).

## Шаг 0. Масштаб и свежесть

`metadata_stats`: сколько объектов, модулей, процедур, покрытие резолва
(`resolve_coverage_pct`), блок `source`. Покрытие говорит, насколько
верить выводам про вызовы: при 92 % — каждый двенадцатый вызов граф не
связал. Это число назвать в отчёте.

`source.in_sync: false` — сначала `metadata_refresh()`.

## Обзор: что есть

- Подсистема: `metadata_subsystem_tree` (`root` — имя подсистемы) — дерево
  с составом.
- Объекты вида: `metadata_list_objects` (`kind: "Справочник"` / `"Документ"`
  / …; `subsystem` — ограничить подсистемой). Большие списки идут
  страницами — `has_more`, `next_offset`.
- Объект подробно: `metadata_object_attributes`, связи —
  `metadata_referrers`.

## Аудит: кандидаты на удаление

**Объекты вне подсистем** — `metadata_dead` (`kind: "Catalog"` и т. п. —
здесь английское имя вида — или все). Это не
обязательно мусор: служебные регистры, константы, объекты обмена часто
сознательно не включают в подсистемы. Кандидат на удаление — объект вне
подсистем **и** без ссылок (`metadata_referrers` пуст) **и** без кода,
который с ним работает (`code_procedures_operating_on` пуст).

**Процедуры без вызовов** — `code_dead_procedures`:

- по модулю (`module_id: "Catalog.X.ObjectModule"`), а не по всей
  конфигурации: по всей — тысячи строк, их никто не прочитает;
- по умолчанию обработчики (`ПриЗаписи`, `ПриСозданииНаСервере`, …) и
  экспортные исключены. Экспортные включать (`include_exports: true`)
  только с пояснением: их могут звать извне через строку или из
  расширений.

Почему «нет вызовов» ≠ «мёртвая»:

- вызов через строку (`Выполнить`, `ВыполнитьМетодКонфигурации`,
  оповещения, `ОписаниеОповещения("Имя", ЭтаФорма)`);
- команды формы и обработчики элементов, привязанные в `Form.xml`;
- подписки на события и регламентные задания;
- код расширений и внешних обработок — их в графе нет.

Поэтому в отчёте — «нет статических вызовов», и перед удалением
— поиск имени процедуры по тексту выгрузки.

## Аудит: пробелы в графе

`code_unresolved_callsites` — вызовы, похожие на обращение к коду
конфигурации, которым граф не нашёл адресата. По модулю
(`module_id`) или по причине (`reason`):

- `unknown_module` — модуль с таким именем не найден: опечатка, удалённый
  модуль, или модуль из расширения/БСП;
- `unknown_method_in_common_module` — модуль есть, метода нет: метод
  удалён или переименован, а вызов остался — **это потенциальная ошибка
  рантайма**, показать первой;
- `unknown_local_method` — метода нет в своём модуле;
- `stale_after_incremental` — граф устарел после точечного обновления,
  ждёт полной индексации; не дефект кода.

## Аудит: качество кода

- Модуль: `bsl_check_file` с путём внутри контейнера —
  `/data/1c-src/<путь от корня конфигурации>`.
- Каталог: `bsl_check_directory` (`/data/1c-src/CommonModules`) —
  постранично, файлы с проблемами.
- Коды замечаний — одним вызовом `v8std_explain_diagnostics`, в отчёт —
  номер стандарта и требование, а не пересказ.
- `answerable: false` от линтера — проверка недостоверна (`bsl_stats` —
  почему). «Замечаний нет» не писать.

## Что отдавать пользователю

Отчёт по разделам: обзор (цифры из `metadata_stats`), кандидаты на
удаление с тремя проверками (подсистемы / ссылки / код), потенциальные
ошибки (`unknown_method_in_common_module`), замечания линтера по
стандартам. В конце — чего граф не видит и что поэтому надо проверить
руками перед удалением.

## Ловушки

- `has_more: true` — показано не всё; итоговые числа считать только после
  всех страниц или назвать «не менее N».
- `graph_empty` / `neo4j_unavailable` — остановиться; аудит по памяти не
  делать.
- Объект не нашёлся — может жить в расширении. Не утверждать, что его нет.
