# PLAN-12: полная индексация быстрее — диск, процессор, полнота

Дата: 3 ноября 2026. Предыдущий план — `PLAN-11.md` (граф следит за
выгрузкой через git), состояние набора — `СТАТУС.md`, что не сделано —
`ОТКРЫТОЕ.md`.

## Правило захода

**Сначала мерить, потом ускорять.** Захода два раза подряд начинались с
гипотезы «тормозит X» и заканчивались тем, что тормозило Y. Поэтому
каждый пункт про скорость здесь либо убирает причину, измеренную в логе,
либо сам является измерением.

Исходные числа — полная индексация 3 ноября 2026 (переход на git,
`PLAN-11`), боевая выгрузка: 58 215 файлов, 1,2 ГБ, 238 911 процедур.

| Этап | Время | Чем ограничен |
|---|---|---|
| Обход выгрузки для отпечатков | 12,3 мин | диск через границу Docker |
| Поиск `*.bsl` перед разбором (`rglob`) | ~16 мин, без единой строки в логе | то же |
| Разбор BSL | 7,6 мин | процессор, одно ядро |
| Резолв, итерация 1 | >30 мин; скорость падает 701 → 133 проц/с | процессор, одно ядро (98 % CPU, память 3 из 11,5 ГБ) |
| Запись в Neo4j | минуты | Neo4j |

Выводы, на которых стоит план:

1. Почти полчаса — ожидание диска. Его убирает git (`git ls-files`), а не
   другой язык или больше ядер.
2. Резолв упирается в одно ядро при свободной памяти. Своп исключён
   (`docker stats`). Падение скорости внутри одного прохода при постоянной
   работе на процедуру — признак того, что время уходит не на резолв, а
   на что-то, растущее с числом объектов в памяти: первая гипотеза —
   сборщик мусора Python.
3. Переписывать индексер на другой язык не стоит: ~6 600 строк разбора и
   вывода типов плюс 210 тестов, а полная индексация после `PLAN-11` —
   редкое событие (переход, ночь, крупное обновление). Сравнение
   вариантов — в конце.

Блоки A → (стенд) → B → C. Блок C — по результатам замеров.

## Блок A. Дешёвое, и замеры для блоков B и C

### `PERF-14` — список `*.bsl` без второго обхода выгрузки

**Где.** `bsl_parser.walk_workspace_bsl`: `sorted(root.rglob("*.bsl"))` —
полный обход 58 тысяч файлов через границу Docker Desktop сразу после
обхода для отпечатков, и молча: прогресс начинается только после того,
как список готов. В логе это 16 минут между «Парсим BSL…» и первой
строкой прогресса.

**Что сделать.**
- Режим git: список из `git ls-files -z -- <subdir>` (читает один файл
  индекса, секунды) плюс файлы из `dirty` состояния источника. Новые
  неотслеживаемые модули, о которых агент не сообщил, подхватит сверка —
  она и так запускается после полной индексации (`needs_reconcile`).
  `ls-files` — в белый список `git_source.py`, сторож уже есть.
- Режим legacy: список берётся из обхода для отпечатков
  (`fingerprint_workspace_multi` и так видит каждый файл) — второго обхода
  нет.
- Если список всё-таки строится обходом (индексер запущен вне обоих
  путей) — прогресс-строка раз в 20 секунд: «найдено N файлов, прошло…».
- `walk_workspace_bsl` получает необязательный `paths=` — сигнатура
  обратно совместима, тесты разбора не меняются.

**Мера приёмки.** На стенде между «Парсим BSL…» и первой строкой
прогресса — секунды, а не 16 минут. Число файлов на входе разбора то же,
что раньше (17 864), — `разбор BSL: вход N файл` в логе.

**Тесты.** На временном репозитории: список из `ls-files` + dirty
совпадает с `rglob`; файл вне `src/` в список не попадает; неотслеживаемый
файл без dirty — не попадает (и это записано как ожидаемое).

**Объём:** S.

### `PERF-13`, шаг 1 — сколько времени съедает сборщик мусора

**Гипотеза.** Сборщик мусора Python раз за разом пересматривает миллионы
объектов: разобранные модули с текстом процедур плюс копящиеся узлы и
рёбра вызовов. Каждый проход дольше предыдущего — скорость резолва падает
монотонно, процессор занят, память свободна. Ровно картина из лога.

**Что сделать.**
- Счётчик времени сборщика через `gc.callbacks` (почти бесплатно): в
  строке прогресса резолва — `gc: 41 %` (доля времени с прошлой строки) и
  в итоговой строке итерации — сколько секунд из её времени ушло на сборку.
- Флаг `METADATA_GC_FREEZE` (по умолчанию `false` до замера): после
  разбора BSL — `gc.collect()` + `gc.freeze()`. Разобранные модули уходят в
  «вечное» поколение, сборщик перестаёт их пересматривать. Это
  стандартный приём для программ с большой неизменной кучей.
- Флаг передаётся в `docker-compose.yml` (сторож
  `TestEnvReachesContainers` проверит, что он дошёл до контейнера).

**Мера приёмки — двойная, записанная до опыта:**
- `gc` в строке прогресса больше 30 % → гипотеза подтверждена; прогон с
  `METADATA_GC_FREEZE=true` обязан держать скорость резолва не ниже
  500 проц/с на всём проходе. Тогда флаг включается по умолчанию.
- `gc` меньше 5 % → гипотеза опровергнута, причина в алгоритме → шаг 2
  (`PERF-13` в блоке C), профилировщик.

**Тесты.** Флаг выключен — поведение байт в байт прежнее (граф на
фикстурах совпадает). Флаг включён — тот же граф.

**Объём:** S.

### `FIX-34`, часть Б — модули команд объектов (~1 550)

**Решение владельца (3 ноября 2026): вариант 1 — только код.**

Команда объекта отдельным узлом в слое 1 не лежит (индексер не разбирает
раздел `Commands` XML объекта), поэтому модулю команды не к чему
«прилипнуть», как модуль формы прилипает к `:Form`. Решение: модуль
команды — самостоятельный узел-модуль, как модуль объекта и менеджера:

    Catalogs/Номенклатура/Commands/ПечатьЭтикеток/Ext/CommandModule.bsl
      → module_id   Catalog.Номенклатура.Command.ПечатьЭтикеток
        вид         Command, родитель Catalog.Номенклатура

- Имя команды сохраняется в id модуля — вызовы из разных команд одного
  объекта (у всех `ОбработкаКоманды`) не сливаются.
- Контекст — клиент (`&НаКлиенте` в модуле команды — норма); директива
  процедуры, как у форм, уточняет.
- Владение: модуль виден `ownership_report` как модуль с владельцем
  (родитель — объект), `HAS_METHOD` от модуля к его процедурам.
- `owner_of` и `dependent_owners` (частичное обновление): правка XML
  объекта перезаливает и модули его команд — как модули форм.

Чего вариант 1 **не** даёт: команды как метаданных — поиска по синониму,
свойств (тип параметра, группа). Если понадобится — вариант 2 (узел
`:Command` из XML + модуль к нему) надстраивается сверху без переделки:
id модуля останется тем же.

**Мера приёмки.** `разбор BSL: дошло` — 99 % и выше (отсев — только
действительно незнакомые размещения); `code_callers` на процедуре общего
модуля, вызываемой из `ОбработкаКоманды`, показывает модуль команды.

**Тесты.** Путь → id/вид/родитель для команды объекта и для вложенного
объекта (`…/Commands/X` у документа, регистра, обработки); две команды
одного объекта дают два разных модуля; частичное обновление: правка XML
справочника перезаливает модули его команд.

**Объём:** M.

## Блок B. Параллельность в одном контейнере

### `PERF-15` — разбор и резолв на нескольких ядрах

**Почему один контейнер, а не несколько.** Все контейнеры Docker Desktop
работают в одной виртуальной машине и делят одни ядра. Несколько
контейнеров — те же ядра плюс сетевая координация (раздать модули,
передать каждому весь индекс резолвера, синхронизировать итерации,
собрать результат), то есть самописный пул процессов через сеть. Смысл
он имел бы только на разных машинах. Потоки в Python процессорную работу
не параллелят (GIL); нужны процессы.

**Разбор BSL.** Файлы независимы → `multiprocessing.Pool` по файлам,
результат собирается в исходном порядке. Ожидание: 7,6 мин → 2–3 мин на
4 процессах.

**Резолв.** Внутри одной итерации каждая процедура обрабатывается
независимо: читает общие реестры типов (`param_types`, `return_types`) и
индекс, выдаёт свои узлы, рёбра и факты. Реестры обновляются между
итерациями. Отсюда схема:

```
итерация k:
  fork пула (модули, индекс, реестры — без копирования, copy-on-write)
  каждый процесс: _resolve_pass по своей доле модулей
  сборка результатов В ПОРЯДКЕ модулей → слияние фактов в реестры
  пул закрывается; следующая итерация — новый fork с новыми реестрами
```

`_resolve_pass` уже чистая функция от (модули, индекс, реестры) — её не
надо переписывать, только звать на долях.

**Подвохи и что с ними делать.**
- **Память.** Python трогает счётчики ссылок, и страницы, «общие» после
  fork, копируются в каждый процесс. Средство — то же `gc.freeze()` перед
  fork (`PERF-13`): замороженные объекты сборщик не трогает. Сейчас 3 ГБ
  из 11,5 ГБ, поэтому число процессов — настройка `METADATA_WORKERS`,
  по умолчанию `min(4, ядра − 1)`; `1` — прежний последовательный путь
  байт в байт. Docker Desktop на стенде владельца видит **12 ядер**
  (`NCPU`, 3 ноября 2026) — потолок задаёт память, а не ядра: начинать с
  4, после замера пиковой памяти с `gc.freeze` пробовать 6 и 8.
- **Объём результатов.** Миллионы словарей узлов и рёбер на обратном пути
  сериализуются. Процесс возвращает компактные кортежи, словари
  собираются в главном процессе.
- **Детерминированность.** Порядок сборки фиксирован (по модулям), поэтому
  граф и счётчики совпадают с последовательным прогоном до числа.
- **Платформа.** `fork` — только Linux, то есть контейнер. На Windows-хосте
  (тесты разработчика) пул работает через `spawn` или выключается
  (`METADATA_WORKERS=1`) — тесты обязаны проходить в обоих случаях.

**Чего не трогаем.** Запись в Neo4j: минуты, а параллельная запись упрётся
в блокировки базы. Точечное обновление (`PLAN-11`): там единицы файлов.

**Мера приёмки.**
- Граф после параллельного прогона совпадает с последовательным:
  счётчики узлов и рёбер по типам, покрытие резолва — до единицы
  (`scripts/check_baseline.py`).
- Разбор + резолв на стенде — в `METADATA_WORKERS` раз быстрее с допуском
  на сборку (цель для 4 процессов — не меньше чем в 2,5 раза).
- Пиковая память контейнера — в `СТАТУС.md`; не больше 80 % лимита.

**Тесты.** `tests_parallel_resolve.py`: фикстура из десятков модулей,
последовательный и параллельный прогон (`workers=1` и `workers=3`) дают
одинаковые `code_graph` до байта; падение одного процесса пула — прогон
падает с понятной ошибкой, а не отдаёт неполный граф (`FIX-15`).

**Объём:** L.

### `PERF-16` — PyPy для контейнера индексера (эксперимент)

Индексер использует только стандартную библиотеку и ничего новее
Python 3.10 (проверено) — его можно запустить на PyPy (JIT): на циклах
такого вида обычно в 3–10 раз быстрее. Отдельный `Dockerfile.indexer-pypy`,
переключение одной строкой `dockerfile:` у `metadata-indexer`; серверы
остаются на CPython. Мера приёмки — та же сверка графа с эталоном и время.
Совместимо с `PERF-15` (у PyPy есть `multiprocessing`).

### `FIX-36` — декларации без конца

По примерам из `LOG-2`: усечённое имя (`СформироватьОтправлени`) похоже
на ошибку разбора, а не на директивы препроцессора; может оказаться той
же причиной, что `FIX-35` (процедура разбирается дважды). Фикстуры из
реальных мест → правка парсера → тест на каждое место.

**Отступления от плана.**
- Процесс возвращает те же словари узлов и рёбер, что и последовательный
  проход, а не компактные кортежи: так склейка — простая конкатенация, и
  равенство с `workers=1` проверяется сравнением целого `code_graph`.
  Если на стенде сериализация окажется заметной в профиле — сжать.
- На Windows (`spawn`) параллельный путь не включается вовсе:
  `resolve_workers` возвращает 1. Иначе дочерним процессам пришлось бы
  передавать весь индекс через pickle — дороже, чем выигрыш.
- `gc.freeze()` делается вокруг каждого пула (`frozen_for_fork`) и
  снимается после, если не задан `METADATA_GC_FREEZE` — тот морозит раз
  и навсегда, и его заморозку пул не снимает.
- С `METADATA_PROFILE=true` резолв идёт в один процесс: `cProfile` видит
  только свой процесс и показал бы одно ожидание дочерних.
- Ниже 2000 файлов или процедур (`PARALLEL_MIN_ITEMS`) — последовательно:
  на точечном обновлении fork дороже работы.

**Тесты.** `tests_parallel_resolve.py` (20): последовательный и
параллельный (2 и 3 процесса) резолв дают одинаковый `code_graph` на
синтетике с фикс-пойнтом в две итерации; разбор — одинаковые модули и
одинаковый список деклараций без конца; падение работника роняет прогон
и не оставляет состояния; прогресс считает все процедуры; маленький
объём идёт последовательно; `AMBIGUOUS` переживает pickle как тот же
объект; `GcMeter` и профиль. Мутационная проверка: склейка в обратном
порядке и потеря деклараций без конца из дочерних процессов — тест падает.
