# Промпт-шаблоны для работы с 1C MCP Suite

Готовые формулировки задач для агента, подключённого к четырём серверам:
`metadata` (структура конфигурации и граф вызовов), `bsl` (статический анализ),
`help` (справка платформы), `query` (запросы).

Имена в шаблонах совпадают с ключами в `.cursor/mcp.json`.

## Принципы, общие для всех шаблонов

Хороший промпт содержит четыре блока:

1. **Контракт задачи** — вход, выход, краевые случаи. Без этого агент угадывает.
2. **Маршрутизация по MCP** — в каком порядке смотреть за знаниями. Принцип:
   сначала существующий код и структура конфигурации, потом справка,
   потом написание с нуля.
3. **Стандарты** — стандарты разработки 1С, стиль кода, серверный/клиентский
   контекст.
4. **Формат ответа** — план, код, результат проверки. Чтобы не разбирать каждый
   раз разные структуры.

Во всех шаблонах ниже явно запрещены уточняющие вопросы. Это сознательно:
для понятной задачи лучше получить «разумное предположение, помеченное
в плане», чем потратить вызовы на диалог. Для действительно неоднозначных
задач запрет снимайте — в шаблоне 4 он снят намеренно.

## 1. Чтение CSV-файла в таблицу значений

```
# Задача
Напиши функцию на BSL, которая читает CSV-файл и возвращает ТаблицуЗначений.

# Контракт
Сигнатура: ПрочитатьCSVВТаблицу(ПутьКФайлу, Параметры = Неопределено) Экспорт

Параметры:
- ПутьКФайлу: Строка — путь к файлу на сервере.
- Параметры: Структура с опциональными полями:
  - Разделитель            (Строка, ";")
  - Кодировка              (КодировкаТекста, UTF8)
  - ПерваяСтрокаЗаголовки  (Булево, Истина)
  - ТипыКолонок            (Соответствие: ИмяКолонки -> ОписаниеТипов, пусто = Строка)
  - ЭкранированиеКавычками (Булево, Истина)

Возвращает: ТаблицаЗначений.
- Если ПерваяСтрокаЗаголовки = Истина — имена колонок из первой строки
  (нормализация: пробелы -> подчёркивания, недопустимые символы убираются).
- Если Ложь — "Колонка1", "Колонка2"…
- Пустой файл -> пустая таблица без ошибки.

# Требования
- Только на сервере. Директива &НаСервере или экспорт из общего модуля «Сервер».
- Обработка ошибок: при проблеме с файлом или несоответствии числа колонок —
  ВызватьИсключение с текстом, содержащим номер строки.
- Парсер должен обрабатывать: экранирование двойных кавычек ("" -> "),
  переносы строк внутри полей в кавычках, пустые поля, BOM в начале файла.
- Никаких глобальных переменных.

# Стандарты
- Следуй стандартам разработки конфигураций фирмы «1С».
- Комментарии к функции по формату БСП (описание, параметры, возвращаемое, пример).
- Именование на русском, КаждоеСловоСБольшой.

# Маршрут работы
1. help — синтаксис ЧтениеТекста, ТаблицаЗначений.Колонки.Добавить, ОписаниеТипов.
2. metadata — code_procedures_operating_on по ТаблицаЗначений и ЧтениеТекста:
   есть ли в конфигурации уже написанные функции разбора файлов. Если есть —
   посмотри их через code_method_signature и держись того же стиля.
3. bsl — после написания прогони bsl_check_code. Если есть диагностики, исправь
   и прогони повторно.

# Формат ответа
1. План (3-5 строк): что нашёл в справке и в существующем коде, какой подход
   выбираешь.
2. Код функции целиком.
3. Результат bsl_check_code (должно быть «без диагностик»).
4. Список краевых случаев, которые стоит покрыть тестами (сами тесты не пиши).

Не задавай уточняющих вопросов. Неясное — отметь в плане как предположение.
```

## 2. Добавление нового реквизита в справочник

```
# Задача
Добавить в справочник «Контрагенты» реквизит «ИННДляКонтроля» (Строка, длина 12,
обязательный). При записи элемента реквизит должен валидироваться: длина 10 или
12 цифр, корректная контрольная сумма.

# Что нужно сделать
1. Показать изменения в метаданных (описание для Конфигуратора или XML).
2. Написать функции валидации ИНН (общий модуль, серверный контекст).
3. Написать обработчик ОбработкаПроверкиЗаполнения (уточни по стандартам БСП,
   где правильнее — модуль объекта или модуль менеджера).
4. Обновить форму элемента: индикация ошибки, сообщение пользователю.

# Маршрут работы
1. metadata — metadata_object_attributes по Справочник.Контрагенты: какие
   реквизиты уже есть, чтобы не создать дубликат. Затем metadata_referrers —
   кто ссылается на этот справочник, чтобы понимать масштаб влияния.
2. metadata — code_procedures_operating_on по Справочник.Контрагенты: какие
   процедуры уже работают с этим объектом. Если валидация ИНН где-то написана —
   переиспользуй, не дублируй.
3. help — ОбработкаПроверкиЗаполнения, СообщениеПользователю: где и когда
   вызываются, как привязать сообщение к полю формы.
4. bsl — после написания.

# Стандарты
- Валидация ИНН по алгоритму из налогового законодательства: разные веса
  для 10- и 12-значных.
- Сообщения — через СообщениеПользователю с привязкой к полю формы.
- Серверный код — в общем модуле с признаком «Сервер».
- Тексты сообщений — в НСтр(...), если в проекте это принято.

# Формат ответа
1. Список изменений в метаданных (plain text, без XML если возможно).
2. Код общего модуля с функциями валидации.
3. Код обработчика проверки заполнения.
4. Код модуля формы — только изменения, diff-стиль.
5. Результат bsl_check_code.
6. Список случаев для тестов: валидный 10-значный, валидный 12-значный,
   неверная контрольная сумма, буквы, пустая строка.
```

## 3. Написание отчёта на СКД

```
# Задача
Отчёт «Продажи по менеджерам за период» на СКД.

# Контракт отчёта
Группировки: Менеджер → Контрагент.
Ресурсы: Количество, Сумма, СуммаСкидки, СуммаБезСкидки.
Параметры отбора: НачалоПериода, КонецПериода (обязательные),
                  Организация (необязательный), Менеджер (необязательный).
Источник: документы «РеализацияТоваровУслуг», проведённые, в рамках периода.
Вывод: табличный документ с итогами по менеджеру и общим итогом.

# Маршрут работы
1. metadata — metadata_search по «продаж», затем metadata_list_objects
   по регистрам накопления: есть ли регистр, где продажи уже агрегированы.
   Использовать регистр ПРЕДПОЧТИТЕЛЬНЕЕ, чем строить запрос по документам.
2. metadata — metadata_object_attributes по выбранному источнику: как именно
   лежат суммы, скидки, менеджер. Для полей ссылочного типа —
   metadata_attribute_type, чтобы правильно строить соединения.
3. query — query_fields по выбранной таблице, потом query_build.
   Для регистра накопления используй виртуальную таблицу Обороты или
   ОстаткиИОбороты с параметрами периода.
4. query — query_validate, затем query_optimize. Замечания уровня HIGH
   исправь обязательно. В ответе query_validate различай errors и warnings:
   errors — доказанное расхождение с метаданными, исправляй молча;
   warnings — места, где проверка не смогла ничего утверждать, их проверяй
   глазами, а не переписывай наугад.
5. help — секции СКД: схема компоновки, наборы данных, ресурсы, параметры.

# Что жду
1. Какую таблицу выбрал источником и почему (1-2 строки).
2. Текст запроса.
3. Описание схемы СКД: поля, ресурсы, параметры, роли (Измерение/Ресурс) — таблицей.
4. Настройки варианта по умолчанию: группировки, отборы, условное оформление.
5. Код модуля отчёта, если нужна программная пост-обработка.

# Стандарты
- Использовать регистры, а не документы, если регистр есть.
- Виртуальные таблицы — ВСЕГДА с параметрами периода и отбора, а не с отбором
  в ГДЕ после соединения.
- Формат сумм в ресурсах: Число(15, 2).

Не задавай уточняющих вопросов.
```

## 4. Рефакторинг длинной процедуры

```
# Задача
В модуле объекта документа РеализацияТоваровУслуг процедура ОбработкаПроведения
выросла до ~400 строк: проверки, движения по 5 регистрам, вызовы внешних API,
уведомления.

Нужен рефакторинг: разнести ответственность, но НЕ СЛОМАТЬ поведение.

# Ограничения
- Поведение при проведении остаётся 1-в-1. Никаких «улучшений логики по пути».
- Сигнатура ОбработкаПроведения не меняется — это обработчик события.
- Транзакционность сохраняется: что падало с исключением и откатывало
  проведение — должно продолжать падать с тем же исключением.
- Структуру регистров не менять, даже если кажется, что лучше.

# Маршрут работы
1. metadata — code_callees по ОбработкаПроведения: полный список того, что
   процедура вызывает. Это каркас декомпозиции.
2. metadata — code_callers по каждой вспомогательной процедуре, которую
   собираешься трогать. Если у неё есть другие вызывающие — трогать нельзя.
3. metadata — metadata_referrers по документу: какие подписки на события
   и регламентные задания на него завязаны, чтобы не продублировать логику,
   уже вынесенную в подписку.
4. metadata — code_unresolved_callsites: если в процедуре есть неразрешённые
   вызовы, скажи мне об этом до начала — там граф не поможет и нужна
   ручная проверка.
5. help — если используются нестандартные методы платформы.
6. bsl — после рефакторинга, обязательно.

# Стандарты
- Декомпозиция по ответственности: проверки отдельно, движения отдельно,
  внешние эффекты (API, уведомления) отдельно и в самом конце.
- Внешние эффекты не должны быть внутри транзакции. Если сейчас они внутри —
  отметь как известное техдолговое место, но САМ НЕ ЧИНИ: это изменение поведения.
- Именование приватных процедур — как принято в проекте; посмотри соседние
  через code_method_signature.

# Формат ответа
1. Разбор: какие логические части выделил, с номерами строк.
2. План рефакторинга: что куда переезжает, какие процедуры появляются.
3. Дождись моего подтверждения плана, код сразу не пиши.
4. После подтверждения — код в формате «было / стало» по каждой части.
5. Результат bsl_check_file.

ЗДЕСЬ уточняющие вопросы разрешены: если план двусмысленный, лучше спроси.
```

## 5. Разбор ошибки из журнала регистрации

```
# Задача
У пользователя «Иванов И.И.» с 14:30 до 14:35 сегодня валится серия ошибок
«Поле объекта не обнаружено (Контрагент)» при проведении документов
ПоступлениеТоваровУслуг.

Текст ошибки из журнала целиком:
<вставить сюда>

Нужно: понять причину, показать место в коде, предложить исправление.

# Маршрут работы
1. metadata — metadata_object_attributes по Документ.ПоступлениеТоваровУслуг:
   есть ли реквизит Контрагент прямо на документе или он берётся из договора.
   Если ссылочный — metadata_attribute_type, чтобы понять, что там за тип
   и может ли он быть пустым.
2. metadata — code_procedures_operating_on по этому документу: все процедуры,
   которые с ним работают. Из них выбери те, что участвуют в проведении.
3. metadata — code_callers по найденной процедуре: откуда она вызывается,
   не приходит ли туда объект в неинициализированном состоянии.
4. help — если нужен справочник по конкретному методу.

# Что жду
1. Гипотезу о причине (1-2 абзаца).
2. Точное место: модуль, процедура, строка.
3. Исправление в формате «было / стало».
4. Как избежать впредь: проверка через ЗначениеЗаполнено, или архитектурная
   правка, если причина в метаданных.

# Чего делать НЕ нужно
- Не предлагай «переписать документ с нуля». Нужен точечный фикс.
- Не выдумывай содержимое журнала регистрации: у тебя нет доступа к живой базе.
  Работай только с тем текстом ошибки, который я привёл выше.

# Формат ответа
1. Гипотеза.
2. Чем подтвердил: что увидел в метаданных и в коде.
3. Код фикса.
4. Рекомендация на будущее.
```

## 6. Оценка влияния изменения

Шаблон под то, ради чего граф вызовов и строился: понять цену правки до того,
как она сделана.

```
# Задача
Хочу изменить сигнатуру функции <ОбщийМодуль.ИмяФункции>: добавить обязательный
параметр <Имя>.

Нужно: полный список того, что сломается, и план правки.

# Маршрут работы
1. metadata — code_method_signature по функции: текущая сигнатура,
   какие параметры уже есть и какие из них с значениями по умолчанию.
2. metadata — code_callers по функции: все места вызова.
3. metadata — code_call_path от каждого найденного вызывающего до точек входа
   (обработчики событий, команды форм, регламентные задания) — чтобы понимать,
   какие пользовательские сценарии затронуты.
4. metadata — code_unresolved_callsites: если у этой функции есть неразрешённые
   вызовы (вычисляемые имена, Выполнить), скажи явно — граф их не видит,
   и список вызывающих неполон.

# Формат ответа
1. Текущая сигнатура.
2. Таблица: модуль | процедура | что придётся изменить.
3. Затронутые пользовательские сценарии — по цепочкам вызовов.
4. Оценка: правка локальная / затрагивает несколько подсистем / рискованная.
5. Предложение: можно ли обойтись параметром со значением по умолчанию
   вместо обязательного.

Код пока не пиши. Мне нужна оценка, а не реализация.
```

## Хорошие привычки

**Проси план перед кодом.** Пара секунд, но раз из пяти план показывает, что
агент неправильно понял задачу — и ты ловишь это до того, как он потратит
десяток вызовов на неправильное решение.

**Явно называй сервера, когда важен порядок.** Без подсказки агент напишет
из головы то, что нужно было взять из `metadata`. С подсказкой — полезет туда
первым делом.

**Начинай с `metadata_stats`, если граф вызывает сомнения.** Если `code`
показывает ноль callables — индексация не отработала, и все ответы про код
будут выдумкой. Лучше узнать это сразу. `resolve_coverage_pct` на здоровом
графе — за 90%: в знаменатель идут только вызовы, которые претендуют быть
обращением к коду конфигурации, а `callsites_object_method` (вызовы методов
объектов платформы вроде `РезультатЗапроса.Выбрать()`) считаются отдельно.

**Не проси «улучшать» код по пути при рефакторинге.** Разбивай на две задачи:
сначала чистый рефакторинг без изменения поведения, потом улучшения. Безопаснее
и легче ревьюить.

**Запрашивай `bsl` явно.** Агент забывает прогнать проверку, особенно если
задача выглядит простой. Одна строка в промпте гарантирует запуск.

**Для запросов всегда проси `query_optimize`.** Виртуальная таблица без
параметров и соединение с подзапросом — две самые дорогие ошибки в 1С,
и обе ловятся автоматически.

**Для коротких задач — короткие промпты.** Не надо писать простыню для
«переименуй переменную». Шаблоны выше — для задач, где цена ошибки выше
стоимости хорошо написанного промпта.

**Пополняй файл.** Встретил задачу, которая повторится — добавь сюда шаблоном.
Через полгода это сэкономит часы.
