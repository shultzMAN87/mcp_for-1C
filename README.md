# 1C MCP Suite

Набор MCP-серверов, дающих AI-агенту знание о конкретной конфигурации 1С:
граф метаданных и вызовов, синтаксическая справка платформы, конструктор
запросов, статический анализ BSL и стандарты разработки.

Серверы независимы друг от друга и подключаются к любому агенту, который умеет
в MCP по Streamable HTTP — Cursor, OpenCode, собственное расширение для EDT.

---

## Состав

Пять MCP-серверов:

| Сервер | Порт | Что даёт | Инструментов |
|---|---|---|---|
| `metadata-graph` | 8001 | структура конфигурации и граф вызовов в Neo4j | 18 |
| `bsl-checker` | 8002 | статический анализ через BSL Language Server | 4 |
| `platform-help` | 8003 | синтакс-помощник платформы (гибридный поиск по `.hbk`) | 5 |
| `query-builder` | 8009 | построение, валидация и разбор запросов | 5 |
| `v8std-mcp` | 8765 | стандарты разработки 1С (чужой сервер, CC0) | 5 |

Пятый — единственный, код которого мы не пишем: он приезжает из
репозитория `zeegin/v8std` вместе с корпусом. Подробности и обоснование —
`docs/archive/ИТОГИ-STD.md`.

Итого 37 инструментов. Инфраструктура: Neo4j (граф), Qdrant (векторы),
индексаторы метаданных и справки, `workspace-watcher` для инкрементального
обновления графа.

Короткая инструкция по развёртыванию (годится как статья в Confluence) —
`docs/РАЗВЁРТЫВАНИЕ.md`. Устройство набора в двух страницах —
`ARCHITECTURE.md`. Лицензия своя MIT,
чужое (BSL LS, корпус v8std, образы Neo4j и Qdrant) не хранится в
репозитории и приезжает при сборке — там же разобрано, что под какой
лицензией.

Подробно про устройство каждого сервера и назначение каждого инструмента —
раздел «MCP-серверы и инструменты».

Транспорт один — **Streamable HTTP, эндпоинт `/mcp`, режим stateless**.
SSE удалён полностью. Все порты публикуются только на `127.0.0.1`.

## Требования

- Docker Desktop с лимитом памяти **не менее 8 ГБ** (индексатор справки берёт
  ~2 ГБ только под модель, при 4 ГБ он падает по OOM)
- Python 3.10+ на хосте — только для проверочных скриптов
- XML-выгрузка конфигурации в `workspace/`
- Установленная платформа 1С на хосте — из неё скрипт
  `scripts\fetch_platform_help.py` копирует справку (`*_ru.hbk`) в
  `platform-help-data/`
- Корпус стандартов в `v8std-data/` — забирается командой
  `python3 scripts/fetch_v8std.py` (нужна сеть один раз)

## Установка

### 1. Секреты

```powershell
Copy-Item .env.example .env
```

Заполнить два обязательных поля:

```dotenv
MCP_SHARED_SECRET=<openssl rand -hex 32>
NEO4J_PASSWORD=<случайная строка, hex или base64 без спецсимволов>
```

Сгенерировать в PowerShell без openssl:

```powershell
python -c "import secrets; print(secrets.token_hex(32))"
```

Пустое значение любого из них — **серверы не стартуют**, выход с кодом 78.
Это намеренно: раньше пустой секрет просто отключал аутентификацию, и стек
поднимался открытым с предупреждением в логе, которое никто не читает.

Если Neo4j уже поднималась, пароль хранится **внутри тома**, и `NEO4J_AUTH`
его не переопределит — переменная работает только при первой инициализации.
Менять так:

```powershell
docker compose exec neo4j cypher-shell -u neo4j -p <старый> `
  "ALTER CURRENT USER SET PASSWORD FROM '<старый>' TO '<новый>'"
```

### 2. Проверка окружения

```powershell
python scripts\check_prereqs.py
```

Проверяет Docker, `.env`, пароль Neo4j, `MCP_SHARED_SECRET`, `.cursor/mcp.json`,
наличие выгрузки (`WORKSPACE_DIR` из `.env`, по умолчанию `workspace/`) и
справки в `platform-help-data/`. Если справки нет, подскажет команду
шага 2.6.

### 2.5. Корпус стандартов (STD-1)

```powershell
python scripts/fetch_v8std.py
```

Кладёт в `./v8std-data` индекс стандартов и модули MCP-сервера v8std,
пишет `FETCH.json` с коммитом, датой и sha256 каждого файла. Каталог в
`.gitignore`. Сеть нужна только здесь — контейнер потом работает офлайн.
Обновление корпуса — та же команда (скачает только изменившееся).

Проверить, насколько индекс отстал:

```powershell
python scripts/fetch_v8std.py --check
```

Шаг можно пропустить: при пустом `./v8std-data` сервер возьмёт индекс с
v8std.ru сам при старте. Тогда ему нужна сеть при каждом холодном старте
(кеш живёт в томе `v8std-cache`), а при системном прокси — ещё и
переменные `HTTPS_PROXY`, закомментированные в сервисе `v8std-mcp`.
Запретить этот режим: `V8STD_ALLOW_REMOTE_INDEX=0` в `.env`.

### 2.6. Справка платформы (HELP-COPY)

```powershell
python scripts\fetch_platform_help.py
```

Копирует **только русскую** справку — файлы `*_ru.hbk` — из каталога `bin`
установленной платформы в `./platform-help-data`. Английские `*_root.hbk`
не берутся: индексатор (`HBK_INDEX_LANG=ru`) их всё равно пропускает, а
места они занимают столько же.

Откуда брать, скрипт решает так:

1. ключ `--src`;
2. переменная `ONEC_BIN_DIR` — из окружения или из `.env`;
3. иначе — самая новая версия в `C:\Program Files\1cv8` (и в `Program Files (x86)`).

Чтобы версия платформы не зависела от того, что установилось последним,
закрепите её в `.env`:

```dotenv
ONEC_BIN_DIR=C:\Program Files\1cv8\8.3.27.1606\bin
```

Можно указать и каталог версии, и корень `1cv8` — тогда берётся самая
новая. Полезные ключи:

```powershell
python scripts\fetch_platform_help.py --list      # какие версии найдены
python scripts\fetch_platform_help.py --dry-run   # что будет скопировано
python scripts\fetch_platform_help.py --clean     # заодно убрать лишние .hbk
```

Время изменения файлов сохраняется, поэтому повторный запуск на той же
версии ничего не меняет и переиндексацию не вызывает. Откуда и из какой
версии взята справка — в `platform-help-data/SOURCE.json`; её же
показывает `check_prereqs.py`.

**Обновили справку, когда индекс уже собран** (новая версия платформы) —
индексатор по умолчанию (`skip_if_nonempty`) непустую коллекцию не
трогает, пересборку нужно запустить явно (1,5–2 часа):

```powershell
docker compose run --rm -e REINDEX_MODE=if_files_changed help-indexer
```

### 3. Сборка и запуск

```powershell
docker compose build
docker compose up -d
```

Первая сборка — 10–15 минут (образ с моделями эмбеддингов тяжёлый).
Первая индексация справки — **час-полтора на CPU**. Это разовая работа:
`REINDEX_MODE=skip_if_nonempty` гарантирует, что последующие `up` стартуют
мгновенно.

В логах каждого сервера должно быть три строки:

```
[tool-filter] metadata-graph: профиль=core, инструментов 29 -> 18
[mcp-auth] metadata-graph: auth ENABLED (secret length=64)
[mcp-http] metadata-graph: Streamable HTTP на http://0.0.0.0:8001/mcp (stateless, auth on)
```

### 4. Приёмка

```powershell
bash scripts\smoke_zahod1.sh
```

Проверяет: секретов нет в репозитории, без заголовка `Authorization` серверы
отвечают 401, с заголовком — 200, `/sse` отдаёт 404, порты не слушают наружу,
состав инструментов в бюджете, выключенные серверы не подняты.

### 5. Подключение Cursor

Положить `.cursor/mcp.json` в корень **рабочего проекта 1С** — того, где лежит
XML-выгрузка, а не обязательно этого репозитория. Вписать туда значение
`MCP_SHARED_SECRET` из `.env` вместо плейсхолдера:

```json
{
  "mcpServers": {
    "metadata": {
      "url": "http://127.0.0.1:8001/mcp",
      "headers": { "Authorization": "Bearer <секрет>" }
    },
    "v8std": {
      "url": "http://127.0.0.1:8765/mcp"
    }
  }
}
```

У `v8std` заголовка нет намеренно: сервер чужой и нашу bearer-схему не
знает. Публичный вариант — тот же блок с адресом `https://ai.v8std.ru/mcp`
(и с оговоркой про `v8std_explain_snippet`, см. описание сервера № 5).

Подстановка `${MCP_SHARED_SECRET}` работает не во всех версиях Cursor, поэтому
секрет вписывается строкой. Файл в `.gitignore` — коммитить его не нужно.

Проверить независимо от Cursor можно через MCP Inspector:

```powershell
npx @modelcontextprotocol/inspector
```

Transport — `Streamable HTTP`, адрес `http://127.0.0.1:8001/mcp`, заголовок
`Authorization: Bearer <секрет>`.

## MCP-серверы и инструменты

Разделение по серверам не по темам, а по **источникам данных**: у каждого
своё хранилище, свой цикл наполнения и свой режим отказа. Общее у всех —
транспорт Streamable HTTP, bearer-авторизация (`mcp_auth.py`), запуск через
`start.py`, фильтр инструментов, метрики, пагинация и кэш.

**Два поля в каждом ответе своих серверов** (`OBS-1`): `answerable` — можно
ли опереться на ответ, и `degraded` — ответ пригоден, но хуже штатного.
Рядом с отказом идёт `meaning` с прямым текстом «это НЕ значит, что объекта
нет». Пустой список и отказ выглядели одинаково — шесть дефектов подряд
жили ровно на этом. `v8std-mcp` не тронут: он чужой.

**Постраничность у всех своих серверов одна** (`B-4`): `pagination`,
`has_more`, `next_offset`, `returned`. У справки `pagination: "none"` —
ранжированная выдача не листается, и ответ говорит, что делать вместо
листания. Словарь живёт в `mcp_pagination.py`, а `tests_pagination.py`
не даёт завести второй.

### MCP-Сервер № 1 — `metadata-graph`, порт 8001

**Назначение.** Ядро проекта. Отвечает на вопросы «что есть в конфигурации»
и «кто кого зовёт». Данные складывает отдельный контейнер
`metadata-indexer`, сервер только читает. Индексация двухфазная: слой
метаданных (разбор XML выгрузки) и слой кода (разбор `.bsl` и резолв
вызовов). Второй слой зависит от первого, первый от второго — нет, поэтому
метаданные можно проиндексировать отдельно и быстро.

**Стек.** Python, FastMCP, Neo4j по HTTP-транзакциям — без драйвера, только
stdlib `urllib`. Разбор XML и BSL собственный: регулярки и рекурсивный
спуск, без внешних парсеров. Инкрементальное обновление — вручную через
`apply_changes.py` либо автоматически контейнером `workspace-watcher`;
про выбор между ними см. «Обновление выгрузки».

Инструменты — структура конфигурации:

- **Инструмент 1 — `metadata_stats`** — общая картина обоих слоёв: сколько чего в графе, покрытие резолва вызовов.
- **Инструмент 2 — `metadata_search`** — поиск объектов по имени и синониму. Точка входа почти для любой задачи.
- **Инструмент 3 — `metadata_list_objects`** — список объектов заданного вида целиком.
- **Инструмент 4 — `metadata_object_attributes`** — реквизиты объекта с ролями (реквизит, измерение, ресурс) и типами.
- **Инструмент 5 — `metadata_attribute_type`** — тип конкретного реквизита с резолвом до объекта-цели.
- **Инструмент 6 — `metadata_referrers`** — кто ссылается на объект через реквизиты, включая табличные части.
- **Инструмент 7 — `metadata_find_link_path`** — пути связи между двумя объектами через ссылочные реквизиты.
- **Инструмент 8 — `metadata_subsystem_tree`** — дерево подсистем целиком или поддерево от указанного корня.
- **Инструмент 9 — `metadata_dead`** — объекты, не входящие ни в одну подсистему.

Инструменты — граф вызовов:

- **Инструмент 10 — `code_callers`** — кто вызывает процедуру, транзитивно.
- **Инструмент 11 — `code_callees`** — кого вызывает процедура, транзитивно.
- **Инструмент 12 — `code_call_path`** — кратчайший путь вызовов от одной процедуры к другой.
- **Инструмент 13 — `code_method_signature`** — сигнатура: тип, директива, экспортность, параметры.
- **Инструмент 14 — `code_procedures_operating_on`** — процедуры, работающие с конкретным объектом метаданных.
- **Инструмент 15 — `code_dead_procedures`** — процедуры без входящих вызовов.
- **Инструмент 16 — `code_unresolved_callsites`** — настоящие пробелы в графе вызовов. Отфильтровано всё, где слева от точки не модуль конфигурации: переменная (`РезультатЗапроса.Выбрать()`), свойство контекста (`Ссылка.ПолучитьОбъект()`), глобальный объект платформы (`Метаданные.НайтиПоТипу()`). В `resolve_coverage_pct` они не входят.

Свежесть графа (`SRC-8`):

- **Инструмент 17 — `metadata_refresh`** — доиндексировать граф по изменениям выгрузки. С путями — «я поменял эти файлы» (агент зовёт после записи в `src/`); без аргументов — «проверь сейчас» (сдвинулся ли `HEAD`). `reconcile=true` — сверка через `git status`, `dry_run=true` — только план. Свежесть — в `metadata_stats` → `source`.

Служебные, вызывает `workspace-watcher` в режиме poll, агенту не нужны (в режиме git они идут через тот же механизм, что `metadata_refresh`):

- **Инструмент 18 — `metadata_upsert_file`** — точечно переиндексировать один файл выгрузки.
- **Инструмент 19 — `metadata_remove_file`** — удалить из графа срез, принадлежащий одному файлу.

### MCP-Сервер № 2 — `bsl-checker`, порт 8002

**Назначение.** Статический анализ кода 1С: синтаксис и соответствие
стандартам. Единственный сервер без хранилища и без состояния — ничего не
индексирует и ничего не помнит между вызовами.

**Стек.** Обёртка над внешним анализатором **BSL Language Server** на Java.
Образ `eclipse-temurin:17-jre` плюс Python-обёртка: кладёт код во временный
файл, запускает анализатор, разбирает его JSON и отдаёт диагностики.

- **Инструмент 1 — `bsl_check_code`** — проверить переданный фрагмент кода.
- **Инструмент 2 — `bsl_check_file`** — проверить файл `.bsl` на диске.
- **Инструмент 3 — `bsl_check_directory`** — проверить все `.bsl` в каталоге.
- **Инструмент 4 — `bsl_stats`** — состояние самого анализатора: доступна ли
  java, на месте ли jar и какой он версии, чем закончились последние запуски
  (`B-7`).

Проверка одного файла или фрагмента идёт через долгоживущий BSL LS
(`PERF-7`): JVM стартует один раз, поэтому первый вызов в сессии стоит
около десяти секунд, а последующие — доли секунды. Если долгоживущий
процесс не поднялся или умер, проверки идут прежним путём `--analyze` —
медленнее, но с тем же результатом; `bsl_stats` покажет причину и счётчик
`analysis.by_mode`, из которого видно, каким путём шли вызовы. Выключить:
`BSL_LSP_MODE=off`. Анализ каталога быстрым путём не идёт намеренно.

`bsl_stats` отвечает всегда, в том числе когда анализатор мёртв: «java не
найдена» — это достоверный ответ на заданный вопрос, а не поломка
инструмента. Поэтому `answerable: true` даже при разобранном линтере, а
неготовность видна по `linter_available: false`. Так же устроен
`metadata_stats` после `FIX-3` — он обязан отвечать и на пустом графе.

Кеша у него нет намеренно: к диагностическому инструменту приходят с
вопросом «жив ли ты прямо сейчас», и кешированный ответ на такой вопрос не
устарел, а перевёрнут (урок приёмки 15 августа, когда `metadata_stats`
отдавал из кеша картину здоровья работающего графа во время аварии).

**Свой набор диагностик (`CFG-4`).** Файл настроек BSL Language Server
лежит в `./bsl-config/bsl-language-server.json` и монтируется в контейнер
`:ro`. Правка правил стоит `docker compose restart mcp-bsl-checker` —
пересборка образа не нужна.

Каким набором получен отчёт, видно в самом отчёте: у всех трёх проверок
есть секция `config` с отпечатком файла, режимом и числом включённых
правил. Это не украшение. При `mode: ONLY` включены **только**
перечисленные диагностики, поэтому «замечаний не найдено» означает «не
найдено из этого списка» — без отпечатка такой ответ нельзя ни
воспроизвести, ни сравнить с прошлым.

Если файл не найден или не разбирается, проверка **не** останавливается:
она идёт набором по умолчанию, а ответ помечается `degraded: true` с
причиной. Битый JSON анализатору не передаётся намеренно — с ним BSL LS не
поднимается ни быстрым путём, ни запасным, и деградация («проверили не тем
набором») превратилась бы в полный отказ («не проверили вовсе»).
Предпочитаете отказ — `BSL_LS_CONFIG_STRICT=true`.

⚠️ **Корень конфигурации.** BSL LS ищет метаданные там, куда показывает
`configurationRoot` — относительно **анализируемого каталога**
(`/data/1c-src`), а не относительно самого файла настроек. Не нашёл — не
сообщает: просто не подтягивает метаданные, и диагностики, которым они
нужны, тихо не срабатывают, а отчёт выглядит чище, чем код. `CFG-7`:
параметр из `bsl-config/bsl-language-server.json` убран (выгрузка лежит в
корне тома), но проверка осталась и работает в обоих случаях — заданного
пути и незаданного. Ответ: `bsl_stats` → `config.configuration_root_check`
(`resolves`), у проверок каталога — `config.warning` и `degraded: true`.
Подробности — `bsl-config/README.md`.

### MCP-Сервер № 3 — `platform-help`, порт 8003

**Назначение.** Семантический поиск по справке платформы 1С. Важное
различие: `metadata_*` — про **вашу конфигурацию**, `platform_help_*` — про
**сам язык и платформенные объекты**. Индекс наполняет отдельный контейнер
`help-indexer`: разбирает контейнеры `.hbk`, режет страницы на карточки,
считает эмбеддинги и кладёт в Qdrant.

**Стек.** Python, Qdrant, `sentence-transformers` (модель E5), `fastembed`.
Поиск гибридный: плотные векторы плюс BM25, результаты сливаются через RRF.
Самый тяжёлый образ в проекте — там же `torch`.

- **Инструмент 1 — `platform_help_search`** — семантический поиск по справке, когда точное имя неизвестно.
- **Инструмент 2 — `platform_help_lookup`** — точная карточка по имени метода, свойства или события.
- **Инструмент 3 — `platform_help_details`** — карточка целиком: параметры, синтаксис, примеры.
- **Инструмент 4 — `platform_help_kinds`** — какие типы страниц есть в индексе и сколько их.
- **Инструмент 5 — `platform_help_stats`** — доступен ли Qdrant, сколько документов, схема коллекции.

**Первый запрос после перезапуска контейнера стоил 23 секунды.** Причина
была не в ленивой загрузке — прогрев в фоне существовал, — а в том, что
флаг «загружено» ставился ПОСЛЕ загрузки: поток прогрева и первый запрос
грузили по копии модели одновременно (`PERF-6`). Флаг отвечает на вопрос
«уже готово?», а спрашивать надо было «этим уже кто-то занят?» — на это
отвечает только замок.

Тем же были больны все ленивые синглтоны сервера, поэтому и клиент Qdrant
переехал в общий реестр (`PERF-6.1`) — он грузится первым, раньше моделей:
секунда против двенадцати, а нужен `lookup`, `stats` и определению схемы
коллекции, которым модель не нужна вовсе. Схема коллекции определяется там
же, в конце прогрева, но запоминается только удачный ответ: на старте
`help-indexer` может ещё строить индекс, и запомнить «коллекции нет» значило
бы отвечать «поиск недоступен» из кеша следующие полминуты (`FIX-12`
наоборот).

Итог: разовая цена перезапуска платится, пока контейнер поднимается, а
`platform_help_stats.warmup` показывает состояние, время и число загрузок
по каждой записи реестра — `parts.dense`, `parts.sparse`, `parts.qdrant`.
Двойка в `loads` означала бы, что гонка вернулась; за этим следит пример
`ph-023`. Отключается `HELP_WARMUP=0`.

### MCP-Сервер № 4 — `query-builder`, порт 8009

**Назначение.** Построение и проверка запросов на языке запросов 1С. Читает
тот же граф Neo4j, что и `metadata-graph`, но **только слой метаданных** —
код ему не нужен. Это значит, что запросы работают сразу после первой фазы
индексации, не дожидаясь разбора кода.

**Стек.** Python, FastMCP, Neo4j по HTTP. Логика вынесена из `server.py` в
модули без FastMCP и без базы, чтобы её можно было покрыть тестами:
`query_parser.py` (лексер и разбор структуры запроса), `query_check.py`
(сверка с метаданными через интерфейс провайдера — в проде Neo4j, в тестах
словарь), `query_optimize_rules.py` (правила производительности). Полного
разбора выражений нет намеренно: для сверки имён достаточно вытащить
цепочки `Псевдоним.Поле.Поле`.

- **Инструмент 1 — `query_fields`** — поля таблицы: реквизиты, стандартные реквизиты, табличные части, виртуальные таблицы; для регистров измерения и ресурсы отдельно. Умеет отдавать состав колонок временной таблицы, если передать текст пакета в `query_text`.
- **Инструмент 2 — `query_join_hint`** — как соединить две таблицы: ищет ссылочные связи в обе стороны и через табличные части, возвращает готовый фрагмент соединения.
- **Инструмент 3 — `query_build`** — каркас запроса по описанию задачи. Вспомогательный: результат нужно доводить руками.
- **Инструмент 4 — `query_validate`** — сверка запроса с метаданными: таблицы, табличные части, виртуальные таблицы и каждое поле, включая точечные пути в два уровня и колонки временных таблиц пакета. В `errors` попадает только доказанное расхождение; там, где утверждать нечего, — `warnings` или молчание.
- **Инструмент 5 — `query_optimize`** — замечания по производительности с приоритетами. Разбирает структуру запроса, а не ищет подстроки.

### MCP-Сервер № 5 — `v8std-mcp`, порт 8765

**Назначение.** Стандарты разработки 1С: текст стандарта по номеру, поиск
по формулировке, расшифровка кодов диагностик АПК / BSL LS / EDT.
Разграничение с соседями: `metadata_*` — про **вашу конфигурацию**,
`platform_help_*` — про то, **как работает** платформа, `v8std_*` — про то,
**как положено** писать.

**Стек.** Чужой сервер из репозитория `zeegin/v8std` (лицензия CC0),
запущенный локально. Своего кода — только `v8std_entrypoint.py`. Код и
корпус приезжают в `./v8std-data` скриптом `scripts/fetch_v8std.py` и
монтируются в контейнер только на чтение; версия и дата фиксируются в
`v8std-data/FETCH.json`. Семантика считается их собственными
хеш-эмбеддингами, поэтому образ лёгкий — ни `torch`, ни моделей.

- **Инструмент 1 — `v8std_get_page`** — полный текст стандарта или диагностики по id (`std783`). Главный: номер агент видит постоянно, доставать текст должен точно и без семантики.
- **Инструмент 2 — `v8std_search`** — поиск по формулировке, номеру или коду диагностики.
- **Инструмент 3 — `v8std_explain_diagnostics`** — список кодов линтера → диагностики, сгруппированные со связанными пунктами стандартов. Мост от `bsl_check_*`, см. поле `std_lookup` в его ответе.
- **Инструмент 4 — `v8std_get_related`** — переходы стандарт ↔ диагностика ↔ стандарт.
- **Инструмент 5 — `v8std_explain_snippet`** — подбор стандартов по фрагменту BSL/SDBL.

**Почему локально, а не публичный `https://ai.v8std.ru/mcp`.** Публичный
адрес рабочий и подключается одной строкой, но `v8std_explain_snippet`
отправляет туда фрагмент кода — авторы прямо просят не слать закрытый код.
Плюс требование к набору: работать без интернета и не зависеть от чужой
доступности. Переключение на публичный — одна строка в `.cursor/mcp.json`:

```json
"v8std": { "url": "https://ai.v8std.ru/mcp" }
```

**Авторизации у него нет.** Bearer из `mcp_auth.py` — наша схема, чужой
сервер про неё не знает. Поэтому порт публикуется только на `127.0.0.1`,
как у Neo4j и Qdrant, которые тоже без токена.

### Граф и выгрузка: шпаргалка

Для выгрузки в git-репозитории (`WORKSPACE_DIR` — корень репозитория,
`CONFIG_SUBDIR=src`). Подробности — «Обновление выгрузки через git» ниже.
Все команды — PowerShell из корня этого репозитория.

| Задача | Как |
|---|---|
| доиндексировать то, что изменилось | `.\scripts\graph-refresh.ps1` — секунды |
| посмотреть, что изменится, ничего не меняя | `.\scripts\graph-refresh.ps1 -DryRun` |
| найти правки, о которых никто не сообщил | `.\scripts\graph-refresh.ps1 -Reconcile` |
| собрать граф заново | `.\scripts\graph-refresh.ps1 -Full` — ~10 минут |
| агент поправил файлы в `src/` | агент вызывает `metadata_refresh(paths=[…])` — правило для AGENTS.md в `docs/agents/metadata-refresh.md` |
| обновлять граф автоматически | `.env`: `WATCHER_ENABLED=true`, `SOURCE_POLL_SEC=60` (или `300`), затем `docker compose up -d --no-deps --force-recreate workspace-watcher` |
| свежий ли граф | `metadata_stats` → блок `source`, поле `hint` говорит, что делать |
| проверить на стенде, что частичное обновление работает | `.\scripts\check-graph-refresh.ps1` — сценарии «пришла выгрузка» и «правка руками», итог ПРОЙДЕНО/ПРОВАЛ, протокол в `logs\` |
| где лог | ручной запуск — `logs\graph-refresh-<дата>.log`; watcher — `docker logs -f workspace-watcher` |
| после обновления кода стека | `docker compose build metadata-indexer workspace-watcher mcp-metadata-graph`, затем `docker compose up -d --no-deps mcp-metadata-graph workspace-watcher` |

Индексер, watcher и ручной запуск друг другу не мешают: граф пишет один
процесс, остальные ждут (аренда записи, `FIX-39`). Полная индексация идёт
в 4 процесса (`METADATA_WORKERS`, см. «Фаза 2 графа» ниже).

архивация меняет ссылки, и до коммита, потому что после него правка
документа становится вторым коммитом «про то же самое».

### Обновление выгрузки через git (`SRC`, PLAN-11)

Если выгрузка лежит в git-репозитории, граф узнаёт об изменениях у git, а
не обходом 56 тысяч файлов через границу Docker Desktop. Найти изменения
стоит секунды вместо 3–12 минут, `docker compose up` на неизменившейся
выгрузке не уходит в полную индексацию, а возврат правок агента
(`git stash`) граф замечает сам.

#### Раскладка — одна для двух случаев

```
<корень репозитория>/        ← WORKSPACE_DIR; .git здесь
├── .git/
├── AGENTS.md, .cursor/, openspec/   ← служебное, в граф не идёт
└── src/                     ← CONFIG_SUBDIR; Configuration.xml здесь
```

| | Клон `ubd_for_ai` из GitLab | Своя выгрузка |
|---|---|---|
| Откуда `.git` | `git clone` | `.\scripts\dump-and-commit.ps1 -Repo <путь> -Init -SkipDump` |
| Новая версия | `ubd-git-sync`: `pull --ff-only` (утром и при старте чата) | выгрузка в `src\` + коммит: `.\scripts\dump-and-commit.ps1 -Repo <путь> …` |
| Правки агента | `metadata_refresh` из чата | то же |

`.env`:

```dotenv
WORKSPACE_DIR=D:/work/ubd_for_ai     # корень репозитория, НЕ src
CONFIG_SUBDIR=src
SOURCE_MODE=auto                     # git, если есть .git; иначе legacy
```

После правки `.env` — пересоздать сервисы, которые видят выгрузку:

```powershell
docker compose build
docker compose up -d --no-deps --force-recreate mcp-metadata-graph mcp-bsl-checker workspace-watcher
docker compose up metadata-indexer
```

Последняя строка — один раз, при переходе. Индексер увидит, что
состояния источника ещё нет, проверит граф прежним способом (обход,
минуты) и, если выгрузка не менялась, примет граф как есть — **без**
полной индексации. Дальше каждый старт сверяет только `HEAD`.

#### Как граф узнаёт об изменениях

Граф помнит коммит, по которому собран (`indexed_sha`), и файлы, которые
агент правил поверх него (`dirty`). На каждом шаге три сравнения на файл:
что в графе, что на диске, что в `HEAD`. Граф ≠ диск — файл
переиндексируется; диск ≠ `HEAD` — файл в `dirty`; диск = `HEAD` — из
`dirty` уходит.

| Что произошло | Кто сообщает | Стоимость |
|---|---|---|
| `ubd-git-sync` подтянул выгрузку, или вы закоммитили свою | сдвинулся `HEAD` → `git diff` | секунды |
| агент записал файлы в `src/` | агент: `metadata_refresh(paths=[…])` | только эти файлы |
| вы вернули `src/` к канону (`restore-src-canon.ps1`) | файлы из `dirty` снова = `HEAD` | секунды |
| правка руками, о которой никто не сказал | сверка (`-Reconcile`, ночью по расписанию) | `git status`, минуты |

Корневые файлы (`Configuration.xml`, `ConfigDumpInfo.xml`) в граф не идут
и частичное обновление не блокируют (`SRC-1`): граф их не читает, а
`ConfigDumpInfo.xml` меняется с каждой выгрузкой из хранилища.

#### Ручной запуск доиндексации

Работает всегда — включён watcher или нет. Все три способа делают одно и
то же:

| Откуда | Команда |
|---|---|
| PowerShell, из корня репозитория стека | `.\scripts\graph-refresh.ps1` |
| Linux / WSL | `make graph-refresh` или `docker compose run --rm --entrypoint python metadata-indexer /app/apply_changes.py` |
| чат с агентом | `metadata_refresh()` |

| Ключ PowerShell | `make … ARGS=` | Что делает |
|---|---|---|
| (нет) | (нет) | доиндексировать изменившееся |
| `-DryRun` | `--dry-run` | показать план, ничего не меняя |
| `-Reconcile` | `--reconcile` | сверка: найти правки, о которых никто не сообщил |
| `-Full` | `--full` | полная индексация (после `PLAN-12` — десятки минут), с подтверждением |
| `-ForceUnlock` | `--force-unlock` | снять аренду, если её держатель упал |

Коды выхода: `0` — готово или делать нечего; `1` — часть файлов не
обновилась, состояние не сдвинуто (повторный запуск повторит); `2` —
Neo4j не отвечает; `3` — нужна полная индексация или граф ещё не
индексировался; `4` — граф сейчас обновляет кто-то другой.

Полный лог каждого запуска `graph-refresh.ps1` сохраняется в
`logs\graph-refresh-<дата>.log`, путь печатается в конце. Не добавляйте
`*>&1 | Tee-Object`: до `FIX-40` это обрывало скрипт на первой строке в
stderr, а запущенная индексация продолжалась без лога.

#### Автоматический режим — watcher

Выключен по умолчанию. Включить — две строки в `.env`:

```dotenv
WATCHER_ENABLED=true
SOURCE_POLL_SEC=60          # раз в минуту; 300 — раз в 5 минут (30…3600)
```

и пересоздать один контейнер (`--no-deps` — чтобы не поднять заодно
индексер):

```powershell
docker compose up -d --no-deps --force-recreate workspace-watcher
docker logs -f workspace-watcher
```

В логе через ~30 секунд: `mode: GIT (interval=60s)` и
`watcher запущен, жду изменений...`. Дальше — строка на каждый такт, где
что-то обновилось, и раз в час «жив». Выключить — `WATCHER_ENABLED=false`
и та же команда.

Такт в режиме git читает только `.git` и несколько файлов — держать
watcher включённым круглосуточно дёшево (в отличие от режима poll ниже).

Дополнительно (`.env`): `SOURCE_RECONCILE_AT=03:00` — ночная сверка;
`SOURCE_FULL_REINDEX_AT=sat 02:00` — плановая полная индексация (сбрасывает
долг частичных обновлений); `SOURCE_AUTO_FULL=true` — разрешить watcher'у
самому запускать полную, когда частичной не обойтись (по умолчанию он
только напоминает); `TZ` — пояс для расписаний.

#### Правило для агента

Граф не видит незакоммиченные правки, пока о них не сказали. Строки для
AGENTS.md вашего репозитория выгрузки (или правила / скилла) — в
`docs/agents/metadata-refresh.md`.

#### Цикл с клоном `ubd_for_ai`

1. Агент правит `src/`, вызывает `metadata_refresh` — граф видит правки
   сразу.
2. Вы собираете .cf и заливаете в хранилище.
3. `.\scripts\restore-src-canon.ps1` — возвращает `src/` к `HEAD` (правки
   уходят в `git stash`, не удаляются) и запускает `ubd-git-sync`.
   Пока `src/` изменён, sync не тянет (`dirty_src`).
4. Через час выгрузка из хранилища приходит в GitLab с вашими правками;
   sync подтягивает её, граф догоняет по `git diff`.

#### Свежий ли граф

`metadata_stats` → блок `source`: режим, `HEAD` против `indexed_sha`,
`dirty_count`, `needs_full`, включён ли watcher, и `hint` — что делать.
Если watcher выключен, а граф отстал, там так и написано.

#### Когда всё-таки полная индексация

- изменений больше `METADATA_MAX_PARTIAL` (300 единиц) — например, неделю
  не подтягивали выгрузку;
- проиндексированного коммита нет в истории (force-push);
- сменился `CONFIG_SUBDIR`; `metadata_stats` говорит `needs_full`;
- долг частичных обновлений выше порога (см. ниже).

Цикл сам её не запускает (если не `SOURCE_AUTO_FULL=true`) — пишет в лог и
в `metadata_stats`. Запуск: `.\scripts\graph-refresh.ps1 -Full`. После
`PLAN-12` это ~10 минут на боевой выгрузке, поэтому `SOURCE_AUTO_FULL=true`
стал разумным выбором для watcher'а.

### Обновление выгрузки без git (режим legacy): 3–12 минут или полная индексация

Всё ниже — для выгрузки, которая лежит не в git-репозитории
(`SOURCE_MODE=legacy` или нет `.git`). Так стек работал до `SRC`, и так он
работает и сейчас, если git нет.

Главный вопрос при обновлении конфигурации — когда граф перестроится
частично, а когда целиком. Разница в двадцать раз, и определяется она не
объёмом правки, а **тем, что вы запустили**.

#### Два разных механизма

| | Полная переиндексация | Частичное обновление | Watcher |
|---|---|---|---|
| Что запускает | контейнер `metadata-indexer` | `apply_changes.py` вручную | контейнер `workspace-watcher` |
| Когда стартует | при `docker compose up` | только когда вы его вызвали | сам, через 3 с после сохранения файла |
| Время | **~10 минут** (до `PLAN-12` — 1,5–2 часа) | **3–12 минут** | секунды на файл |
| Что делает | сносит слой и собирает заново | правит только изменившиеся единицы | зовёт `metadata_upsert_file` на каждый файл |
| Отпечатки исходников | пересчитывает | пересчитывает | **не трогает** |

**Ловушка.** `mcp-metadata-graph` зависит от `metadata-indexer`, а тот — от
`neo4j`. Поэтому обычный `docker compose up` запускает индексер, и если
выгрузка изменилась, вы получите полную индексацию (~10 минут). Чтобы поднять серверы, не
трогая индексацию:

```powershell
docker compose up -d --no-deps mcp-metadata-graph mcp-query-builder mcp-platform-help mcp-bsl-checker v8std-mcp
```

#### Порядок после обновления выгрузки

Все команды — **из корня репозитория** (там, где `docker-compose.yml` и
`.env`). Скрипт читает выгрузку из `/data/repo/<CONFIG_SUBDIR>` внутри
контейнера, а это каталог из `WORKSPACE_DIR` в `.env` (по умолчанию
`./workspace`). Тот же каталог видят `mcp-metadata-graph` и
`workspace-watcher`:

```dotenv
WORKSPACE_DIR=D:/projects/Cursor/my_config    # ваш путь к выгрузке
CONFIG_SUBDIR=                                # пусто — конфигурация в корне
```

**0. Один раз — подготовка.**

- Если репозиторий обновлялся, пересоберите образ, иначе в контейнере
  останется старая версия скриптов (или их не будет вовсе):

  ```powershell
  docker compose build metadata-indexer
  ```

- **После каждой полной индексации** сохраните состояние по объектам.
  Полный индексер его не пишет, и без этого шага `apply_changes.py`
  ответит «сохранённого состояния нет — первая индексация» (код 3) либо
  будет сравнивать со снимком, сделанным до полной индексации:

  ```powershell
  docker compose run --rm --entrypoint python metadata-indexer /app/what_changed.py --save
  ```

  Это безопасно: пишется только служебный блок с отпечатками, узлы и
  рёбра графа не трогаются.

**1. Посмотреть, что изменилось** (обход диска, 3–12 минут, ничего не
меняет):

```powershell
docker compose run --rm --entrypoint python metadata-indexer /app/apply_changes.py --dry-run
```

**2. Применить**, если в плане нет причины для полной:

```powershell
docker compose run --rm --entrypoint python metadata-indexer /app/apply_changes.py
```

Скрипт сам обновит и внутреннее состояние, и общий fingerprint — то есть
следующий старт контейнеров переиндексацию не запустит (кроме случая
`METADATA_FINGERPRINT_STRICT=true` — скрипт об этом предупредит).

Коды выхода: `0` — готово или делать нечего; `1` — ошибки при обновлении,
состояние не сохранено, повторный запуск повторит работу; `2` — нет
каталога выгрузки или Neo4j не отвечает; `3` — частичное обновление
невозможно, нужна полная индексация (причина в логе, см. таблицу ниже).

#### А почему это вручную, если есть watcher

`workspace-watcher` умеет то же самое автоматически: следит за каталогом
выгрузки и зовёт `metadata_upsert_file` через три секунды после сохранения
файла. По умолчанию он **выключен**: контейнер стартует, пишет в лог
`WATCHER_ENABLED=false — watcher отключён` и спит.

##### Как включить watcher (режим poll)

Для выгрузки в git — см. «Автоматический режим — watcher» выше: там
другой режим, дешёвый. Здесь — опрос файлов для каталога без git.

**1. `.env`** (в корне репозитория) — поставить `true` и проверить
остальные строки блока «Watcher»:

```dotenv
WATCHER_ENABLED=true            # главный выключатель
WATCHER_MODE=poll               # или auto — poll выберется сам, если нет .git
WATCHER_POLLING_INTERVAL=10     # опрос раз в 10 с; меньше не ставить
WATCHER_USE_POLLING=true        # на Windows/Docker Desktop — только true
METADATA_WATCH_ENABLED=true     # слать изменения в граф (уже true)
ENABLE_WATCH_TOOLS=1            # сервер графа принимает upsert (уже 1)
```

Каталог, за которым следит watcher, — тот же `WORKSPACE_DIR`.

**2. Пересоздать только контейнер watcher'а.** `--no-deps` обязателен:
без него compose потянет по зависимостям `metadata-indexer`, и при
изменившейся выгрузке вы получите полную индексацию (~10 минут).

```powershell
docker compose up -d --no-deps --force-recreate workspace-watcher
```

Если `docker-compose.yml` или код watcher'а обновлялись — сначала
`docker compose build workspace-watcher`.

**3. Проверить лог:**

```powershell
docker logs -f workspace-watcher
```

Примерно через 30 секунд (начальная задержка) должно быть:

```
mode: POLLING (interval=10.0s) — ...
watcher запущен, жду изменений...
```

Если в строке `interval=2.0s` — значение из `.env` до контейнера не
дошло: проверьте, что в `docker-compose.yml` у сервиса `workspace-watcher`
есть `WATCHER_POLLING_INTERVAL`, и пересоздайте контейнер. После
сохранения любого `.bsl`/`.xml` в выгрузке через ~3 с в логе появится
вызов `metadata_upsert_file`.

**Выключить обратно** — `WATCHER_ENABLED=false` в `.env` и та же команда
из шага 2.

**Не забывать:** watcher не обновляет отпечатки исходников (см. ниже),
поэтому перед любым `docker compose up` без `--no-deps` прогоните
`apply_changes.py` — иначе индексер увидит расхождение и уйдёт в полный
прогон.

##### Почему по умолчанию выключен

Причин было две.

**Цена опроса.** На Windows события файловой системы через bind-mount в
контейнер не доходят, поэтому watchdog переключается на polling —
периодически пересканирует всё дерево выгрузки. На 16 тысячах объектов
один обход стоит примерно столько же, сколько явный запуск обновления,
только платится он круглосуточно. Интервал в 10 секунд вместо стандартных
2 снижает эту цену в пять раз; на удобство это не влияет, выгрузка меняется
не чаще чем раз в несколько минут.

**Потеря владения — снята в Заходе 8.** Пофайловый upsert XML пересоздавал
узлы форм без метки `:Module`, рёбра `HAS_METHOD` уходили, и никто об этом
не узнавал: ровно так граф однажды остался без слоя владения кодом на
шесть дней (`FIX-27`). Теперь `upsert_xml_file` возвращает коду владельца
в том же вызове, и одиночный upsert безопасен. Возражение осталось одно —
цена опроса.

**Что watcher не делает.** Он не трогает отпечатки исходников. Граф после
него свежий, а отпечатки старые — и ближайший перезапуск
`metadata-indexer` увидит расхождение и уйдёт в полный прогон. Поэтому даже
с включённым watcher время от времени стоит прогонять `apply_changes.py`:
он приводит отпечатки в соответствие с графом.

#### Когда частичное невозможно

`apply_changes.py` сам откажется работать и скажет, почему. Изменение
корневых файлов (`Configuration.xml`, `ConfigDumpInfo.xml`) больше не
причина (`SRC-1`): граф их не читает.

| Причина | Почему нельзя частично |
|---|---|
| **Изменилось больше 300 единиц** | при таком объёме полная и быстрее, и точнее |
| **Нет сохранённого состояния** | первый прогон обязан быть полным: слой кода собирается глобальным резолвом, из кусков он не сложится. Если полная индексация уже была — выполните `what_changed.py --save` (шаг 0 выше) |
| **Сменён `METADATA_FINGERPRINT_STRICT`** | суммы по содержимому и по `(размер, mtime)` несравнимы |

Порог числа единиц меняется через `METADATA_MAX_PARTIAL`.

#### Полная переиндексация

```powershell
$env:METADATA_FORCE_REINDEX="true"
docker compose up -d --force-recreate metadata-indexer
docker logs -f metadata-indexer
$env:METADATA_FORCE_REINDEX="false"     # переменная живёт до закрытия окна

# когда индексер закончил — сохранить состояние для apply_changes.py
docker compose run --rm --entrypoint python metadata-indexer /app/what_changed.py --save
```

Раздельно: `METADATA_FORCE_XML` (слой метаданных — тянет за собой и слой
кода, потому что очистка сносит `:Module`-узлы) и `METADATA_FORCE_BSL`
(только код, около 1,8 часа).

#### Долг частичных обновлений

Слой кода собирается **глобальным** резолвом: тип параметра в модуле A
зависит от вызова в модуле B. Точечное обновление такой сходимости не даёт
— вызовы из чужих модулей в обновлённый помечаются
`stale_after_incremental`, и покрытие медленно падает.

Скрипт печатает долг после каждого прогона. Одна правка модуля — около 150
callsite'ов; порог `METADATA_STALE_DEBT_LIMIT` по умолчанию 20 000, это
примерно 3 % графа вызовов и запас на сотню правок. По достижении порога
скрипт предупредит — тогда стоит прогнать полную.

Долг — предупреждение, а не запрет: работать он не мешает, но чем он
больше, тем менее полны ответы про использование процедур.

#### Почему обход занимает минуты

3–12 минут из времени частичного обновления — это чтение метаданных 56 410
файлов через границу Docker Desktop, около 5 мс на файл. Разброс зависит
от загрузки диска. Уменьшить можно только переносом выгрузки в файловую
систему WSL2 — на ext4 то же самое занимает секунды. Это решение об
инфраструктуре, не о коде.

### Мониторинг первой индексации

`points_count = 0` в Qdrant в течение почти всей работы `help-indexer` — это
**норма, а не зависание**. Индексатор сначала считает все эмбеддинги, потом
одним батчем заливает в Qdrant, и счётчик скачет до полного числа в самом конце.

Главный индикатор живости — загрузка CPU:

```powershell
docker stats --no-stream help-indexer
```

| Симптом | Что значит |
|---|---|
| `CPU % > 400`, память ~2 ГБ | считает, всё в порядке |
| `CPU % < 5`, контейнер `Up`, `points_count = 0` | возможно завис, смотреть логи |
| `Exited (0)`, `points_count > 0` | завершён успешно |
| `Exited (137)` | OOM — поднять память Docker Desktop до 8 ГБ |
| `Restarting` | крашится в цикле, смотреть логи |

Индексация завершена, когда `metadata-indexer` и `help-indexer` оба в
`Exited (0)`.

Пока идёт индексация справки, граф метаданных уже доступен — `metadata-indexer`
отрабатывает за минуты, и агенту можно задавать вопросы про структуру
конфигурации.

#### Фаза 2 графа (код BSL): процессы и замеры (`PLAN-12`)

Полная индексация графа — это на боевой выгрузке часы, и почти всё время
уходит на фазу 2: разбор BSL и фикс-пойнт резолва вызовов. Что про неё
видно в логе `docker compose logs -f metadata-indexer`:

| Строка | Что значит |
|---|---|
| `Процессов на разбор и резолв: 4 (METADATA_WORKERS=auto)` | сколько ядер работает; `docker stats` покажет до ~400 % CPU |
| `список файлов готов: N (без повторного обхода выгрузки)` | список `*.bsl` взят из git, второй обход каталога не нужен |
| `разбор BSL: … gc 12%` / `резолв, итерация 1: … gc 12%` | доля времени сборщика мусора Python с прошлой строки |
| `сборщик мусора: 41 мин всего, сборок …` | итог по фазе |
| `объявление без конца — пропуск (путь:строка)` | процедура без `КонецПроцедуры`; первые десять мест — сводкой в конце разбора |

Настройки — в `.env` (описание в `.env.example`):

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `METADATA_WORKERS` | `auto` = min(4, ядер − 1) | процессы на разбор и резолв; `1` — прежний путь в один процесс |
| `METADATA_GC_FREEZE` | `false` | «заморозить» разобранные модули для сборщика мусора; включать по итогам замера «gc N%» |
| `METADATA_PROFILE` | `false` | 30 самых тяжёлых функций резолва в лог; резолв на это время идёт в один процесс |

Результат с любым `METADATA_WORKERS` одинаков — это проверяет
`tests_parallel_resolve.py`. Если на стенде числа в итоге (модули,
процедуры, рёбра, покрытие) с `auto` и с `1` разошлись — это дефект:
вернуть `METADATA_WORKERS=1` и прислать оба лога.

## Troubleshooting

### Инструмент вернул `graph_empty` или `neo4j_unavailable`

Два разных отказа, и различать их важно — ни один из них не значит, что
искомого объекта нет в конфигурации.

`graph_empty` — Neo4j отвечает, но в графе нет ни одного `:MetadataObject`.
Индексация не выполнялась или не завершилась:

```powershell
docker compose run --rm -e METADATA_FORCE_REINDEX=true metadata-indexer
```

`neo4j_unavailable` — база не отвечает: контейнер не поднят, не успел
стартовать или не сходится пароль. В поле `detail` лежит исходная ошибка.

```powershell
docker compose ps neo4j
docker compose logs --tail=50 neo4j
```

`metadata_stats` работает в обоих случаях (при пустом графе вернёт нули и
`graph_empty: true`) — с него и стоит начинать диагностику.

### Cursor подключается, но все инструменты отдают 401

Секрет в `.cursor/mcp.json` не совпадает с `MCP_SHARED_SECRET` в `.env`, либо
там остался плейсхолдер. Сверить и вписать заново; после правки `.env` нужен
`docker compose up -d` — секрет читается на старте контейнера.

### Серверы не стартуют, в логе `[FATAL]` и код выхода 78

Не задан `MCP_SHARED_SECRET` или `NEO4J_PASSWORD`. Сообщение в логе называет
конкретную переменную.

### Скрипты с хоста возвращают `503` на каждый сервер

Системный HTTP-прокси Windows (v2rayN, Clash, Shadowsocks, корпоративный).
Python `httpx` подхватывает его из реестра даже без переменных `HTTP_PROXY`,
и запросы на `localhost` уходят через прокси, который не умеет форвардить
в loopback. `curl.exe` прокси не использует, поэтому работает — по этому
расхождению диагноз и ставится.

```powershell
python -c "import urllib.request; print(urllib.request.getproxies())"
```

Если вывело адрес прокси:

```powershell
$env:NO_PROXY = "localhost,127.0.0.1"                                       # сессия
[System.Environment]::SetEnvironmentVariable("NO_PROXY","localhost,127.0.0.1","User")  # постоянно
```

Внутри контейнеров системный прокси не виден — проблема только у скриптов
с хоста.

### `docker compose ps` показывает контейнер удалённого сервиса

Compose не удаляет контейнеры исчезнувших сервисов автоматически.

```powershell
docker rm -f <имя>
# или
docker compose down; docker compose up -d
```

### `help-indexer` ушёл в `Exited (137)`

OOM. Docker Desktop → Settings → Resources → Memory → минимум 8 ГБ, сохранить,
дождаться перезапуска, затем `docker compose up -d help-indexer`.

### `FutureWarning` про `get_sentence_embedding_dimension`

Косметика. `sentence-transformers` предупреждает о переименовании метода
в будущей версии. Игнорировать.

### Python-скрипты падают с `ImportError`

Не установлены зависимости хоста:

```powershell
pip install -r .\evals\runner\requirements.txt
```

### `v8std-mcp` не стартует, в логе `[FATAL] нет индекса`

Корпус не забран. `python scripts/fetch_v8std.py`, затем
`docker compose up -d v8std-mcp`. Если сеть идёт через системный прокси,
экспортируйте `HTTPS_PROXY` перед запуском скрипта.

### `fetch_v8std.py` падает с `HTTP 404` на модулях сервера

Автор `zeegin/v8std` переложил файлы в репозитории. Так было 17 сентября
2026 (`V8STD-2`): сервер уехал из `scripts/` в пакет `runtime/`. Скрипт в
этом случае **ничего не пишет на диск** — рабочий `v8std-data/` остаётся
как был, и уже поднятый контейнер продолжает работать.

Лечение — сверить список `REPO_FILES` в `scripts/fetch_v8std.py` с их
`delivery/mcp/Dockerfile` (там перечислено ровно то, что нужно серверу).
Временный обход — закрепить последнюю рабочую ревизию:

```powershell
python scripts/fetch_v8std.py --ref <commit>
```

После обновления кода сервера образ пересобирается (у него могли
появиться зависимости — с `V8STD-2` это `markdown-it-py`):

```powershell
docker compose build v8std-mcp
docker compose up -d --force-recreate v8std-mcp
```

### `v8std-mcp` в статусе `unhealthy`, но контейнер жив

`/healthz` у этого сервера отдаёт 503, пока индекс не загружен, — то есть
healthcheck проверяет данные, а не только процесс. Смотрите
`docker logs v8std-mcp`: скорее всего, он пытается скачать индекс с
v8std.ru и не может (нет сети или прокси).

### `v8std_explain_snippet` отвечает пусто или невпопад

Не забрался `retrieval-rules.yml` — без него подбор по сниппету теряет
алиасы и сигнатуры вызовов. Сервер об этом пишет в лог при старте.
Лечится повторным `python scripts/fetch_v8std.py`.

### `bsl_check_*` не находит замечаний на заведомо плохом коде

Сначала проверьте очевидное: `WORKSPACE_DIR` в `.env` должен указывать на
каталог с `.bsl` и `.xml`. Пустой каталог даёт «без диагностик» —
анализировать нечего.

Если выгрузка на месте, а замечаний всё равно ноль — воспроизведите анализ
руками и посмотрите на число разобранных файлов:

```powershell
docker exec mcp-bsl-checker sh -c "mkdir -p /tmp/t && printf 'Procedure Test()\nBeginTransaction();\nCommitTransaction();\nEndProcedure\n' > /tmp/t/Module.bsl && java -jar /opt/bsl-language-server/bsl-ls.jar --analyze --srcDir /tmp/t --outputDir /tmp/t --reporter json && cat /tmp/t/bsl-json.json"
```

`Analyzing files... 0/0` означает, что анализатор не увидел ни одного файла
— обычно из-за неверного пути или ключа. Ключ именно `--srcDir`: `--src`
BSL LS молча игнорирует и берёт текущий каталог. Отчёт называется
`bsl-json.json` и кладётся в `--outputDir`.

После `FIX-9` инструмент такой отказ больше не прячет: если анализатор не
создал отчёт, в ответе будет поле `error` с `stdout`, `stderr` и кодом
возврата, а не `status: ok`. Ответ `ok` теперь означает ровно одно —
анализ прошёл и замечаний нет.
