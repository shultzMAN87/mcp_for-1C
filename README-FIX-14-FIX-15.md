
Диагностика показала, каких именно владельцев не нашлось:

```
"DataProcessor.КонсольЗапросов.Form.Форма",            528, uzel_est=FALSE
```

Все — модули форм.

### Заодно: два «расхождения», которые оказались нормой

Мой список ожидаемых чисел был неверен, и это стоило лишней тревоги.
`CALLS` и `OPERATES_ON` пишутся через `MERGE (a)-[e]->(b)`, то есть
схлопываются по паре узлов. Пять вызовов одной процедуры из другой — это
пять `:CallSite`, но одно ребро `CALLS`.

* `CALLS` 428 918 вызовов → 351 694 пары. Норма.
* `OPERATES_ON` 105 305 → 67 620 пар. Норма.

Сравнивать входной счётчик с числом рёбер в базе для дедуплицируемых связей
нельзя — это разные величины. Ровно поэтому `FIX-15` считает **обработанные
строки**, а не созданные связи.

## `FIX-14` — HAS_METHOD и метки модулей

Владельцем метода может быть узел с разными метками, а запрос был один:

```cypher
MATCH (m:MetadataObject {id: r.src}), (c:Callable {id: r.dst})
```

Общие модули приходят из слоя 1 с меткой `:MetadataObject`. Модули объектов
и менеджеров создаёт `write_module_nodes` — тоже с `:MetadataObject`. А
модуль формы — это узел `:Form`, созданный в слое 1 как

```python
"MERGE (n:Form {id: r.id}) "     # без :MetadataObject
```

которому фаза 2 лишь **дописывает** метку `:Module`. Под `MATCH
(m:MetadataObject …)` он не подходит никогда.

Арифметика подтверждает: `MetadataObject` в базе 16 482 = 10 639 (слой 1) +
5 843 (новые узлы ObjectModule 2 084 + ManagerModule 3 759). Формы в это
число не входят.

Стало — два запроса по метке владельца, `bsl_resolver` проставляет
`src_label` из `module_kind`. Ровно та же конструкция, что `PERF-4` завёл
для `HAS_ATTRIBUTE`.

**Это третий случай одной ошибки подряд.** `HAS_ATTRIBUTE` — источник без
метки. `HAS_METHOD` — источник с одной меткой вместо двух. Оба раза
диагноз один: запрос предполагает, что у всех узлов одного вида одинаковые
метки, а это неверно. Тест `test_every_match_operand_has_label` ловил
только первый вариант — теперь добавились тесты и на второй.

## `FIX-15` — недостача записи больше не молчит

Более важная правка, чем сам `FIX-14`.

Все писатели возвращали `len(rows)` — число строк, которые **отправили**, а
не которые записались. Любой `MATCH … MERGE` на ненайденном узле молча
пропускает строку: ни ошибки, ни предупреждения. Поэтому потеря 158 961
ребра прошла с бодрым логом об успехе и нашлась только ручной сверкой
счётчиков с базой — то есть **могла не найтись вовсе**.

Стало — к каждой записи добавляется `RETURN count(*) AS written`, и при
недостаче в лог идёт:

```
WARNING рёбра HAS_METHOD:Form: записано 0 из 158961 — 158961 строк
        не нашли узлов и пропущены молча. Это почти всегда несовпадение
        меток или id между слоями; сверьте запрос в EDGE_QUERIES с тем,
        какие метки реально висят на узлах (см. FIX-14).
```

Счётчики в итоговых строках лога («узлы: …», «рёбра: …») теперь тоже
показывают записанное, а не отправленное.

Для дедуплицируемых связей `RETURN count(*)` считает обработанные строки, а
не созданные рёбра, — то есть отличает «схлопнулось по замыслу» от «не
нашло узел». Ложных предупреждений на `CALLS` и `OPERATES_ON` не будет.

## Что проверить после переиндексации

Слой 1 не трогается, нужна только фаза 2 — около 1,9 часа минус fingerprint.

**1. В логе не должно быть ни одного `WARNING … не нашли узлов`.** Если
появится на каком-то другом типе рёбер — это следующий такой же дефект, и
теперь он виден сразу, а не через ручную сверку.

**2. Повторить сверку:**

```powershell
$pw = (((Get-Content .env) -match '^NEO4J_PASSWORD=') -replace '^NEO4J_PASSWORD=','').Trim()
```

```powershell
@'
MATCH ()-[r:HAS_METHOD]->() RETURN count(r) AS has_method;
MATCH (c:Callable) WHERE NOT ()-[:HAS_METHOD]->(c) RETURN count(c) AS bez_vladelca;
MATCH (o)-[:HAS_METHOD]->(:Callable) RETURN count(DISTINCT o) AS obj_s_kodom;
'@ | docker exec -i neo4j cypher-shell -u neo4j -p $pw
```

Ждём `has_method` ≈ 231 113, `bez_vladelca` = **0**, `obj_s_kodom` ≈ 14 000
вместо 6 024.

Обратите внимание: во второй и третьей строке метка владельца не указана
намеренно. Проверка не должна повторять допущение, которое и оказалось
дефектом.

**3. Затем — приёмка в Cursor** по трём вашим приоритетным задачам. До этого
патча вопросы про методы формы отвечали бы пусто, и это выглядело бы как
«в конфигурации нет такого кода».
